# Проектные соглашения OpenSpec

## Имена changes

- Исключение для этого инфраструктурного проекта: головной BPM-тикет не задан.
  Используй содержательное имя в русской транслитерации без номера тикета;
  заголовок proposal также без вымышленного номера. Остальные правила сохраняются.

- Формат: `<номер-головного-тикета>-<краткая-суть>`.
- Номер головного тикета бери из имени корневой папки прикладного проекта:
  целиком числового имени либо числового префикса, отделённого от названия
  пробелом или тире. Например, `1690395` или `1690395 — Отчёты`.
  При отдельном хранилище OpenSpec используй папку прикладного проекта,
  а не имя хранилища. Если проект или номер неоднозначен, уточни его.
- Краткую суть определяй по требованиям и доступным материалам задачи.
  Используй русские слова в транслитерации, строчные латинские буквы,
  цифры и одиночные дефисы. Избегай неочевидных сокращений.
- Пример: `1690395-otchet-rabochego-vremeni`.
- Номер дочернего тикета или ERR не подменяет номер головного тикета;
  дополнительные связи указывай в документах. Не придумывай номера.
- Для нескольких changes одного проекта сохраняй общий номер тикета,
  различая изменения по сути. При совпадении имени сначала проверь,
  не относится ли поручение к существующему change.
- Выбирай имя до вызова `openspec new change`. Существующие changes
  автоматически не переименовывай.

## Язык и заголовки

- Пиши обычный текст документов и ответы пользователю на русском языке.
- Служебные заголовки OpenSpec, технические идентификаторы и имена файлов сохраняй.
- Начинай proposal с содержательного русского заголовка с номером головного
  тикета, например: `# 1690395 — Отчёт рабочего времени сотрудников`.
  Общий заголовок вроде «Постановка изменения» дополняй конкретной сутью;
  сохраняй служебные разделы шаблона OpenSpec.
- В общении называй изменение по содержательному русскому заголовку;
  техническое имя добавляй для однозначной идентификации.

## Связь оценки и фактического времени

Это технические соглашения связи данных; правила самого хронометража задаются общими инструкциями агента. Новый проектный AGENTS.md для них не нужен.

- Оценка выбранного change хранится в его `estimate.md` либо по существующему пути схемы. Версии сохраняют исходный ориентир, состав метрик и охват: полный объём или остаток с обозначенной границы. Пересчёт не меняет согласование и прогресс задач.
- Журнал один на проект: `.codex/time-tracking.md`, если проект не определил другое место. В записи указывай change, существующий TASK-ID/пункт (если он есть), этап работы и при необходимости версию/охват оценки. Не вводи TASK-ID для иной схемы. Исследование, оценивание и реализацию различай; работа до границы оценки остатка не входит в её реализационный факт.
- Достаточно Markdown-записи: идентификатор интервала (например, ID чата + начало), начало/конец с часовым поясом, привязка, активное время, ожидание, подтверждённое время пользователя и ограничения замера. Перед добавлением проверь прежние записи и перекрытия, в том числе других чатов; при уточнении существующего интервала сохрани его идентификатор и основание поправки, не начисляй его снова. Неразделимые пересечения обозначь как ограничение, не суммируй их как независимую работу.
- Общую работу учитывай один раз на уровне change или у фактического владельца. Не распределяй её произвольно по TASK и не прибавляй общий итог change каждой задаче. Журнал хранит затраты, а не второй реестр статусов: выполнение подтверждается задачами и результатами проверок.
- Отсутствие реализации после оценки означает «оценено, не выполнялось», только если это подтверждено. Отсутствие записей само по себе означает неизвестный факт, а не выполнение за ноль часов.
- Записи времени не добавляй в specs/design/tasks. При архивировании сохраняй `estimate.md` с историей и связанными расчётами вместе с change; проверь ссылки из единого журнала и оценки, обнови пути с сохранением идентичности change и интервалов. Журнал не копируй в каждый архив. Если оценка лежит вне change, сохраняй её доступность по ссылке.
