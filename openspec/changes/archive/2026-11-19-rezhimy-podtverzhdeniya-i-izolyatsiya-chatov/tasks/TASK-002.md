## Результат и доказательства

19.11.2026 подтверждены пункты 3.1–3.3 для выбранного в [дизайне](../design.md) маршрута native MCP → HTTP proxy → клиент 1С на отдельной копии файловой базы 8.5.1.1529. SQLite принадлежит proxy. Ключ повтора — канал и request_id, содержимое проверяется по отпечатку. Продуктовые настройки журнала и правила хранения описаны в [контракте](../lifecycle-proxy-partial.md).

| Пункт | Что подтвердил свежий прогон |
|---|---|
| 3.1 | При пути журнала, указывающем на обычный файл, native API вернул operation_store_unavailable. Независимый запрос к тестовой базе подтвердил отсутствие записи. После перезапуска подтверждённый результат сохранился, незавершённый перешёл в unknown. SQLite integrity_check прошёл. |
| 3.2 | Шлюз стенда отбросил первый ответ с operation_id и вернул HTTP 504. Повтор с прежним request_id и тем же кодом вернул исходный ID. get_operation показал running до доставки задержанного итога, затем succeeded с исходным результатом. Изменение кода под старым ключом дало request_conflict. В базе ровно один документ с маркером прогона. |
| 3.3 | Ответ 1С после записи был отброшен перед сохранением в журнале. После перезапуска владельца status и повтор вернули прежний ID и unknown. Запрос к базе нашёл ровно один документ. При тестовой квоте в три записи новая команда отклонена без изменения базы, running и unknown сохранились, status доступен, чужой канал получает operation_not_found. После сдвига часов стенда на 86 401 с результат исчез, а занятый ключ вернул result_expired с прежним ID. Изменённое содержимое под тем же ключом по-прежнему отклоняется. |

Для сверки unknown сначала проверить исходный ID или повторить тот же запрос с тем же request_id и содержимым. Затем независимо прочитать данные 1С по уникальному бизнес-признаку, известному до запуска. В прогоне использовался уникальный маркер документа. При отсутствии однозначного подтверждения сохранить unknown и передать решение о дальнейших действиях оператору.

Проверка платформой ThinClient, Server, HandlersExistence и сборка тестовой EPF прошли. Python — 27/27 тестов по lifecycle и progress. Runtime — 28/28 проверок, все процессы стенда завершены. Отчёт и MCP-ответы (локальный путь `.local/task002-20261119/results.json`), сборка (локальный путь `.local/task002-20261119/build.log`), завершение процессов (локальный путь `.local/task002-20261119/cleanup.json`). Число записей и время изменены только в тестовом владельце. В первой попытке оснастка подменила конструктор в неверном модуле, поэтому квота не применялась. Эта попытка сохранена отдельно. Результат приёмки основан на повторе с исправленной оснасткой и новой копией базы.

Встроенный HTTP, файловый мост и предельные нагрузки в этом прогоне повторно не проверялись. Их прежние доказательства и ограничения приведены ниже. Сквозная и пользовательская приёмка второй очереди ведётся в TASK-010.
