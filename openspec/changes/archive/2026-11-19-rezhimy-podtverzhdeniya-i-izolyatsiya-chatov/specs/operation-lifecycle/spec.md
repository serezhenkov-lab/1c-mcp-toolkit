## Purpose

Получение статуса и позднего результата без повторного исполнения после таймаута.

## ADDED Requirements

### Requirement: Ограниченный промежуточный прогресс

Общий владелец lifecycle SHALL хранить последний ограниченный промежуточный снимок в существующей записи операции и выдавать его через status без повторного исполнения. Исполнитель SHALL посылать события только владельцу, объявившему lifecycle_progress_version=1. Контракт — [протокол](../../../../upravlenie-test-klientom/intermediate-progress.md).

#### Scenario: Длительное ожидание UI
- **WHEN** принятая операция продолжает ожидание условия
- **THEN** status возвращает operation_id, монотонный sequence, scope=intermediate_snapshot, phase, completed_count, elapsed_ms и last_confirmed_step; произвольный текст UI и процент готовности не допускаются. Чтение не ставится в очередь UI-команд, снимок не считается окончательным результатом.

#### Scenario: Повторное или устаревшее событие
- **WHEN** доставлен повтор, меньший sequence или уменьшение completed_count/elapsed_ms
- **THEN** сохранённый снимок не откатывается; подтверждённый итог и unknown не возвращаются в running, событие не вызывает UI повторно.

#### Scenario: Недоступность прогресса
- **WHEN** необязательное событие не доставлено, отклонено по квоте либо владелец не объявил поддержку
- **THEN** UI не повторяется и исход действия не заменяется ошибкой прогресса; при замеченном исполнителем сбое доставки итоговая диагностика содержит progress_delivery_failed.

#### Scenario: Восстановление и изоляция
- **WHEN** владелец перезапущен без подтверждённого итога
- **THEN** операция остаётся unknown с последним сохранённым снимком, который не доказывает завершение; чужой канал не получает его, terminal result вытесняет промежуточные данные.

### Requirement: Статус и поздний результат

<a id="ol-01"></a>

Toolkit SHALL выдавать operation_id и предоставлять через native MCP состояние и результат операции. Состояние SHALL различать ожидание подтверждения/очереди, выполнение, подтверждённый итог и unknown. Таймаут ожидания ответа SHALL не удалять запись операции или её поздний результат. Статус SHALL быть доступен без повторного запуска кода.

#### Scenario: Поздний успех
- **WHEN** клиент перестал ждать, но команда затем завершилась успешно
- **THEN** результат можно получить по прежнему ID в пределах объявленного срока хранения; таймаут не выдаётся за отмену.

#### Scenario: Ожидание решения
- **WHEN** операция ожидает разрешения пользователя
- **THEN** доступны её ID и статус ожидания без удержания транзакции базы; чтение статуса не запускает команду повторно.

#### Scenario: Квота исполнения не блокирует чтение
- **WHEN** журнал достиг квоты новых команд, а клиент читает состояние ранее принятой операции
- **THEN** чтение не резервирует новую операцию и не требует свободной admission-квоты; изоляция канала, срок результата и защита ключей принятых команд сохраняются.

### Requirement: Повтор и восстановление состояния

<a id="ol-02"></a>

Повтор обращения к принятой операции SHALL возвращать её состояние/результат без нового исполнения. Иной код под тем же ключом SHALL отклоняться. После сбоя с неизвестным исходом SHALL сохраняться unknown, без автоматического повтора. Хранение SHALL быть ограниченным с явным result_expired; очистка истории SHALL не разрешать повтор старой команды.

#### Scenario: Повтор после таймаута
- **WHEN** клиент повторяет обращение с тем же ключом операции и содержимым
- **THEN** возвращается состояние первой операции; второе изменение данных не выполняется.

#### Scenario: Конфликт содержимого
- **WHEN** с прежним ключом поступает другой код или параметры
- **THEN** возвращается ошибка конфликта без исполнения.

#### Scenario: Сбой исполнителя
- **WHEN** ответ потерян и подтверждённого итога после восстановления нет
- **THEN** состояние unknown сохраняется до сверки; запуск заново не выполняется автоматически и откат не утверждается.

#### Scenario: Истёк срок хранения
- **WHEN** клиент запрашивает удалённый по сроку результат или повторяет просроченный ключ
- **THEN** получает явный result_expired либо отказ просроченного ключа; новый запуск под старым ключом не создаётся. Running/unknown не удаляются автоматически ради квоты.

### Requirement: Обслуживание журнала без длительного захвата HTTP

После готовности embedded-владельца компактация SHALL уступать клиентский поток между ограниченными порциями работы, сохраняя обработку HTTP и чтение состояния. Изменение журнала во время подготовки SHALL не теряться; commit и установка checkpoint SHALL образовывать непрерываемый участок с прежним безопасным восстановлением.

#### Scenario: Чтение во время очистки
- **WHEN** на готовом embedded-владельце выполняется компактация большого журнала и поступают health/status запросы
- **THEN** запросы обслуживаются между шагами; весь проход журнала не удерживает обработчик HTTP до окончания очистки.

#### Scenario: Запись между шагами
- **WHEN** до commit принята новая запись или обновлено состояние операции
- **THEN** незавершённая подготовка отменяется, запись сохраняется в действующем журнале, следующая подготовка включает её; старый checkpoint не перезаписывает новое состояние.
