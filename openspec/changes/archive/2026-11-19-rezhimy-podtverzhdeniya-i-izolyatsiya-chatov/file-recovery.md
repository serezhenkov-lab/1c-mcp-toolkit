# Автовосстановление файлового канала — 17.11.2026

Владелец: TASK-002/3.1–3.3, диагностика TASK-006. Зависимые пункты UI-плана: 2.3, 6.1–6.2. Реализована и проверена доступная Windows-ветка; полные пункты и пользовательская приёмка остаются открытыми.

## Причина и исправление

Ранее `check_unresolved` прерывал startup HTTP-прокси при старом `.running`/`.request.json`. Журнал сохранял unknown, но получить статус и продолжить работу без ручного архивирования указателя было нельзя.

Теперь основной менеджер Toolkit захватывает `executor.lock` посредством `ФайловыйПоток` до чтения current/session. Запись разрешена одному исполнителю; handle удерживается до конечного ответа всех принятых команд, включая асинхронный UI. После атомарного переименования request → running, но до вызова команды, менеджер публикует `<id>.fence.json` с version/channel/session/id. Событие lifecycle не освобождает блокировку. Это изменение существующего менеджера/транспорта, не клиентский наблюдатель.

После аварии proxy проверяет каждый оставшийся запрос: точный маркер захвата и запись того же канала/ID в общем журнале с восстановленным unknown либо конечным состоянием. Запросы сканируются перед running: переход между двумя чтениями каталога не должен исчезнуть из обоих наборов. Затем старый session.json отзывается. Под эксклюзивным Windows write-handle архивируется старый указатель в `retired-current.json` и публикуется новый случайный сеанс. Старые файлы не переносятся, не исполняются повторно, поздний ответ автоматически не превращает unknown в успех.

HTTP запускается независимо от ожидания файлового исполнителя. `/health.file_recovery` содержит состояния ready/blocked и причину, без идентификаторов каналов. Пока старый исполнитель занят, причина — `executor_busy`; новый файловый сеанс не публикуется. После освобождения lock восстановление повторяется автоматически. Канал остаётся зарезервирован за файловым consumer, другой транспорт его не перехватывает.

## Открытый остаток

Автовосстановление намеренно не разрешено для pending-команд без индивидуального маркера захвата, без записи общего журнала и для неподтверждённой семантики блокировок других ОС. Нужна отдельная процедура сверки/восстановления legacy и unclaimed запросов; безопасный отказ не закрывает это требование. Восстановление на перенаправленном RDP-диске, Linux, клиент-серверной базе и полная матрица аварий не проверены. Состояние unknown сверяется по фактическим данным, а не повторным действием.

Рабочая установка не обновлялась, наблюдатель не подключён, анонимизация отложена. Выполненные ранее независимые проверки не повторялись. Открытые отметки сохранены.
