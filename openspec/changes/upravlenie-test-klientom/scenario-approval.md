# TASK-021 — ожидание подтверждения и recovery после решения

17.11.2026. Проверен следующий пакет 11.3 на отдельной файловой базе 8.5.1.1529. Продуктовый код не менялся, отметки 13/42 сохранены. Добавлены prepare_runner_approval.py и scenario_approval_runtime.py, маршрут запуска --runner-approval вместе с --scenario-recovery.

## Проверяемый путь

Продуктовый CLI исполняет reviewed-сценарий из двух шагов: ввод уникального текста с finish_focus, затем ожидание значения. Живой режим разрешений — ask. При открытии штатной формы подтверждения запуск возвращает awaiting_approval с operation_id и execution=not_started. Хвост не отправлен.

Отдельная тестовая копия менеджера получает решение из файла, привязанного к request_id ожидающего ввода, и закрывает настоящую форму с Boolean. Далее работает штатный callback и проверка разрешения. Эта обвязка не подключается к тестируемому клиенту, не создаёт продуктового API подтверждения и не является ручной пользовательской приёмкой. Сам сценарий не содержит BSL/авторазрешения; продуктовый поставщик не выдаёт разрешение сам.

Проверены две ветви:

- Отказ: операция failed/permission_denied, execution=not_started. Recover и resume из новых CLI сохраняют отказ и единственную отправку. Текст «Начальное», счётчик ПриИзменении 0.
- Разрешение: та же операция выполняет ввод один раз. Recover только сверяет завершение и возвращает recovered, dispatch_count=1. Явный resume отправляет только оставшееся чтение; итог succeeded/2 отправки. Operation/request ID первого шага сохранены, счётчик формы 1.

## Найденное ограничение файлового маршрута

При ещё открытом подтверждении новый процесс provider.recover сначала вызывает create/binding. Его общий test_session/status остаётся queued за ожидающим test_input; через 30 секунд CLI возвращает blocked/context_observation_timeout с нулём новых отправок. Журнал отдельного прогона содержит test_input/awaiting_approval и test_session/queued. Сохранённый запуск не теряет awaiting_approval. Наблюдение конкретной операции по operation_id доступно.

После решения форма освобождает выполнение, свежий контекст и recovery/resume работают. Это **не исправление и не полная приёмка recovery во время ожидания на file**. Не использован старый контекст и не ослаблена проверка привязки. Следующий конкретный остаток — обеспечить свежий status/binding через файловый мост при ожидающем подтверждении, сохранив последовательность мутаций. На HTTP и embedded проверка при открытом подтверждении прошла: awaiting_approval/одна прежняя отправка.

## Доказательства и проверки

File — 17/17 проверок доступной ветви после решения; HTTP и embedded — по 18/18, включая recovery при открытом подтверждении. Документы неизменны, собственные процессы всех пяти прогонов завершены. [Сводка](evidence/scenario-approval/summary.json). Исходные ответы pending/recovered/resumed, независимые значения, cleanup, привязки и хеши сохранены рядом. File/HTTP дополнительно сверены с lifecycle: две разные операции ввода (внутренние состояния rejected и succeeded), только одна вызвана; одно завершающее test_expect. Публичный конверт отказа — failed/permission_denied. Для embedded используются публичные ответы и счётчик формы, внутренний журнал не заявляется.

Первый пробный прогон завершился connection_lost/not_started из-за ошибки **обвязки**: request_id читался как params.request_id вместо params.args.request_id. После сверки структуры исправлен только тестовый helper. Диагностическая сборка с записью исключения была подготовлена, но не запускалась; вставка удалена. Второй прогон выявил описанную блокировку файлового контекста. Оба исходных результата сохранены, подтверждённые ранее наборы не повторялись. Следующий файловый прогон выполнял непринятые ветви решения, блокировка контекста повторно не запускалась.

Тестовые Fixture/Toolkit EPF собраны с ThinClient/Server/HandlersExistence. В клиентской форме только тестовый счётчик ПриИзменении, без адаптера/наблюдателя. AST изменённых Python проверен. Продуктовые тесты без изменения реализации не повторялись. Рабочая установка не обновлялась; анонимизация отложена, Открыть() не затрагивалось.
