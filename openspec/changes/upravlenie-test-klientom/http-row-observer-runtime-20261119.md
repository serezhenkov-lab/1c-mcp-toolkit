# TASK-019 / 9.2 — влияние опроса и нативные ID накладной

19.11.2026. Тонкий клиент Windows 8.5.1.1529, отдельная файловая копия каркасной базы, штатная форма `Документ.ПриходнаяНакладная.ФормаОбъекта`. Открытие формы, изменения, проверки и назначение проб выполнены зарегистрированными инструментами `toolkit-carcass-85`. Локальный файл управления переключал режим диагностической EPF. Пробы и результаты передавались через встроенный HTTP на 127.0.0.1:17825.

## Совместная работа с TestManager

Во всех четырёх замерах работал тот же тест-клиент с загруженной фикстурой и открытой накладной. Синхронный режим использовал `HTTPСоединение.ВызватьHTTPМетод`, асинхронный — `Ждать ...ВызватьHTTPМетодАсинх`. Время измерено драйвером вокруг операции.

| Режим | `test_inspect/windows` | Длительность |
| --- | --- | ---: |
| Синхронный, первая попытка | `action_not_confirmed` | 17 833 мс |
| Синхронный, вторая попытка | Успех | 19 853 мс |
| Выключен после синхронного | Успех | 15 мс |
| Асинхронный | Успех | 19 мс |

При синхронном HTTP клиентский обработчик ожидания занимает поток, который обслуживает вызов TestManager. В то же время обработчик HTTP зависит от клиентской формы менеджера, которая ждёт синхронный ответ TestManager. Трасса фиксирует двухсекундные тайм-ауты HTTP в этом режиме. Возврат быстрого чтения окон после смены режима подтверждает зависимость от опроса. [Вызов активного окна](../../../1c/MCPToolkit/MCPToolkit/Forms/ФормаМенеджераТестирования/Ext/Form/Module.bsl#L1036), [приём HTTP-событий](../../../1c/MCPToolkit/MCPToolkit/Forms/Форма/Ext/Form/Module.bsl#L20536).

При постоянном асинхронном опросе тоже были двухсекундные тайм-ауты HTTP. На следующем прогоне добавление второй строки завершилось `expectation_timeout` на стадии `resolve`, `execution=not_started`. После выключения опроса чтение показало одну строку и добавление двух оставшихся прошло. Успех чтения окон за 19 мс не даёт гарантии совместной работы всех действий с непрерывным опросом. Кроме того, фикстура иногда отмечала `take` полученным до доставки HTTP-ответа клиенту. Для последней read-only пробы тот же идентификатор был повторно предложен после отсутствия результата. Действие по перестановке выполнено один раз.

## Нативная идентичность

- Первая диагностическая сборка раскрыла причину прежнего общего `form_observation_failed`: имя переменной цикла `Окно` совпало со свойством формы, доступным только для чтения. Ошибка — «Поле объекта недоступно для записи (Окно)». После переименования обнаружены штатная форма и её элемент `СписокНоменклатуры`.
- Свойство `Таблица.ПутьКДанным` из соседней EPF возвращает «Свойство недоступно». Узкая проба отдельно прочитала заранее известный реквизит `Форма.Объект.СписокНоменклатуры`, проверила тип `ДанныеФормыКоллекция` и вызвала `ПолучитьИдентификатор()` у элементов. `Таблица.ТекущаяСтрока` доступна и совпадает с ID выбранной строки коллекции.
- На одном черновике с UUID формы `08feef3f-1300-4066-b832-7f2e1edc337c` наблюдались ID `[0, 1, 2]`. Для двух строк с количеством 2 и ценой 3 последовательный выбор дал `current_row=0` и `current_row=1`. После штатной команды «Переместить вверх» порядок стал `[1, 0, 2]`, текущая строка сохранила ID `1`.

Для промышленных команд остаются открытыми транспорт с координацией опроса и действий, подтверждение привязки элемента к источнику без чтения `ПутьКДанным`, смена поколения источника и отзыв публичных токенов строк. 9.2 остаётся открытым.

## Сборки и проверки

Менеджер — ранее собранная испытательная EPF `Toolkit-observer-fault-probe-v3.epf` на базе `26.11.19.0931` с готовым внутренним HTTP-маршрутом. Сверены модуль TestManager, обработчик HTTP, модуль объекта, метаданные EPF и бинарный шаблон HTTP. Содержимое совпадает с текущими исходниками с учётом номера версии, вставок фикстуры и добавленной пустой строки. Ранее добавленная аварийная пауза в этом прогоне не вызывалась.

Три клиентские EPF собраны с проверками `ThinClient`, `Server`, `HandlersExistence`. Изменения сохранялись только в лабораторной реализации. Черновик закрыт через штатный диалог с ответом «Нет». Запрос подтвердил 0 накладных. Разрешения возвращены в `ask`.
