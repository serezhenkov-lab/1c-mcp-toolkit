## Подтверждённое ограничение file restart

В свежей копии запрос restart_1c_session принят во время running 60-секундного test_expect. Ответ на restart получен через **66,707 с**. К этому времени expect уже завершился с expectation_timeout. Поэтому состояние unknown не возникло; проверка повтора unknown также не могла пройти. Это не потеря результата: повтор сохранил исходную операцию с её конечным отказом.

Причина подтверждается `FileChannel.step` в `onec_mcp_toolkit_proxy/file_transport.py`: пока active не получил response.json, функция возвращает управление без get_next_command. Status(operation_id) читает общий журнал и не зависит от этого ожидания, но restart проходит через ту же последовательную доставку. Сам штатный restart после ожидания выполнился: роль TESTMANAGER сохранилась, session_allow сбросился, старые ID стали недействительными; receipt клиента не изменился, второй start и stop после attach без владения запрещены.

Изменение порядка доставки управляющих команд требует отдельной реализации и регрессии сохранности активного запроса. Оно не выполнено этим поручением на сведение/проверку. Непрерываемые платформенные вызовы также не получают обещания немедленного restart.

## Оснастка и неуспешные попытки

Профиль и начальная настройка соединения задаются доверенным startup-кодом только тестовой EPF. После restart он вновь настраивает профиль; этот факт не доказывает его штатное восстановление без оснастки. Исполнитель UI и lifecycle взяты из текущих исходников. Клиентский наблюдатель и произвольный BSL в публичный test_* не добавлены.

Сохранены ранние попытки: пустое дерево главного окна вместо формы для element_id; преждевременная готовность по старому ready.txt; file restart с 15-секундным HTTP-таймаутом; защитный отказ запуска file proxy с unresolved request; TTL-проверка с недостаточным ожиданием очереди, затем неверным требованием только succeeded вместо обоих конечных результатов succeeded/failed. Исправлены только проверки и подготовка оснастки. Каталог раннего file-стенда сохранён целиком как file-attempt1; незавершённые команды не удалялись ради повторного запуска. Повторный сценарий выполнен в новой базе/канале/журнале, прежняя операция не переисполнялась этим повтором.

Первая embedded TTL-проба столкнулась с PermissionError при одновременном чтении control.json платформой. Для тестового управления добавлена запись во временный файл и ограниченный повтор атомарной замены. Повтор только TTL прошёл, прежний отчёт сохранён. Это гонка оснастки, не отказ production-журнала.

Раннее завершение оснастки оставило перезапущенный HTTP-менеджер из-за различия слешей в пути /Execute; идентичность проверена по командной строке, процесс завершён. Очистка теперь нормализует путь и проверяет точную тестовую базу/EPF; клиент останавливается только по receipt с PID, временем создания и токеном.
