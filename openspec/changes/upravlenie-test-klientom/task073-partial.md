## Изоляция и сценарий записи

Создана отдельная файловая база `.local/task073/db` копированием `1Cv8.1CD` из `.local/task043/db` при исключительном доступе к исходному файлу. До запуска SHA-256 обоих файлов совпадал: `FF1BD54E9D9A304D1D1FE85EEE0BED8297E1694DA8ED60FC3E9023D025ED0C6C`. Рабочая установка и основная конфигурация исходного стенда не обновлялись. База-копия сохраняется для проверки результата; документы из исходной базы не удаляются.

Новый `prepare_acceptance_ui.py` переиспользует harness разрешений, создаёт одноразовую EPF и служебную fixture. В клиенте нет адаптера управления Toolkit или исполнения произвольного BSL. Изменён только тестовый обработчик записи fixture: фиксированные номер и дата позволяют проверять запись тем же параметризованным запросом `acceptance-result.sdbl`, который подготовлен в 7.1. Маркер проверяется после выборки, а не скрывает неверные значения условием WHERE.

Сценарий проходит через локальный `ПринятьКомандуТестирования` → драйвер → API тестирования → поле/кнопку **служебной формы** клиента. Нажатие кнопки вызывает её обычный серверный обработчик: создать T43_Required, ПроверитьЗаполнение, Записать. Нативная автоматически создаваемая форма документа не проверена; её номер/дата в UI не вводились. Форма fixture открывается при запуске клиента через /Execute, поэтому этот прогон не доказывает открытие нативного документа командой test_open.

- До UI и после отказа записи запрос по уникальному номеру даёт ноль строк.
- Пустое поле вызывает сообщение об обязательности, документа нет.
- После ввода уникального маркера повторное нажатие даёт ровно одну запись; проверены номер, дата, маркер и отсутствие пометки удаления.
- Номер `T736391d903`, маркер `TASK073:6391d9038f294780b7497d57e0a1d589`, ссылка `4ed5d2b6-dfda-11f1-bb22-88f4dac657c2` относятся только к базе-копии.
- Менеджер и запросы сравнивают строку соединения непосредственно. Клиент подтверждён принадлежащим процессом, портом, временем создания и точной строкой запуска; независимое чтение записи через клиентский UI не выполнено.
- Запись зафиксирована, откат не имитируется. Изоляция обеспечена копией базы; удаление записи/восстановление копии в этом прогоне не выполняется.

Harness автоматически отвечает на тестовые диалоги разрешений и создаёт fault injection. Это проверка поведения разрешений, а не доказательство автономности пользовательского сценария без тестового управления. Внешний транспорт и общий lifecycle здесь обходятся локальной точкой входа; идентификаторы request_id/operation_id в результатах — идентификаторы локального harness.

## Найденная проблема сеансового harness

Первый сеансовый прогон: 21/22; `interrupted_unknown` ожидал unknown без проверки исходного состояния операции. Фактически `НачатьПодключение` вызывает `ШагНаблюдения` сразу, и быстрый start уже завершился со статусом succeeded. `ЗавершитьМенеджер` переводит в unknown только running и правильно сохраняет завершённый результат. Это несоответствие тестового ожидания, не подтверждённый дефект Toolkit. Исходный отрицательный отчёт сохранён.

Тест исправлен: результат завершения сопоставляется со статусом непосредственно перед вызовом; дополнительно отдельная детерминированная инъекция running проверяет переход в unknown/not_confirmed. Эта инъекция явно отмечена в результатах, не выдаётся за прерывание естественного медленного старта. Производственный код не менялся. Генератор больше не устанавливает session_allow для чисто сеансового harness: режим нужен UI-тестам, а при проверке restart он маскировал бы штатный сброс разрешения.

Сборки всех одноразовых EPF проходят ThinClient/Server/HandlersExistence; проверка выполняется во временной базе-заглушке, сборка — с копией файлового стенда. Синтаксис изменённых Python-генераторов проверен. BSL LS производственных модулей повторно не запускался: их хеши совпадают с отчётом 7.2. Новый тестовый BSL проверен платформой и выполнением.

Повтор исправленного сеансового harness: 23/23, новый процесс менеджера/recover: 8/8. Сброс разрешения, новый сеанс и запрет stop без восстановленного владения подтверждены локально. Исходная база .local/task043/db после всех прогонов сохранила исходный SHA-256.
