## Реализованный безопасный preflight

`prepare_runtime.py --acceptance-preflight` подключает тестовые процедуры только в одноразовую EPF. Production-код Toolkit не меняется. Используются существующие профиль, драйвер и серверный BSL-запрос, без нового транспорта или клиентского адаптера.

Серверный вызов сверяет строку соединения с менеджером (без публикации содержимого), наличие документа/реквизита и нулевой запрос по номеру. Затем в одной транзакции:

- создаётся объект с номером/датой и пустым полем;
- ПроверитьЗаполнение возвращает false, запрос даёт 0;
- поле заполняется маркером, ПроверитьЗаполнение возвращает true;
- программная контрольная запись даёт ровно 1 строку запроса с ожидаемыми значениями;
- транзакция обязательно отменяется, также при исключении; после отмены запрос даёт 0.

Это проверка заполнения и пригодности запроса, **не UI-запись и не доказательство отказа самой Записать() при пустом поле**: код не вызывает Записать() после отрицательного ПроверитьЗаполнение. Сохранение документа между клиентскими вызовами не подтверждается. UUID ссылки в evidence относится к отменённому объекту.

Откат пригоден для одного серверного preflight, но не для нескольких независимых UI-команд. В описанной стендовой роли есть Read/Insert/Update/View; удаление не подтверждено и не использовалось. Очистка зафиксированной UI-записи остаётся условием запуска 7.3: отдельная одноразовая база с согласованным восстановлением либо проверенное удаление конкретной записи с достаточными правами. Обход прав/привилегированный режим не добавлены.
