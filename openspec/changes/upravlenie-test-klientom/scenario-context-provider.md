# TASK-021 — продуктовый поставщик контекста сценария

17.11.2026. Реализован `onec_mcp_toolkit_proxy.scenario_context.ScenarioContextProvider` и CLI `python -m onec_mcp_toolkit_proxy.scenario_context`. Поставщик не зависит от tests/harness, не вызывает execute_code и не принимает готовый словарь контекста из сценария. Существующий ScenarioRunner получает от него transport/guard и свежий контекст.

## Источники доверия

1. **Публичный test_session/status:** BSL-менеджер возвращает scenario_binding: owner (UUID экземпляра менеджера), base_id (отпечаток текущей базы по существующему механизму ключа receipt), profile_id, generation (ID живого сеанса), implementation_revision и base_mode. Главная форма добавляет фактический channel/transport из маршрута общего lifecycle и текущий approval_mode. Настройки соединения, пароль и пользователь профиля в привязку не включаются. Готовность, manager_mode, platform_version и observed_at берутся из штатного статуса. Старый runtime без binding блокируется.
2. **Локальная утверждённая политика:** JSON вне шаблона/parameters, с точными channel_id, approved_base_id, profile_id, policy_id, allow_mutation, scope_digests и expires_at. Политика — доверенная настройка оператора/приложения, не вход публичной команды. Поставщик не генерирует разрешения из произвольного сценария. Разрешение UI-команды не отменяет действующие права и подтверждения исполнителя.
3. **Поставляемый реестр реализации:** scenario-capabilities.json, привязанный к scenario-context-v1 и 8.5.1.1529. Только доказанные комбинации, неизвестная версия/среда → пустой реестр и blocked. JSON Schema команды не служит доказательством capability.

Контекст живёт максимум 60 секунд от наблюдения и не дольше политики. При каждом шаге guard проверяет, что контекст выдан этим экземпляром поставщика, срок не истёк, политика не изменилась, owner/base/profile/session/generation/implementation/platform/channel/transport/approval те же. Для адресованных целей дополнительно выполняется полное inspect с однозначностью/видимостью/доступностью. Исполнитель повторяет разрешение цели и подтверждения внутри UI-команды. Смена контекста останавливает продвижение, не перезапускает сценарий.

Провайдер делает только наблюдения при подготовке. `dispatch_count=0` preflight означает отсутствие шагов сценария/мутаций; служебные status/inspect могут создавать операции в общем lifecycle. Второй журнал и отдельная очередь не добавлены.

## Использование без тестовой обвязки

```powershell
python -m onec_mcp_toolkit_proxy.scenario_context --endpoint http://127.0.0.1:6003 --channel queue1 --policy C:/configs/scenario-policy.json --binding
python -m onec_mcp_toolkit_proxy.scenario_context --endpoint http://127.0.0.1:6003 --channel queue1 --policy C:/configs/scenario-policy.json --template C:/scenarios/reviewed.json --parameters C:/scenarios/values.json
python -m onec_mcp_toolkit_proxy.scenario_context --endpoint http://127.0.0.1:6003 --channel queue1 --policy C:/configs/scenario-policy.json --template C:/scenarios/reviewed.json --parameters C:/scenarios/values.json --run
```

Первая команда только показывает текущую привязку для сверки, файл политики ей не требуется читать. Вторая — preflight, третья явно запускает сценарий. Эти команды приведены как интерфейс, на рабочем порту не выполнялись. Сеанс должен быть отдельно настроен/подключён штатным test_session; провайдер сам не запускает и не переподключает клиент. Для встраивания доступен параметр client с уже настроенным доверенным HTTP-клиентом; endpoint/channel задаёт владелец приложения, не сценарий.

Формат локальной политики:

```json
{
  "version": 1,
  "channel_id": "queue1",
  "approved_base_id": "ИД_ИЗ_ПРОВЕРЕННОЙ_ПРИВЯЗКИ",
  "profile_id": "PROFILE",
  "policy_id": "reviewed-scope",
  "allow_mutation": false,
  "scope_digests": [],
  "expires_at": "2026-12-01T00:00:00Z"
}
```

Пустой scope ничего не разрешает. Для разрешённых оператором точных материализованных команд используется существующий command_scope(step); finish_focus входит в digest. Автоматическое вычисление digest произвольного запроса не является согласованием. Само `--binding` не разрешает автоматически доверять другой базе. При смене утверждённой политики требуется новый create/preflight.

## Реальный охват и остаток

В поставляемом реестре сейчас пять ключей: guarded text input, expect/value, inspect/windows/tree/values. Это явный доступный охват поставщика, а не разрешение всех действий установленной платформы. Остальные ключи не подменяются supported; расширение реестра требует переноса подходящих доказательств конкретной комбинации. Для клиент-серверной базы, другой версии платформы и старой EPF — blocked. База идентифицируется по текущему адресу подключения; альтернативные адреса не объединяются эвристикой. Отпечаток не является независимым UUID объекта базы.

Политика утверждается отдельно от сценария. Редактор/экран управления политиками не добавлен. Существующие механизмы анонимизации не обходятся; её развитие отложено. Восстановление связей run/step и продолжение после unknown остаются отдельным незавершённым объёмом. Старый harness-интерфейс preflight/runner совместим. Пункты не закрываются (13/42).
