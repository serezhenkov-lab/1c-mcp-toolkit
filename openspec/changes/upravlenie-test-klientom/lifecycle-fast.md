# Чтение status при квоте и ускорение компактации — 15.11.2026

Продолжение очереди 1 по поручению исправить ограничения [предыдущего прогона](lifecycle-limits.md). Общий владелец относится к TASK-002 соседнего lifecycle change; здесь проверяется его UI-адаптация TASK-016. Все незавершённые пункты и 13/42 отметки сохранены. Анонимизация отложена, наблюдатель не подключён, Открыть() не исследовался, рабочая установка не обновлена.

## Изменения

`test_session/status` с operation_id читает уже принятую операцию без новой записи, admission и очереди. Для нового чтения внешний operation_id указывает цель, request_id — корреляция текущего запроса, data.operation — актуальный конверт цели. Повтор с тем же request_id видит изменение состояния. Собственный ключ чтения не сохраняется и не занимает квоту; это не новый журнал с отдельной бесконечной квотой. status без operation_id, который запрашивает наблюдение за сеансом, остаётся обычной командой.

Старые сохранённые status остаются доступны по прежним ID и ключам. Если request_id уже занят принятой командой или старым status, сохраняется проверка fingerprint и request_conflict. Проверки канала, формы параметров, TTL и действующей политики результата сохранены. Та же семантика реализована в Python-адаптере proxy; его SQLite-владелец не изменён. Анонимизация не разрабатывалась, существующий защитный отказ embedded не ослаблен. Уточнение чтения закреплено в TI-01a и design.md; обязательный конверт и входные схемы сохранены.

В embedded чтение истёкшего результата возвращает result_expired без обязательного append в полный файл. Обслуживание получает cleanup_needed и удаляет payload при физической очистке. Ключи не освобождаются; таймаут не разрешает повтор действия.

При чтении/записи checkpoint SHA256 вычисляются сервером пакетами вместо отдельного клиент-серверного вызова для каждой строки. Пакет отправляется после 256 строк или достижения 1 048 576 символов payload; последняя добавленная строка может пересечь порог. Это ограничение накопления пачки, не новый лимит допустимой записи. Проверки каждого хеша, ревизий, ключей, count/digest и обе проверки checkpoint сохранены. Файлы по-прежнему читаются и заменяются на стороне менеджера; серверу не передаётся локальный путь, что не привязывает алгоритм к файловой базе. Клиент-серверный runtime отдельно не проверен.

Выше 60 MiB принудительная очистка перед admission/append нужна при приросте файла после предыдущей компактации. Для уже уплотнённого неизменившегося журнала проверяются истечения/cleanup_needed, но полная перезапись не повторяется перед каждым отказом. При появлении истёкших результатов, изменённой истории или установленного флага очистка сохраняется. Квоты 100 активных, 10 000 ключей, 60/64 MiB и результата не повышались.

## Стенд и проверки

Windows, тонкий клиент 8.5.1.1529, отдельные файловые базы `.local/lifecycle-fast/limits/db` и `compaction/db`, пользователь ApiProbe. Контролируемые синтетические наборы совпадают по числу и размеру с предыдущим прогоном; это не выполнение 10 000 UI-действий. HTTP localhost:17661. Сборки трёх тестовых EPF проверяют ThinClient/Server/HandlersExistence. Тестовые процедуры и инъекции отказов не входят в runtime Toolkit.

На 100 активных записей публичный диспетчер возвращает queued, а после события — awaiting_approval при том же request_id. Записей остаётся 100; 101-я команда получает operation_quota_exceeded. Чужой канал получает permission_denied, занятый ключ команды — request_conflict. На 10 000 ключей и файлах выше 60 MiB проверяются реальные REST и native MCP вызовы чтения с сохранением числа записей и ID цели. Граница результата и файловые отказы повторяются на исправленном runtime.

В Python прошли 29 проверок публичного адаптера и общего lifecycle: статус при квоте ключей/байт, обновление состояния без записи, старый cached status и конфликт, TTL, чужой канал, unknown/restart, очередь/события подтверждения. Существующая проверка политики вложенного результата сохранена; разработка анонимизации не расширялась.

BSL LS: один основной модуль, 6608 диагностик, 752 существующих Error, **0 Error на 65 изменённых строках**. Весь текст до секции EMBEDDED LIFECYCLE, включая прежние GENERATED-блоки, сохранён. Это статический анализ с ограниченным контекстом метаданных, а не приёмка. SHA256 основной формы: `579044970d357789fd24a4ddbda01000281a6e5728a4bc5ef20d006bb167b3dd`.

Регрессия владельца: **258 BSL-проверок** прошли, включая четыре границы прерывания, повреждённые commit/checkpoint, незавершённый next, простой, реальные файловые блокировки, сохранение ID/fingerprint/event_seq и удаление истёкшего payload. История 10 034 028 → 164 485 байт. Дополнительно корректно отвергнуты валидные JSON-записи с неверным хешем в середине пакета и в последнем неполном пакете.

Отдельная TTL-проверка на 8.5.1.1529: после загрузки в памяти оснастки задано истечение результата (контролируемая инъекция, без изменения часов ОС). status вернул result_expired при размере 67 104 847 байт, размер после чтения не изменился. Обычная непринудительная очистка затем уменьшила файл до 66 256 021 байта; прежний ID и 79 ключей сохранены. Это подтверждает новый путь чтения без обязательного append и последующую физическую очистку.

OpenSpec strict обоих изменений, generator --check и git diff --check прошли. Незавершённые отметки сохранены (13/42). Все собственные тестовые процессы завершены. [Архив доказательств](evidence/lifecycle-fast-runtime.zip) и [SHA256-манифест](evidence/lifecycle-fast-manifest.json) содержат исходники, отчёты, обе версии для сравнения, тестовые формы, журналы отказов и замеры; базы и EPF-бинарники не включены.

Для 10 000 небольших записей загрузка ускорилась примерно в 5,4 раза, компактация — в 5 раз. Для файлов около 60–64 MiB время самой компактации существенно не сократилось (17,6–18,9 с); небольшие различия одиночных замеров не считаются доказанным ускорением. Но отказ admission на уже уплотнённом полном журнале сократился с 16,9–21,7 с до 13–19 мс.

REST status на 10 000 ключей до очистки вернул succeeded за 92 мс, около 60–64 MiB — за 189–204 мс; native MCP после раунда также succeeded с ID цели на всех пяти наборах. Число записей сохраняется: новые status больше не создают копий крупных результатов. Для near60 исходный и новый файл после проб поэтому различаются по объёму; это следствие исправления, а не идентичная нагрузка на байт.

Во время принудительной очистки остались ReadTimeout: 3 на трёх раундах keys1000, 10 на keys10000, 8/8/9 на объёмных наборах. На keys10000 также 111 ответов HTTP 503. Квота чтения исправлена, но чтение не стало параллельным компактации. Native MCP проверяется после раунда; его успех не доказывает доступность во время блокировки. Исходный протокол сравнения и новые сырые выборки сохранены.

## Границы результата

Компактация всё ещё синхронная. Ускорение не означает отсутствие таймаутов/503 во время неё; выделенный асинхронный/пошаговый алгоритм этим изменением не внедрён. На крупных payload основная стоимость чтения/JSON/передачи данных сохраняется. Нет заявленного SLA и статистических процентилей: по три раунда для 1 000 записей и одному для остальных; HTTP timeout=2 с, а при быстрых 503 число проб выше. Это замеры разработки на общем компьютере, не выделенный нагрузочный сервер.

Совмещённый предел 10 000 ключей/64 MiB, физически полный диск, потеря питания, клиент-сервер/RDP, штатный trusted profile вне оснастки и пользовательская приёмка остаются открытыми. Рабочая установка не обновлялась.
