# Физическая очистка embedded-журнала и lifecycle — 15.11.2026

Продолжение очереди 1 по поручению пользователя. Анонимизация отложена; её требования не удаляются, реализация не расширяется. Все 13/42 отметки плана сохранены, незавершённые пункты остаются открытыми. Клиентский наблюдатель не подключён, Открыть() не исследовался, рабочая установка не обновлена.

## Что реализовано

Общий владелец embedded runtime, TASK-002 соседнего lifecycle change, получил физическую компактацию. Исходник — `1c/runtime/embedded_compaction.bsl`, включаемый существующим `generate.py` в основную форму. Формат действующего `operations.jsonl` совместим с прежними записями: при компактации остаётся одна последняя запись на ключ, её локальная ревизия начинается с 1. ID, fingerprint, канал, ключ запроса, состояние и event_seq сохраняются. Старые 344 GENERATED-блока не изменены.

Очистка выполняется при старте владельца, раз в 60 секунд при наличии истёкших результатов/неочищенной истории, после прироста истории более 8 MiB и перед записью/admission при приближении к прежнему порогу 60 MiB. Отсутствие запросов status не задерживает очистку бессрочно. Все операции сериализованы клиентским runtime под прежним writer lock.

Истёкший результат становится result_expired, payload удаляется из нового файла. Ключ остаётся занят, повтор возвращает прежний ID, изменённые параметры дают конфликт. queued/running/awaiting_approval и unknown не удаляются ради освобождения места; unknown сохраняет данные до сверки. Неистёкшие результаты остаются доступными.

Сохранённые status объявляют общему владельцу `context.result_dependencies`. Их payload живёт не дольше результата-источника; после его истечения зависимый status также может стать result_expired до собственного TTL. Это удаляет физические копии истёкших данных, включая цепочки статусов. Для старого формата UI-адаптер восстанавливает зависимости перед checkpoint через внутренний callback/подготовку первого публичного вызова. Общий владелец не знает test_* и не содержит UI-журнал. Публичные параметры и схемы команд сохранены.

## Протокол замены файла

1. Под отдельным неизменным `owner.lock` записывается `operations.jsonl.next` с актуальными записями и их SHA256; файл закрывается и перечитывается с проверкой count/digest, ревизий и идентичности ключей.
2. Закрывается небольшой `operations.jsonl.commit` с версией, числом записей и digest. С этого момента возврат к старому журналу запрещён.
3. Старый `operations.jsonl` удаляется, next перемещается на его место, commit удаляется. Постоянной резервной копии старых payload нет.
4. При старте без commit временный next не считается принятым и удаляется. С commit проверяется next, а после уже выполненного переименования — действующий файл. Повреждённый marker/checkpoint закрывает исполнение; исправление или откат к старым данным автоматически не предпринимается.

Ошибка записи переводит владельца в неработоспособное состояние, не публикует успех очистки и не разрешает повтор команд. Временный пик управляемых файлов — до двух журналов по 64 MiB и малого маркера; свободное место должно позволять подготовить новый снимок. Ограничения числа ключей/активных операций/результата сохранены. Это удаление payload из файлов владельца, не обещание secure erase носителя или удаления внешних резервных копий. Сохранность при потере питания ОС не заявляется. Старые бинарники не понимают commit: откат допускается после завершённого восстановления, с сохранением журнала.

## Проверки на 8.5.1.1529

Windows, тонкий клиент, отдельные файловые базы `.local/lifecycle-compaction/db` и `public/db`, пользователь ApiProbe. Публичный стенд: HTTP 17659, TESTCLIENT 16543. Политика анонимизации в runtime-прогоне выключена; её разработка отложена. Тестовые источники содержат контролируемые маркеры, не рабочие данные.

- **258 BSL-проверок**: обычная компактация, восстановление и неизменность ID/fingerprint/event_seq, прежние ключи и конфликты, удаление истёкшего payload и старого cached status, сохранение актуального/unknown результата.
- Четыре точки прерывания: после подготовки next, после commit, после удаления старого файла и после переименования. В тестовой копии вставлено исключение точно на границе файловых операций, затем процесс завершается и запускается заново; это управляемая инъекция отказа, не проверка отключения питания. В итоговом Toolkit тестовых инъекций нет.
- Повреждённые commit и подтверждённый next: operation_store_unavailable, исполнение закрыто. Незавершённый неподтверждённый next игнорируется; старый журнал восстанавливается без переисполнения.
- Реальный отказ записи next из-за другого пишущего FileStream: отказ с сохранением ключей, успешное восстановление после снятия блокировки.
- 100 активных операций: 101-я отклонена по квоте; компактация не удалила активные записи.
- История **10 034 028 → 164 485 байт**, актуальный результат сохранён. Проверка байтов действующих файлов подтверждает отсутствие `MARKER_expired`, включая его копию в status; маркеры актуального и unknown результата сохранены.
- Периодическая очистка через 60 секунд проверена в простое, без status/новых команд; после неё выполнена проверка и повторный запуск.
- Публичные `test_*`: запуск и наблюдение, повтор/конфликт, реальные формы подтверждения с ответами оснастки, компактация в awaiting_approval и running, TTL, чужой канал; публичный restart сохранил endpoint/TESTMANAGER, сбросил разрешения, дал unknown без replay.
- **7 native MCP групп и 70 REST случаев** повторно сопоставлены с общими схемами. Python-регрессия адаптера — **7/7**. Ошибка имени переменной URL в доработанной оснастке исправлена до успешного прогона; это не ошибка Toolkit.
- Итоговая сборка с ThinClient/Server/HandlersExistence. BSL LS: один модуль, 6592 диагностики, 752 Error вне изменённых строк; **0 Error на 206 изменённых строках**, 344 GENERATED-блока сохранены. Синхронизация генератора и OpenSpec strict обоих изменений проверены отдельно.

## Оставшиеся границы

Это проверка embedded-владельца; SQLite-владелец proxy не изменён. Полная матрица квот/отказов, задержки компактации при предельном объёме и числе ключей, клиент-серверный/RDP режим и пользовательская приёмка остаются открытыми. Компактация синхронная и может задерживать обработку HTTP в клиентском потоке; непрерываемость платформенных вызовов не устранена. Штатный trusted profile вне оснастки и остальные незавершённые пункты очереди 1 не объявляются выполненными.
