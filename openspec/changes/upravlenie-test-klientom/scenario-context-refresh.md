# TASK-021 — безопасное обновление контекста длинной цепочки

17.11.2026. Реализовано обновление контекста между шагами продуктового runner. Закрыт конкретный пробел, обнаруженный в [пакете полей](scenario-fields.md): истечение 60-секундного контекста после успешного ввода больше не требует повторного запуска цепочки. Незавершённые пункты TASK-021 остаются открытыми, отметки 13/42.

## Контракт и реализация

`ScenarioRunner` получил необязательный доверенный callback `refresh_context(previous)`. Продуктовый `ScenarioContextProvider` подключает его в run/recover. Поставщик принимает только ранее выданный им контекст, заново читает локальную политику и живой test_session/status; не продлевает истёкшую политику и не создаёт новый grant.

Обновление вызывается только перед следующим ещё не отправленным шагом, если истёк expires_at. Все поля, кроме observed_at/expires_at, должны остаться равными: владелец, база, профиль, канал/маршрут, сессия/поколение, платформа/реализация, политика/revision/scope/approval, capabilities/revision и флаги готовности/разрешения. Новые observed_at и expires_at строго позже прежних. Полный preflight заново проверяет весь шаблон; разрешённый план должен совпадать с сохранённым.

Новый контекст и аудит context_refreshes сохраняются в durable state до добавления/отправки следующего шага. Аудит содержит before_step, исходный/новый digest, сроки и plan_digest; первоначальный preflight, run_id, request_id/operation_id и результаты завершённых шагов сохраняются. Отказ хранилища не допускает отправку следующей команды. После сохранения обновления потеря процесса оставляет корректный checkpoint: recovery наблюдает прежние операции и не повторяет успешную мутацию.

После обновления обычный guard снова проверяет актуальные привязку/политику и цель. Срок проверяется до и после guard. Обновление не используется как повтор отказавшего guard; если контекст истёк во время guard, шаг блокируется. Unknown, awaiting_approval и stop-ошибки не запускают обновление/повтор. continue_observation по-прежнему пропускает мутации; обновляется контекст только перед допустимым наблюдением. Самостоятельные старые blocked/unknown-запуски не перезапускаются автоматически.

## Локальная проверка

15 новых тестов: успешное и многократное обновление; неизменность полномочий; запрещённое продление без нового наблюдения; истёкшая политика/ошибка поставщика; отказ/истечение во время guard; unknown/awaiting_approval; ошибка сохранения; потеря процесса после commit обновления; continue_observation и пропуск мутации; новая мутация с новым ID после обновления; запрет поддельного контекста.

23 затронутых прежних теста runner/recovery (12+11) повторены обоснованно: изменены общий цикл исполнения и checkpoint. Все прошли. Старые runtime-проверки полей, страниц, импорта и потери процесса не повторялись. Python AST, OpenSpec strict и diff-check выполнены; BSL/Toolkit EPF не менялись, сборка не запускалась.

## Runtime 8.5.1.1529

Отдельные файловые базы, Windows thin client; существующая Toolkit-route.epf. Новый сценарий содержит один test_input/text с явным finish_focus и одно test_expect/value. Только тестовый child задерживает возврат уже полученного успешного нативного результата до expires_at+1 секунды. Продуктовые часы, срок контекста, guard, обновление, preflight и транспорт не подменяются. Задержка около 53 секунд доводит реальный 60-секундный контекст до истечения; в production этого ожидания нет.

## Рубеж и оставшиеся ограничения

Причина остановки длинной активной цепочки устранена и проверена на всех трёх файловых маршрутах. Runtime отрицательные случаи смены полномочий/ошибки диска не имитировались на платформе — они проверены локально. Полная бизнес-приёмка, editing/property_read_failed, unknown без operation_id, табличные зависимости и другие среды остаются открытыми. Наблюдатель не подключён, анонимизация отложена, Открыть() ячейки не затронуто, рабочая установка не обновлялась. [Единый остаток](task021-remainder.md).
