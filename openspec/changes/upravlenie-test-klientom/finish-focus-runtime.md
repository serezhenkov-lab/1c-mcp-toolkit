# 11.2 — finish_focus: исполнение и сквозная проверка

17.11.2026. Реализована проверка выбранной цели **до ввода** и фактического текущего элемента **после finish_edit** в менеджере тестирования. Проверены файловые стенды 8.5.1.1529: HTTP proxy и встроенный HTTP. Новая запись uilog не велась.

## Итог реализации

- params.finish_focus — совместимое необязательное условие только test_input/text: selector name/type=field, необязательный title, same_form=true. Python-контракт, встроенная схема и BSL-валидация согласованы. Вызовы без условия сохраняют поведение.
- До activate в той же живой форме разрешается единственная цель; проверяется доступность и равенство её нативной ссылки цели, выбранной существующим алгоритмом завершения. При mismatch ввод/активизация не выполняются. Ни заголовок формы, ни равенство текстов не служат идентификатором.
- После finish_edit текущий элемент сравнивается с сохранённой целью. Ошибка не вызывает повтор ввода; completed_steps, execution и флаги before_confirmed/after_confirmed сохраняют сведения об уже выполненном.
- Scenario preflight материализует условие в аргументы команды, учитывает его в scope/digest и требует отдельную capability test_input:text:finish_focus:none с доказательством конкретной реализации/среды. Обычная scalar capability или произвольный флаг поддержки не разрешают запуск.

## Подтверждение на платформе

[HTTP-протокол](evidence/finish-focus-runtime/http/finish-focus-summary.json): **8/8**.

1. Создана нативная форма T43_Required.
2. Ожидаемая «Дата» вместо выбранного «Номер»: failed/finish_focus_mismatch, execution=not_started, completed_steps=[], значение пустое.
3. Несуществующее поле: отказ до ввода, completed_steps=[], значение пустое.
4. Правильное условие: succeeded, before_confirmed=true, after_confirmed=true, значение прочитано обратно.
5. Искусственная активизация исходного поля после finish_edit: failed/finish_focus_mismatch, execution=invoked; три выполненных подшага, before=true/after=false, введённое значение остаётся. Внесение сбоя только в копии тестовой EPF, не в продуктовых исходниках. Повторной доставки/ввода нет.
6. Явно отрецензированная локальная производная записи revision=2 с точным form_name и свежим контекстом: preflight ready.
7. Эта производная выполнена через ScenarioRunner → публичный test_input → общий lifecycle: succeeded, dispatch_count=1, конечный фокус подтверждён.
8. Девять исходных документов не изменены.

[Итоговая EPF без внесения сбоя, embedded](evidence/finish-focus-runtime/embedded/finish-focus-summary.json): **3/3** — все встроенные схемы равны INPUT_SCHEMAS, guarded input успешен, документы неизменны. На первом embedded-запуске проверка остановилась до ввода: выдача вложенного объекта схемы через execute_code обрезалась по max_depth. Обвязка возвращает JSON-строку; повторена только незавершённая проверка. Исходный отказ и cleanup сохранены отдельно, продуктовая схема из-за этого не менялась.

Оба успешных стенда и неуспешный диагностический запуск завершили собственные процессы (cleanup.all_exited=true). Рабочая установка не затронута.

## Рубеж и остаток

Цепочка **сохранённый uilog → draft с условием → локальное ревью → полный preflight → один защищённый ввод → проверка фокуса** пройдена. Отсутствие guard больше не блокирует этот пример. Исторические draft/recording_review сохранены; готовность конкретной локальной производной не превращает произвольную запись в reviewed.

Другие формы/раскладки, варианты записи, клиент-серверный режим и полная приёмка TASK-021 остаются открытыми. Файловый мост в этом этапе не проверялся. Пункты не закрыты, наблюдатель не подключён, анонимизация отложена. Техническую реализацию finish_focus для этого примера повторно не выделять в следующий этап без новых оснований.
