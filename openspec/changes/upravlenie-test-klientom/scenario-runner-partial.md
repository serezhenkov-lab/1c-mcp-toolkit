## Реализация

- `scenario_contract.py`: preflight всего шаблона до отправки команд. Версия/JSON/бюджеты, уникальные шаги, обязательные/лишние параметры и точные типы, ссылки параметров, запрет runtime ID, материализация и valid_request, политики ошибок, доверенный контекст/срок/база/сеанс, разрешённая область и capabilities. Готовый план связан digest с шаблоном, параметрами и контекстом. Схема поставляется рядом с модулем; тест проверяет её равенство закреплённой schema 11.1.
- `scenario_runner.py`: один последовательный запуск, отдельные run_id/step_execution_id/request_id; операция и её результат принадлежат **общему lifecycle**. Никакого второго журнала исполнения или нового публичного API. При queued/running опрашивается test_session/status; команда не публикуется заново. Ошибка guard, отказ подтверждения, unknown и потеря контекста останавливают продвижение.
- Перед каждым шагом обязательный доверенный guard проверяет неизменность контекста и актуальные условия. На стенде guard проверяет жизнь собственных процессов, ready/ID текущего сеанса и существование точной цели; действующий публичный исполнитель повторно разрешает уникальную цель и проверяет доступность непосредственно перед действием. Наблюдатель не подключён.
- `continue_observation` разрешён только для наблюдения; ошибка сохраняется, последующие мутации пропускаются, итог partial. Отказ подтверждения/unknown не могут быть скрыты этой политикой.
- Явный retry_delivery принимает только сохранённый успешный шаг с прежним plan_digest; сначала читает его операцию общего lifecycle, затем передаёт те же аргументы/request_id. Потерянный/истёкший результат или unknown блокируют повтор. При unknown хвоста нельзя повторить и успешный префикс без сверки.

## Контекст доступной интеграции

Контекст **не вводится из записи uilog**. Его формирует доверенный владелец harness: owner/channel/base/approved_base/profile/session/generation, implementation_revision/platform/mode, policy_id, capability_revision, observed_at/expires_at, manager_mode/session_ready, allow_mutation/approval_available.

`scope_digests` — список разрешённых точных команд `SHA256({tool, arguments})` после подстановки параметров и до добавления runtime ID. Изменение параметра требует нового разрешённого digest. Автоматическое построение scope_digests из произвольного пользовательского шаблона **не является авторизацией**; стенд формирует их только для известного сценария на собственной тестовой форме.

`capabilities` индексируется `tool:action-or-property:variant:source_kind`. Для доступных нетабличных команд source_kind=none, variant=scalar либо button/list. Каждая запись содержит supported/unsupported/unknown, platform/mode/implementation_revision и evidence. Пустой/неподтверждённый реестр блокирует запуск. Ветви table, selection_table, group и неизвестный тип цели блокируются независимо от заявления capability: их полная интеграция пока не реализована. Само наличие публичной схемы не доказывает поддержку.

Переносимый шаблон не менялся. Runtime-адаптер полномочий/capabilities для произвольной установленной базы **не подключён**; этот этап проверяет явный контекст известного стенда. Хранилище связей сценария после завершения процесса runner также не внедрено: живые run handles и связи шага хранятся в памяти runner. После потери handles `retry_delivery` возвращает run_state_unavailable; неизвестный run_id не восстанавливается догадкой и не исполняется заново. Это ограничение, а не доказательство восстановления сценария после рестарта.

## Проверка на 8.5.1.1529

Обвязка `tests/test_client/run_scenario_runner.py` создаёт отдельную копию `.local/profile-runtime/db`, читает существующие тестовые Toolkit-production.epf и Fixture.epf, запускает только собственные процессы. Три шага: ввод уникального маркера → нажатие кнопки записи документа → проверка введённого значения. Результат записи отдельно проверяется существующим execute_query.

Сохранены два прогона:

1. `.local/scenario-runner-20261116T110931/http`: **7 успешных проверок**, затем отдельное несовпадение ожидания обвязки. Поздний неверный шаг не вызвал ни одного шага сценария; первый запуск выполнил три шага и создал один документ; повтор доставки write вернул тот же operation_id без второго документа; новые параметры создали новый run/ID шагов и один другой документ.
2. `.local/scenario-runner-20261116T111148/http`, `--remaining`: **4/4 оставшихся проверки**. Ошибка чтения отсутствующего элемента оставила успешные шаги и итог partial. Потеря ответа после записи дала unknown, следующий шаг не отправлен; явный повтор отказан; запрос показал один документ.

Первый случай ожидания ложного значения **не засчитан как подтверждённый failed**: timeout runner наступил до получения терминального ответа, сохранён unknown/runner_wait_expired. Уже завершённые шаги не повторены. Для ветки подтверждённого отказа во втором прогоне использовано чтение отсутствующего элемента с немедленным отказом. Семь ранее прошедших проверок во втором прогоне пропущены.

Итого **11 новых подтверждённых проверок пакета** по двум прогонам, а не «11/11 одного чистого прогона». Первая проверка preflight и отказ retry выполняются локально в обвязке; UI-действия, общий lifecycle, ID операций и итоговые запросы — реальные на стенде. Fault unknown введён на границе harness: адаптер получает succeeded общего lifecycle после UI-записи и выбрасывает ошибку доставки runner. Это не падение 1С и не переход операции lifecycle в unknown; неопределённым остаётся знание runner, которое он не заменяет автоматическим повтором.

Все собственные процессы обоих прогонов завершены (`cleanup.all_exited=true`). [Сводка и артефакты](evidence/scenario-runner/summary.json). Новая сборка EPF не требовалась. Прежние наборы lifecycle, 24 примера компаратора и тесты импортёра не запускались повторно.
