# Очередь 2 — проверка окон и HWND на 8.5.1.1529

16.11.2026. Отдельные файловые базы, Windows, thin client, интерфейсы Такси и Версия 8.5. Обычная EPF Toolkit из предыдущего этапа; менялись только fixture, runners и доказательства. Наблюдатель/адаптер в клиент не подключён, анонимизация отложена, рабочая установка не обновлена. 13/42 и все незавершённые отметки сохранены.

## Уточнение исходной гипотезы

«Два главных окна» и «два HWND-кандидата компоненты» — разные условия. По [официальному описанию основного окна](https://v8.1c.ru/platforma/osnovnoe-okno/) основное окно сеанса одно. Коллекция ПолучитьОкна() и свойства Основное в runtime обеих проверенных разновидностей интерфейса также показывали ровно одно основное окно. Множественное число в общем описании коллекции платформенного индекса не доказывает возможность создать несколько основных окон одного сеанса.

Компонента ScreenCapture использует более широкий критерий: все видимые top-level HWND нужного PID без GW_OWNER. Она отказывает при count != 1, не определяя семантический тип окна 1С. Значит, проверку неоднозначности можно провести на настоящем оповещении платформы, не создавая второе логическое главное окно и не подменяя PID/владельца. Нормативное требование не выбирать неоднозначную цель сохранено; исправлена неточная гипотеза нашего предыдущего списка проверок.

## Что проверено

### Два реальных кандидата, один логический main

Fixture вызывает штатный ПоказатьОповещениеПользователя со статусом Важное. Одновременно присутствуют основное окно и HWND оповещения: оба видимы, принадлежат одному реальному PID, оба без владельца. В обоих интерфейсах публичный get_screenshot(target=test_client) возвращает screenshot_target_unavailable без PNG. Внутреннюю строку ambiguous_window публичный адаптер не раскрывает; связь с guard count != 1 установлена исходниками и наблюдаемым набором кандидатов, не отдельной трассировкой внутреннего return.

После автоматического закрытия оповещения видимым кандидатом остаётся прежнее основное окно. Повторное оповещение получает другой HWND в том же продолжающем жить процессе. SetWinEventHook фиксирует CREATE/SHOW/HIDE/DESTROY обоих вспомогательных HWND. Это внешний read-only OS listener теста, не компонент/наблюдатель в тест-клиенте. Никаких SetParent, GW_OWNER-перезаписей или подстановки PID не было.

| Интерфейс | PID | Основной HWND | Оповещение 1 → 2 |
| --- | --- | --- | --- |
| Такси | 9952 | 1512444 | 9965920 → 8323236 |
| Версия 8.5 | 46152 | 1577980 | 6620188 → 6685724 |

Оба HWND оповещений созданы и уничтожены по WinEvent, основные HWND остались теми же. После каждой смены вспомогательного HWND второй кандидат вновь приводит к отказу снимка. Повторное использование того же числового HWND не воспроизведено.

### Попытки пересоздания основного HWND

Локальная справка установленной 8.5.1.1529 содержит КлиентскоеПриложение.УстановитьРежимОсновногоОкна и ограничивает вызов обработчиком ПередНачаломРаботыСистемы. Это подтверждено runtime: попытка в работающей fixture вернула точную ошибку ограничения вызова, режим/основной HWND остались прежними. Прочие режимы тем же запрещённым способом не перебирались. Ранний неуспешный exploratory-прогон сохранён, не засчитан как успешная смена режима.

Штатный ОбновитьИнтерфейс() выполнен отдельно в обоих интерфейсах. ПолучитьОкна() до/после показывает один main, WinAPI — прежний основной HWND; CREATE/DESTROY для него не зарегистрированы. Работоспособность WinEvent listener подтверждена реальными событиями оповещений, а не только отсутствием событий в этом опыте.

| Интерфейс | PID | HWND до/после обновления |
| --- | --- | --- |
| Такси | 42560 | 5310526 → 5310526 |
| Версия 8.5 | 44992 | 24120286 → 24120286 |

**Пересоздание основного HWND при живом процессе не воспроизведено.** Обновление интерфейса не оказалось способом его вызвать. Это не утверждение, что HWND никогда не может измениться, и не приёмка гонки повторного использования дескриптора. Прежняя проверка смерти процесса внутри захвата остаётся отдельным доказательством.

## Проверки и артефакты

- Обновление интерфейса: 4/4 assertions на каждой разновидности интерфейса; уведомления: 6/6 на каждой. Сводная проверка review.json дополнительно сопоставляет CREATE/DESTROY, два разных HWND, ровно один logical main и отсутствие PNG. Подготовительные подключения не считаются новым критерием маршрутов.
- Fixture собрана с modules,handlers. Production BSL/Python/C++/DLL не менялись; повторные BSL LS, Python unit и native unit не запускались. AST runners, generator --check, OpenSpec strict, diff check проверены.
- Все собственные процессы завершены, проверено cleanup/CIM. Для UI-диагностики был попробован CUA: инициализация завершилась ошибкой записи kernel assets; действий в UI через него не выполнялось. Runtime-проверки завершены через штатный менеджер тестирования и внешние WinAPI-наблюдения.
- Runners: tests/test_client/run_hwnd_modes.py, run_hwnd_notice.py; флаг --85 выбирает отдельную базу с интерфейсом Версия 8.5. В .local/hwnd лежат fixture/Toolkit EPF, базы refresh/version85/notice/notice85. Для повторения нужны отдельные копии баз с ApiProbe и указанным вариантом интерфейса. Исходники fixture и извлечённая справка включены в архив; результаты защищены от перезаписи.
