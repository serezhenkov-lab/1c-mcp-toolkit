# Очередь 1: штатная настройка и восстановление профиля — 16.11.2026

Добавлен блок «Тест-клиент текущей базы» в обычную форму EPF. Настройка больше не требует вставки инициализатора профиля в исходники обработки. Пункты 2.3, 6.1–6.3 и остальные незавершённые пункты не закрыты; сохранены 13/42 отметки. Наблюдатель не подключён, анонимизация отложена, рабочая установка не обновлена.

## Использование

1. Открыть обычную EPF в тонком клиенте Windows 8.5 с `/TESTMANAGER` в нужной тестовой базе.
2. Включить «Использовать профиль», указать ID (латинские буквы, цифры, `_`, `-`), имя пользователя этой базы и свободный локальный порт 1024–65535. Нажать «Сохранить профиль».
3. Если нужен пароль, ввести его и сохранить. Пароль хранится только в памяти драйвера текущего сеанса, поле формы после сохранения очищается. После перезапуска пароль нужно ввести заново перед `start`; `attach` не требует повторного пароля запуска.
4. Разрешить требуемые операции обычным механизмом подтверждения и явно вызвать `test_session/start` либо `attach`. Сохранение/восстановление профиля само не запускает и не подключает клиент.

Для сохранения требуется право платформы `СохранениеДанныхПользователя`. Toolkit не включает привилегированный режим и не выдаёт себе это право. При его отсутствии предусмотрено отдельное сообщение. Настройка транспорта и его автостарт остаются независимыми от профиля тест-клиента.

## Реализация

- `1c/runtime/local_test_profile.bsl` включается штатным генератором в основную форму. Сервер загружает/сохраняет настройки текущего пользователя в `ХранилищеОбщихНастроек`, ключи `MCPToolkit / TestClientProfileV1`.
- Сохраняется белый список: `version`, `id`, `user`, `port`, `enabled`, `password_required`. Не сохраняются пароль, строка соединения, путь программы, аргументы запуска и разрешения. Запись предварительно проверяется; некорректная запись не активируется при загрузке.
- Исполняемый файл берётся из каталога текущей платформы, подключение — из текущей базы. Это один локальный профиль текущей базы, без произвольного переключения базы через HTTP.
- Receipt процесса находится в пользовательском рабочем каталоге `MCPToolkit/test-client/`. Имя строится из SHA-256 подключения и пользователя менеджера в безопасной для имени файла форме Base64. Оно не зависит от редактируемых ID/порта профиля: смена ID не прячет известный процесс.
- Смена идентичности/отключение профиля запрещены при активной операции, живом или неопределённом процессе и занятом старом порте. Пароль того же профиля можно обновить после окончания операций. Неприменённый флажок в форме не меняет разрешённость публичного исполнения: действует сохранённое состояние.
- При открытии обычной формы восстанавливается профиль и receipt через существующий драйвер. Автоматического start/attach нет, прежнее владение и `session_allow` не восстанавливаются. Служебное открытие «управление сервером» не создаёт драйвер.

## Проверки и границы доказательства

Стенд: файловая копия `.local/profile-runtime/db`, Windows, тонкий клиент **8.5.1.1529**, пользователь `ApiProbe`, embedded HTTP **17668**, TESTCLIENT **16548**. EPF собиралась непосредственно из production-исходников, без внедрённых обработчиков старта/управляющего файла и без вызова `Настроить` из оснастки. HTTP запускался штатным `/C startup;mode=embedded;...`; после restart использовался обычный механизм автозапуска Toolkit.

Проверяющий HTTP-скрипт использует существующий `execute_code` для заполнения реквизитов и вызова штатной команды формы, настройки тестовых разрешений и чтения результата. Это внешнее управление тестом, а не настройка драйвера через прежний startup fixture. Отдельно выполнено настоящее нажатие кнопки «Сохранить профиль» после заполнения; положительное состояние сохранено в `ui-saved.json`. Полная ручная приёмка всех полей не заявляется.

Обнаруженные условия, не скрытые успешным итогом:

- Первые попытки ввода через UI Automation не подтвердили корректную передачу значений форме. Пользователь также получил отказ проверки полей. Положительный финальный сценарий использует известные значения и отдельное нажатие кнопки; первоначальный текст отказа не объявляется доказательством единственной причины.
- Диагностическая копия выявила самостоятельный отказ `ХранилищеОбщихНастроек.Сохранить`: у минимальной роли ApiProbeAdmin отсутствовал `SaveUserData`. В конфигурацию только этой копии базы добавлено одно право; ошибка и изменение роли сохранены. Диагностический вывод исключения не вошёл в production EPF.
- При включённой точной анонимизации сохраняется прежний `operation_result_policy_not_ready`. Во внешнем сценарии она отключена явно в каждом сеансе; её реализация/приёмка не выполнены.
- Первый status во время фоновой инициализации журнала может вернуть `operation_store_unavailable`; после завершения инициализации статус доступен. Профиль и lifecycle не подменялись тестовым каталогом.

Сборка EPF с `ThinClient / Server / HandlersExistence` успешна. BSL LS проверил оба изменённых модуля: 7231 диагностик, 752 Error; в новых процедурах профиля и изменённых участках драйвера Error нет. Общая чистота большого существующего модуля не заявляется. XML-валидатор: те же **39** ошибок до/после, новых нет; это ограничения/существующие замечания исходной формы. Регрессия Python: **54** теста публичного lifecycle/журнала/file transport прошли.

Полная клиент-серверная/RDP-матрица, остальные отказы хранилища, аварийные сценарии всех транспортов и общая приёмка остаются открытыми. Этот прогон подтверждает профиль и штатный restart на embedded HTTP файловой 8.5, а не всю очередь 1.
