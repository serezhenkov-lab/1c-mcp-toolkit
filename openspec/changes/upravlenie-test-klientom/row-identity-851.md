# Продолжение 4.1: идентичность строк на 8.5.1.1529

13.11.2026, отдельный стенд controlled85, тонкий клиент Windows, ApiProbe. Пользователь разрешил исследование и необходимые части 5.1–5.2; рабочая установка не обновлялась, 1.4 не затрагивался.

## Проверенные результаты

1. ПерейтиКСтроке включает текущую строку в поиск в обоих направлениях. Повторный поиск последней строки возвращает true. Отсутствующее значение в данном прогоне даёт исключение, а не false. Такой поиск нельзя использовать как перечисление разных строк по числу true.
2. Shift-переход между двумя одинаковыми строками увеличивает количество выделенных с 1 до 2. Следующий переход на границе даёт исключение «В элементе управления отсутствует указанное значение». Обратный Shift-переход уменьшает выделение до 1. Тексты для определения этих переходов не сравнивались.
3. Выделение **не является устойчивым маркером идентичности**. После обычного перехода с первой одинаковой строки на вторую количество выделенных остаётся 1; переключение выделения текущей строки даёт 0. Это тот же результат, что без смены строки. Физическая смена отдельно доказана записью метки во вторую строку без изменения первой. Поэтому данный способ не включён в Toolkit.
4. В коде самого тестируемого клиента ПолучитьОкна().Содержимое предоставляет реальные формы. Связка UUID формы + нативный идентификатор строки различает одинаковые строки: повторное чтение первой даёт 0, переход ко второй — 1. ТекущаяСтрока совпадает с идентификатором строки данных формы.
5. Перестановка двух одинаковых строк меняет порядок идентификаторов `[0,1]` на `[1,0]`, сохраняя сами ID. Удаление первой строки этой коллекции и добавление даёт `[0,2]`; очистка и новое добавление — `[3]`. Установка порядка таблицы также сохранила текущий ID; при одинаковых текстах это не отдельное доказательство фактического изменения визуального порядка.

Это подтверждённая основа для адаптера ДанныеФормыКоллекция, а не доказательство любых динамических списков или всех способов перезагрузки источника. Нативный доступ проверен исследовательским кодом внутри фикстуры. Обычный внешний тестовый API этих ключей не возвращает.

## Следующий шаг и статус

Подготовлено [предложение клиентского адаптера](client-row-adapter-proposal.md): отдельный ограниченный режим в тест-клиенте, повторное использование существующего транспорта, связь с сеансом/UUID формы и нативными ID, без произвольного BSL и без подмены штатных действий формы. Решение пользователя 13.11.2026 — сохранить прототип и описание архитектуры без внедрения. Исходники проб, результаты и инструкции воспроизведения сохранены; подключение адаптера к Toolkit отложено до отдельного поручения.

Успешный выбор через настоящую табличную форму в Toolkit **не подтверждён**. 4.1/5.1/5.2 остаются открытыми; новое доказательство устраняет прежнюю неопределённость о доступности независимых ID для коллекции формы, но не заменяет интеграцию и приёмку. 1.4 открыт; Открыть() не исследовался.
