# 1c-mcp-toolkit / TASK-011 — Контракт команд и проверка предпосылок

## Цель и ожидаемый результат

Зафиксировать проверяемый контракт и доказать применимость API до зависимой реализации.

## Требования и сценарии

[TS-01, TS-02](../specs/test-client-session/spec.md), [UI-01](../specs/test-client-ui/spec.md), [TI-01, TI-03](../specs/test-client-integration/spec.md); сценарии «Запуск без режима менеджера», «Неоднозначный элемент», «Конфликт ключа».

## Границы работы

Контракт, паспорт среды, небольшой прототип и обязательный анализ двух доноров перед реализацией. Answer42 — кандидат BSL-адаптации, Testpilot — образец проверяемого поведения. Не разрабатывать общий lifecycle и не переносить чужие транспорт/инфраструктуру.

## Затрагиваемые объекты и технические указания

Схемы tools.py, основная форма EPF и изолированный прототип API; выбор реальных методов подтвердить платформенной справкой и запуском. См. [решение](../design.md) и [исследование](../research.md).

## Зависимости

Нет внутри изменения. Используется контракт operation-lifecycle из соседнего change; его реализация сюда не переносится.

## Критерии приёмки и проверка

Паспорт содержит версии, тип клиента, базу и права. Прототип подтверждает подключение API. Схемы описывают обязательность полей, ошибки, лимиты и различие execution/verification. Оба донора привязаны к commit/лицензии; минимальный состав BSL-адаптации замкнут по зависимостям и не содержит чужого протокола.

## План выполнения

Прогресс хранится только в [tasks.md](../tasks.md#task-11).

- 1.1 Зафиксировать паспорт тестового стенда и проверить API /TESTMANAGER–/TESTCLIENT на выбранной платформе; приложить параметры среды и протокол подключения.
- 1.2 Получить и проанализировать фиксированные исходники Testpilot и Answer42, выделить минимальное замыкание адаптируемых BSL-зависимостей; проверить лицензии и отсутствие чужого протокола/WebSocket/RAG/создания базы менеджера в составе переноса.
- 1.3 Закрепить схемы семи групп команд, селекторы, лимиты, классификацию разрешений и адаптацию общего lifecycle; проверить примеры валидных, неоднозначных и конфликтующих запросов.

- 1.4 Подтвердить матрицу capabilities по конкретным сборкам менеджера/клиента и методам, включая точный API открытия значения ячейки; отделить документированное от runtime-проверенного.

## Результат и доказательства

Пункты 1.1/1.2 выполнены 12.11.2026. Оба донора зафиксированы по SHA и лицензиям. Для 28 входов Answer42 выделено 138 функций, две переменные и два инфраструктурных адаптера; замыкание прошло платформенную проверку и сборку отдельной EPF. Полный перечень и граф — [bsl-dependencies.md](../bsl-dependencies.md).

На изолированной файловой базе, под отдельным ApiProbe, платформа 8.5.1.1529 выполнила 32/32 проверки. Отрицательный запуск без /TESTMANAGER подтвердил недоступность типа. Сравнение на 8.3.27.2342: 28/32, совместимость 8.3 полностью не подтверждена. Паспорт, исходники прототипа, ограничения и сырые результаты — [preflight.md](../preflight.md).

Пункт 1.3 выполнен 13.11.2026: в [design.md](../design.md#контракт-команд-v1-зафиксирован-13112026) закреплены схемы семи групп, обязательность/типы параметров, селекторы, лимиты, разрешения, ошибки, состояния и адаптация общего lifecycle. Примеры валидных, неоднозначных и конфликтующих запросов сверены документально. Целевая ветка v1 — 8.5; выборочная поддержка 8.3 отложена. Реализация Toolkit не начиналась; компиляция исходного замыкания не означает разрешения перенести небезопасные ветви без адаптации. Сквозная приёмка через транспорты и прикладную базу не выполнялась.
