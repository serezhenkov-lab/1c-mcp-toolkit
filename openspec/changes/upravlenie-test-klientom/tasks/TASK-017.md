# 1c-mcp-toolkit / TASK-017 — Сквозная проверка и приёмка первой версии

**Уточнение MVP 17.11.2026:** Единая приёмка MVP: меню/разделы/панели, документ, справочник, обработка, отчёт, регистр, константа, настройки/общая форма. Один набор данных/роль и недостающие простые формы только в изолированном стенде; один пакет прямого embedded HTTP, без повторения всей матрицы. Документный пример не является границей охвата. [План](../tasks.md#http-mvp), [оценка остатка](../estimate.md).


**17.11.2026 — ближайший рубеж:** [самостоятельный MVP встроенного HTTP](../tasks.md#http-mvp), без Python proxy. Существующие проверки засчитываются по совместимому кандидату; новый пакет — штатная настройка/подключение, UI-запись, HTTP-сверка, снимок и завершение. Файловый мост и полная матрица остаются после MVP, пункты не закрываются этим решением.


## Цель и ожидаемый результат

Подтвердить прохождение сценария агентом и диагностируемость отказов на полной матрице.

## Требования и сценарии

[TI-05](../specs/test-client-integration/spec.md) и все сценарии [сеанса](../specs/test-client-session/spec.md), [UI](../specs/test-client-ui/spec.md), [интеграции](../specs/test-client-integration/spec.md).

## Границы работы

Общая регрессия, сборка и сквозная приёмка. Рабочую установку не обновлять; неподтверждённые проверки не считать выполненными.

## Затрагиваемые объекты и технические указания

Существующие Python/BSL-средства проверок, отдельная тестовая EPF, паспорт стенда и протоколы. Подготовка/проверка данных существующими запросами и BSL. См. [решение](../design.md) и [исследование](../research.md).

## Зависимости

Для полной приёмки v1 — [TASK-011](TASK-011.md)–[TASK-016](TASK-016.md), исходные пробелы UI-01/TS-02 в TASK-018 и доказанная идентичность строк; подтверждённый паспорт среды и доступ к обоим типам базы. Частичные проверки и новый 7.5 идут на каждом этапе, не ждут всех задач. TASK-020–TASK-022 и дополнительные TE-требования не являются зависимостью исходного рубежа. Архивирование расширенного change отдельно требует закрытия/оформленного переноса нового объёма.

## Критерии приёмки и проверка

Для каждой из шести комбинаций маршрута и типа базы сохранён результат основного сценария и проверок отказов. Итоговый запрос подтверждает ровно один документ. После настройки стенда ручных действий нет. Статика, сборка, runtime и приёмка описаны отдельно.

## Дополнительные проверки по исходникам доноров

Процесс на совпавшем порту без доказанного владения; одинаковые строки таблицы; один кандидат в усечённой форме выбора; отказ завершения редактирования без автоматической отмены; навигационное чтение с сообщением о курсоре; сбой диагностики после вызванного действия; неизвестный ввод без повторной мутации другим методом. Отдельно подтвердить захват окна внутри RDP со стороны менеджера, когда proxy находится на другом компьютере.

## Матрица приёмки

| Маршрут | Файловая база | Клиент-серверная база |
| --- | --- | --- |
| HTTP через proxy | Основной сценарий + отказы | Основной сценарий + отказы |
| Файловый мост через proxy | Основной сценарий + отказы | Основной сценарий + отказы |
| Встроенный HTTP Toolkit | Основной сценарий + отказы | Основной сценарий + отказы |

Основной сценарий: start → open → заполнить документ без обязательного поля → нажать запись → получить отказ и сообщение → исправить поле → записать → подтвердить запросом ровно один документ с ожидаемыми значениями. Для идентификации использовать уникальный признак тестового прогона. Дополнительно проверить таблицу и снимок клиента.

Отказы: отсутствие /TESTMANAGER, второй клиент, другая база, неоднозначная/устаревшая цель, модальное окно, ограничение выдачи, тайм-аут, частичная табличная операция, потеря ответа после записи, повтор/конфликт ключа, истечение хранения, потеря связи и restart, detach и stop чужого процесса. Для разрешений отдельно проверить deny/ask/session_allow и сброс после restart; для анонимизации — вложенные данные и сохранность ID.

Настройка стенда (доступы, разрешение внешней обработки, исходные данные, допустимый режим разрешений) выполняется до начала автономного сценария и фиксируется в протоколе. Ручное исправление формы или ответа на диалог во время сценария означает непрохождение критерия автономности. Доказательства содержат версии платформы/конфигурации/EPF/proxy, тип клиента, маршрут, тип базы, операции и итоговый запрос. Отсутствующая среда означает неполную приёмку, а не успешную проверку.
