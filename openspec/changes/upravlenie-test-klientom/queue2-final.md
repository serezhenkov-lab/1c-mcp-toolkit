# Очередь 2 — заключительный доступный пакет 16.11.2026

Поручение: доступный остаток 8.2, 8.3, 6.4 без повторения принятых проверок. Локальный файловый Windows стенд 8.5.1.1529. Все незавершённые пункты и 13/42 сохранены. Наблюдатель не подключён, анонимизация отложена, рабочая установка не обновлена.

## Найдено и исправлено: 8.3

Обычная EPF предыдущего этапа воспроизвела дефект: test_input/select с отсутствующим вариантом после activate/open_choice_list возвращал element_not_found в errors.observation. Два подготовительных действия не превращают отказ поиска варианта в ошибку наблюдения результата.

Минимальная правка драйвера: на время поиска варианта сохраняется diagnostic_stage=resolve. При отказе публичная error.stage=resolve, ошибка относится к errors.command; после успешного разрешения маркер снимается, последующее наблюдение остаётся прежним. execution=invoked, два подтверждённых шага, последний open_choice_list и исходный operation_id сохраняются. Повтор request_id возвращает исходный результат, список не открывается повторно. Выбор, поиск по таблице и клиентский адаптер не добавлены.

Проверено на embedded и HTTP с отдельным тестовым экспортом чтения кнопки; **file bridge проверен обычной EPF без тестовых экспортов**. Проверки общего lifecycle/progress/компактации повторно не запускались.

## Новые проверки 8.2

У активной кнопки Проверить текст редактирования и режим редактирования недоступны: available=false, value=null, reason=property_read_failed. Список имеет отдельную причину not_an_input_field. Публичный tree не изменяет активный элемент; сравнение выполнено независимым чтением штатного API до/после. Тестовый экспорт существует только в отдельной EPF менеджера, не в тест-клиенте и не в исходниках продукта.

Первое ожидание harness было слишком строгим: оно требовало property_read_failed и для списка. Исправлено ожидание теста, а не производственная логика. Подтверждённые проверки выбора не повторены: embedded продолжен с --remaining-only.

## Новые проверки 6.4

### Неактивный desktop

Создан отдельный Windows desktop, оба собственных процесса запущены через CreateProcessW/STARTUPINFOW.lpDesktop. EnumDesktopWindows по дескриптору созданного desktop подтвердил видимые HWND обоих фактических PID; тестовый клиент подключился и публично отдал окна. Input desktop до/после оставался прежним. Никакого SwitchDesktop и переключения рабочего стола пользователя не выполнялось.

get_screenshot(target=test_client) отказал с screenshot_target_unavailable, PNG отсутствует. Проверена именно недоступность input desktop, а не невозможность attach. После теста процессы остановлены, CloseDesktop успешен, input desktop не изменён.

Сохранены диагностические попытки: Python STARTUPINFO не передавал произвольный атрибут lpDesktop (первые процессы фактически работали на обычном desktop); затем чтение дескриптора desktop чужого потока из harness оказалось недоступно и заменено прямым EnumDesktopWindows. В заключительном runtime первые два критерия прошли; третье ожидание ошибочно требовало внутреннюю строку desktop_unavailable. Публичный адаптер нормализует её в screenshot_target_unavailable. Сохранённый ответ проверен автоматически в accepted-review.json; **неуспешный assertion исходного harness сохранён и не выдан за успешный полный прогон**, повторный запуск ради уже доказанного отказа не выполнялся. Исправленная проверка записана в runner.

### Прекращение клиента внутри захвата

Отдельная тестовая копия ScreenCapture DLL содержит барьер после получения пикселей/метаданных, непосредственно перед существующей финальной проверкой HWND/PID/desktop/Alive. Harness дождался барьера при живом клиенте, остановил только собственный тест-клиент, отпустил барьер. Маркер внутри существующей ветви identity_changed доказал срабатывание именно финального guard. Публичный ответ — screenshot_target_unavailable без PNG.

Production C++/DLL/template не менялись. В тестовой копии добавлены только ограниченный 15-секундный барьер и маркер ветви; условия проверки не ослаблены. Компонента выполняется в менеджере, клиентского наблюдателя нет. Это проверка исчезновения HWND/процесса между началом и завершением захвата, **не доказательство обработки пересоздания HWND при продолжающем жить процессе или повторного использования HWND**.

### Попытка создать неоднозначное окно

Fixture штатно открыла ТекстовыйДокумент.Показать. Публичный UI сообщил дополнительную TextDocumentForm, но EnumWindows нашёл только один видимый unowned HWND того же PID; дополнительные окна имеют владельца. Поэтому критерий двух главных окон не создан и не засчитан. PID/владение не подменяли, окна не перепривязывали WinAPI ради прохождения теста. Проба сохранена; автоматически повторять её на других маршрутах бессмысленно.
