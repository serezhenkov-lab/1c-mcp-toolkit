# TASK-021 — восстановление runner после потери процесса

17.11.2026. Реализованы сохранение связей запуска и восстановление через существующий общий lifecycle. Рабочая установка не обновлялась; наблюдатель не подключался, новой записи uilog нет. Пункты остаются открытыми.

## Продуктовый путь

`ScenarioRunner(..., store_path=...)` и `ScenarioContextProvider.run(..., store_path=...)` сохраняют запуск в локальной SQLite. CLI: обычный `--run --store <путь>`; новый процесс использует тот же endpoint/channel/policy и `--store <путь> --recover <run_id>`. Только дополнительный `--resume` разрешает отправку ещё не начатых шагов. Список сохранённых запусков и их ID доступен через `--store <путь> --list-runs` без сетевых запросов; после потери процесса не требуется ручное чтение SQLite. Проверено на сохранённом прерванном запуске и отдельным локальным тестом. Без store сохраняется прежний совместимый режим в памяти; потерянный запуск из него восстановить нельзя.

Хранилище фиксирует шаблон/параметры, план, исходный контекст, ID запуска/шага/запроса и полученный operation_id. Перед отправкой фиксируется dispatching, после получения ответа — operation_id, затем результат. SQLite synchronous=FULL; ошибка первоначального сохранения не допускает отправку. Это связи сценария и сохранённые наблюдения, не второй исполнитель или источник истины об операциях: при восстановлении даже сохранённый succeeded повторно сверяется с общим lifecycle.

Один файл хранилища обслуживается одним процессом одновременно. Межпроцессная блокировка ОС снимается при гибели процесса; PID и истечение произвольного lease не используются для захвата владения. Файл является доверенным локальным состоянием приложения и содержит параметры сценария; управлять доступом к нему следует как к локальной политике. Переносимость между пользователями/машинами и сетевые файловые системы здесь не подтверждены.

Новый поставщик получает свежий контекст и выполняет полный preflight сохранённого сценария. Привязка owner/channel/base/profile/session/generation/implementation/platform/mode и ревизии политики/capabilities должны совпасть. Истечение прежнего краткого контекста разрешено компенсировать свежим наблюдением той же привязки; изменение сеанса или политики блокирует восстановление. Перед новым шагом выполняется обычный свежий guard.

Для каждого ранее отправленного шага допускается только `test_session/status` по сохранённому operation_id с проверкой request_id и сеанса. Подтверждённый успешный префикс пропускается. Восстановление само не отправляет test_input/test_action и не вызывает retry_delivery. Явный resume продолжает с первого ещё не созданного исполнения шага, сохраняя run_id и детерминированные ID следующих шагов.

Если ID операции не успел сохраниться, результат удалён/недоступен, идентичность не совпала или lifecycle сообщает unknown, продолжение блокируется. Отсутствие записи не доказывает отсутствие мутации. Running/queued/awaiting_approval возвращаются для последующего наблюдения. Автоматического повторного исполнения нет. Если runner ранее уже зафиксировал unknown, успешная сверка записывается отдельно в reconciliation; исходный unknown не переписывается, общий итог остаётся partial.

## Проверка

- **11 новых локальных тестов:** потеря процесса после/до receipt, явное продолжение без повтора, повторное восстановление, другой сеанс, retention/чужой ID/unknown/running, отказ guard, сохранение истории unknown, конкурирующий владелец, смена scope, отказ диска до отправки, законченный запуск. Некоторые сценарии объединены в одном тесте.
- **12 тестов прежнего runner** и **11 поставщика** повторены обоснованно: изменены их общий цикл исполнения и продуктовый вход. Успешны.
- На отдельной файловой **8.5.1.1529 / embedded HTTP** два реальных дочерних Python-процесса принудительно завершены, а восстановление выполнялось отдельными процессами продуктового CLI.
- Сохранённый receipt: реальный ввод подтверждён, процесс убит до сохранения терминального результата. Первый recover только наблюдал (dispatch_count=1). Resume выполнил только readback (2). Повторный resume оставил те же ID и число отправок (2). Проверка всего JSON в harness первоначально ошибочно ожидала отсутствие нового reconciliation у readback; исправленная проверка ID выполнена на сохранённых ответах, без повторного UI-ввода. Исходное неуспешное утверждение сохранено как историческое свидетельство.
- Потерянный receipt: процесс убит после возврата HTTP-ответа транспортом, до передачи его runner. В checkpoint operation_id отсутствует. Recover и два resume сохранили unknown и одну отправку. Независимый test_expect подтвердил введённое значение; документы до/после совпадают. Здесь принудительная потеря ответа моделируется границей процесса, а не обрывом сети.
- В обоих прогонах собственные процессы стенда завершены. В первом прогоне итоговая отдельная query-сверка документов не выполнялась из-за описанного assert; readback продукта прошёл. Число новых отправок подтверждено связями runner и локальными тестами транспорта; отдельный счётчик бизнес-обработчика в конфигурацию не добавлялся.
- BSL/EPF не менялись: использована ранее собранная Toolkit-route.epf. Сборка платформой и прежние UI-наборы не повторялись. AST, OpenSpec strict и diff-check выполнены отдельно.
