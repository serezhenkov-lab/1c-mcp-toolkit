# HTTP во время пошаговой компактации — 15.11.2026

Продолжение очереди 1 после [пакетной оптимизации](lifecycle-fast.md). Изменён embedded-владелец TASK-002 соседнего change; UI-адаптация и проверка относятся к TASK-016. Анонимизация отложена, наблюдатель не подключён, Открыть() не исследовался, рабочая установка не обновляется. Все 13/42 отметки и незавершённые пункты сохранены.

## Устройство

После запуска владельца LifecycleКомпактировать планирует работу и возвращается. Одноразовый обработчик ожидания продолжает её короткими шагами: поиск истёкших результатов, распространение зависимостей, запись next, первая и повторная проверки, commit/установка. Между шагами клиентский цикл принимает HTTP. Нет вложенного ручного вызова HTTP-диспетчера, нового процесса-владельца, наблюдателя или второго журнала.

Порция записи/проверки ограничивается 64 строками, порогом 262 144 символа либо 50 мс накопления, затем выполняется проверка хешей и управление возвращается клиенту. Одна большая запись и отдельный файловый/серверный вызов не прерываются посередине, поэтому 50 мс не являются гарантированным верхним пределом задержки. Поиск истечений проходит по 128 записям за шаг. Запланированный шаг не откладывается заново каждым входящим запросом; повторный запрос принудительной очистки сохраняется в текущей работе.

До commit любая запись владельца закрывает потоки подготовки и удаляет неподтверждённый next. Новая запись сначала сохраняется в действующем журнале, затем подготовка начинается заново. Это обеспечивает согласованность при admission, событиях подтверждения и завершении операции. При непрерывном потоке записей очистка может откладываться; квоты и отказ при нехватке места сохраняются, ключи не удаляются ради прогресса.

Обе полные проверки checkpoint выполняются до commit. Запись/закрытие маркера, удаление старого файла, перемещение next и удаление маркера выполняются в одном шаге без уступки управления. Восстановление после сбоя по-прежнему проверяет подтверждённый next/установленный файл, запрещает откат к старому файлу после commit и игнорирует неподтверждённый next. Ошибка закрывает исполнение через healthy=false. Формат журнала и маркера не изменён.

Первичное чтение и восстановление файла остаётся синхронным; при ленивой инициализации первым test_* оно ещё может задержать первый запрос. Следующая за чтением начальная компактация в production-пути уже выполняется по шагам: initializing=true закрывает admission/получение результата до завершения очистки и перевода прежних активных операций в unknown. HTTP при этом продолжает работать, status получает явный operation_store_unavailable без принятия новой команды. После готовности доступен прежний ID. Эта ошибка означает временную неготовность владельца, не потерю записи.

Внутреннее синхронное ожидание того же алгоритма сохранено для отдельного вызова настройки и детерминированных тестов; embedded-диспетчер его не включает. Обычное обслуживание и очистка по квоте не используют синхронное ожидание. Пока место ещё не освобождено, новая команда может получить прежний operation_quota_exceeded; ключ не принят и действие не запущено. Чтение существующего operation_id после готовности по-прежнему не расходует admission-квоту.

## Проверка

Стенд: отдельные файловые базы `.local/lifecycle-http`, тонкий клиент 8.5.1.1529, ApiProbe, HTTP localhost:17661. Синтетические наборы прежнего формата: 1 000 и 10 000 ключей, файл около 64 MiB. `/health` и REST `test_session/status(operation_id)` опрашиваются на протяжении каждого раунда с таймаутом 2 с; native MCP проверяется после раунда. Замеры не являются SLA или пользовательской приёмкой.

Первый прогон 10 000 прервался из-за PermissionError оснастки: Python прочитал служебный JSON во время его перезаписи 1С. Это ошибка фиксации измерений, не HTTP-отказ. Исходные отчёты и незавершённый журнал сохранены; добавлен ограниченный повтор чтения JSON. Повтор идёт в отдельной копии, включая восстановление неподтверждённого next, под именем keys10000retry.

Проверка простоя в ранней оснастке ожидала готовую очистку строго через 65 с и не увидела завершённую очистку. Сохранён исходный отказ assertion_cached_expired. Оснастка теперь ограниченно ждёт окончания реально запущенной работы, не вызывает очистку принудительно и проверяет физический файл; таймаут не считается успехом.

В контролируемых точках write, verify, verify_again и перед commit оснастка вызывает штатные API владельца: admission, awaiting_approval, running и завершение с результатом. Это инъекция входящих записей между шагами, не отдельный клиентский наблюдатель и не новый публичный метод. Каждый раз подготовка отменяется; после финального checkpoint и restart сохранены ID/fingerprint, event_seq=2 и маркер результата. Число ключей не уменьшилось, служебные status не добавляли записей.

На 10 000 ключей полный проход теперь занял 54,974 с вместо 32,099 с в синхронном пакетном варианте; около 64 MiB — 33,754 с вместо 18,909 с. Цель изменения — доступность HTTP между порциями, а не уменьшение общего времени. Прежние результаты и прерванные попытки сохранены отдельно от окончательного прогона.

## Ограничения

Работа распределена по клиентскому циклу; это не параллельное исполнение BSL. Совокупная длительность очистки может увеличиться ради доступности HTTP. Начальная загрузка, отдельные вызовы платформы/носителя, экстремальная нагрузка без свободного клиентского времени и потеря питания ОС не получают новой гарантии. Клиент-серверный/RDP режим, одновременный предел 10 000 ключей и 64 MiB и пользовательская приёмка остаются открытыми. SQLite proxy и его транспорт не изменялись.
