## Purpose

Управление жизненным циклом одного тест-клиента в одной тестовой базе и одном канале Toolkit.

## ADDED Requirements

### Requirement: Раздельное версионирование Toolkit

Toolkit SHALL хранить версию основы поставщика в отдельной функции модуля объекта `ВерсияОсновыToolkit`. Поле `Версия` в `СведенияОВнешнейОбработке` SHALL содержать версию нашей сборки в формате `ГГ.М.Д.ЧЧММ` по времени Саратова. Имя файла SHALL иметь формат `MCPToolkit__ГГ_М_Д_ЧЧММ.epf` с той же версией.

#### Scenario: Версии и авторство на форме
- **WHEN** открывается основная форма Toolkit
- **THEN** форма показывает «Основа Toolkit — 1.10.0» для текущей основы и «Наша сборка — ГГ.М.Д.ЧЧММ» для текущей сборки. Блок настроек подписан «Управление тест-клиентом — разработка нашей команды».

#### Scenario: Сборка на той же версии поставщика
- **WHEN** из исходников Toolkit собирается новая EPF без обновления выпуска поставщика
- **THEN** версия поставщика сохраняется, а поле регистрации БСП и имя файла используют один номер новой сборки.

### Requirement: TS-01 Режим менеджера и единственный клиент

Toolkit SHALL предоставлять test_session с действиями start, attach, status, detach, stop. Запуск и подключение SHALL требовать режим /TESTMANAGER и доступность штатного API ТестируемоеПриложение. Одновременно допускается один клиент; база клиента должна соответствовать выбранной тестовой базе менеджера. Произвольное переключение на другую базу в активной сессии запрещено.

#### Scenario: Запуск без режима менеджера
- **WHEN** start или attach вызван в обычном сеансе
- **THEN** возвращается manager_mode_required до запуска процесса или подключения.

#### Scenario: Второй клиент
- **WHEN** уже имеется запускаемый, подключённый либо известный собственный отключённый клиент
- **THEN** новый start отклоняется; состояние существующего клиента остаётся доступным.

#### Scenario: Подключение другой базы
- **WHEN** параметры attach указывают на другую базу или соответствие базы нельзя подтвердить
- **THEN** готовность к UI-командам не объявляется, возвращается диагностическая ошибка.

#### Scenario: Предупреждение открытия внешней обработки
- **WHEN** запуск остановлен предупреждением безопасности до готовности API
- **THEN** ready не возвращается; по ограниченному ожиданию выдаётся состояние запуска и доступная диагностика, без автоматического ослабления защиты пользователя или повторного запуска клиента.

### Requirement: TS-02 Запуск и наблюдаемое состояние

start SHALL запускать отдельный сеанс /TESTCLIENT и возвращать session_id и operation_id. Долгое ожидание готовности SHALL не удерживать транспортный запрос до полного запуска: состояние и итог доступны отдельно. status SHALL различать absent, starting, ready, detached, disconnected, stopping, stopped, failed и сообщать текущую операцию, факт владения и безопасные сведения о базе/клиенте. Готовность означает успешное подключение API тестирования, а не только существование процесса.

#### Scenario: Долгий запуск
- **WHEN** процесс создан, но API ещё не готов
- **THEN** возвращаются идентификаторы и starting; последующий status показывает готовность либо диагностируемый отказ без повторного запуска.

#### Scenario: Ошибка запуска
- **WHEN** клиент не достигает готовности за установленный срок
- **THEN** результат содержит стадию, причину и сведения, остался ли запущенный процесс; второй клиент автоматически не создаётся.

### Requirement: TS-03 Подключение и ограничение остановки

attach SHALL подключаться к указанному клиенту; detach SHALL разрывать управление без завершения процесса. stop SHALL завершать только клиент, запущенный Toolkit и однозначно опознанный по сохранённому доказательству владения. Один PID или имя процесса недостаточны. attach к чужому клиенту SHALL не давать право его остановки. При диалоге несохранённых данных Toolkit SHALL показывать состояние и не выбирать ответ произвольно.

#### Scenario: Отключение
- **WHEN** выполняется detach
- **THEN** процесс остаётся работающим, UI-команды отклоняются до нового подключения.

#### Scenario: Чужой процесс
- **WHEN** stop адресован клиенту без доказанного владения
- **THEN** возвращается client_not_owned, процесс не завершается.

#### Scenario: Совпадение порта
- **WHEN** обнаружен процесс TESTCLIENT на ожидаемом порту, но происхождение от запуска Toolkit не подтверждено
- **THEN** совпадение порта не даёт права stop; принудительная остановка по шаблону командной строки запрещена.

#### Scenario: Остановка собственного клиента
- **WHEN** stop выполнен для собственного клиента без блокирующего диалога
- **THEN** остановка подтверждается наблюдением завершения; чужие процессы 1С остаются работать.

#### Scenario: Подтверждение выхода
- **WHEN** штатная остановка собственного клиента открывает диалог выхода
- **THEN** stop возвращает `blocking_window` с ID диалога и сохраняет готовое подключение. Явный ответ о завершении подтверждается по остановке того же процесса.

### Requirement: TS-04 Перезапуск и потеря связи

Штатный перезапуск Toolkit SHALL сохранять роль /TESTMANAGER, но не сеансовое разрешение опасных операций. Старые session_id и идентификаторы интерфейса SHALL инвалидироваться при новом подключении. Автоматическое восстановление SHALL не повторять незавершённые действия и не запускать второй клиент при неизвестном состоянии первого. При недоказуемом владении после перезапуска остановка запрещена.

#### Scenario: Перезапуск менеджера во время действия
- **WHEN** менеджер перезапущен без подтверждённого результата действия
- **THEN** результат остаётся unknown по общему контракту операций; старые цели отклоняются, действие автоматически не повторяется.

#### Scenario: Первый штатный перезапуск со встроенным журналом
- **WHEN** встроенный менеджер штатно перезапущен с существующим журналом
- **THEN** старый менеджер освобождает журнал до ответа о перезапуске. Новый менеджер подтверждает прежнюю операцию через status, сохраняя состояние и ключ дедупликации.

#### Scenario: Потеря связи
- **WHEN** соединение API с клиентом потеряно
- **THEN** status возвращает disconnected; следующие UI-команды получают session_not_ready, а состояние процесса не подменяется утверждением об остановке.

#### Scenario: Управляющий restart при активной файловой операции
- **WHEN** файловый исполнитель уже принял запрос и асинхронная операция оставляет клиентский цикл доступным, а в том же канале поступает restart_1c_session
- **THEN** restart доставляется без ожидания конечного ответа активной операции; обычные команды не обходят её, исходный запрос не публикуется повторно, его собственный результат сохраняется отдельно от ответа restart.

#### Scenario: Неопределённая доставка управляющего запроса
- **WHEN** ответ restart отсутствует, публикация неоднозначна либо исходная операция ещё не вернула свой результат
- **THEN** restart и исходная операция автоматически не повторяются; отсутствие ответа restart не освобождает обычную последовательную очередь. Второй restart не доставляется одновременно с уже выполняемым restart/close.

### Requirement: Настройки тест-клиента текущей базы
Форма Toolkit SHALL показывать поля «Пользователь» и «Пароль». Локальный порт SHALL находиться в сворачиваемых дополнительных настройках и по умолчанию иметь значение 1538. Форма не показывает переключатели использования профиля и обязательного пароля, ID профиля и кнопку сохранения профиля. Для MCP сохраняется совместимость с ранее сохранённым ID, для новой настройки используется `local`.

#### Scenario: Автосохранение пользователя и порта
- **WHEN** пользователь меняет имя пользователя или порт
- **THEN** допустимое значение сохраняется автоматически. При занятом тест-клиенте изменённые параметры применяются перед следующим запуском или подключением.

#### Scenario: Пароль текущего сеанса
- **WHEN** пользователь вводит пароль
- **THEN** пароль применяется к запуску тест-клиента только в текущем сеансе. При пустом поле аргумент `/P` отсутствует.
