# Restart во время активной операции файлового моста — 15.11.2026

Продолжение очереди 1, пункты 2.3/6.1/6.2: устранена задержка управляющего restart, выявленная в [предыдущем прогоне](queue1-remaining-checks.md). Общий журнал/очередь остаются у прежнего владельца. Все незавершённые пункты и 13/42 отметки сохранены. Наблюдатель не подключён, анонимизация отложена, рабочая установка не обновлена.

## Изменение

FileTransport хранит один обычный active и один управляющий control. Пока обычная операция ждёт результата, из того же канала разрешено выбрать только restart_1c_session, причём после появления её `.running`: исполнитель уже принял исходный запрос. Обычные команды перед restart остаются в очереди, не извлекаются и не теряют порядок. Фильтр использует штатный метод выдачи очереди с прежними проверками доставки и состояния; дополнительного реестра операций нет.

Управляющий запрос публикуется обычным атомарным request.json с собственными ID, сроком и каналом. Новый файловый протокол и обработчик 1С не добавлены. Активные `.running` и ID не заменяются; повтор исходного request.json не производится. Ответы исходной операции и restart проверяются и сохраняются независимо. Обычная очередь продолжает работу только после обоих ответов. Неполученный ответ, неизвестный исход публикации или отказ restart не инициируют повтор. На одну активную операцию допускается одна управляющая доставка; restart/close не прерываются ещё одним restart.

BSL уже принимал файлы во время асинхронного UI-ожидания и при штатном закрытии отдавал unknown незавершённой операции. Исправление использует это поведение. Синхронный непрерываемый вызов платформы не получает гарантии немедленного прерывания. При аварийной потере исходного ответа мост сохраняет блокировку обычной доставки и доказательства незавершённости; автоматическая очистка/переисполнение не добавлены.

## Проверка

Новый файловый стенд `.local/queue1-file-restart/file`, тонкий клиент Windows 8.5.1.1529, ApiProbe, локальный file bridge 17666/TESTCLIENT 16546. Сценарий публичного REST запустил expect на 60 секунд, увидел running и отправил restart. Все **23/23** утверждения прошли: unknown исходной операции, тот же ID при повторе без исполнения, роль TESTMANAGER, сброс session_allow, старые session/window/element ID, один прежний клиент и запрет stop без владения. Повтор только TTL также успешен: result_expired, прежний ID, status и конфликт после истечения.

Первый исправленный прогон дал ответ restart за 6,934 с вместо прежних 66,707 с. Затем добавлена защита от вложенного restart/close и выполнен финальный повтор на тех же исходниках Python, которые включены в доказательства. Точное время финального повтора — `verification.json`; измерение не является SLA. SQLite-проверка после выполнения подтверждает одну строку исходного ключа с прежним operation_id и state=unknown. Служебных `.running` после штатного завершения не осталось.

Окончательный результат: **6,885 с**, 23/23 утверждения, одна запись `fda04a56-1ea2-4bad-8ddb-22a6d087d135` для исходного ключа со статусом unknown. Итоговая проверка собственных процессов: 0. Архив содержит 56 файлов; CRC и SHA256 каждого файла проверены.

Промежуточный повтор остановился до restart: проверка позднего итога полагалась на фиксированный сон и получила ещё активную операцию вместо конечного ответа. Оснастка теперь ограниченно опрашивает тот же ключ status, не повторяя действие. Неудачная попытка сохранена в file-before-final; финальный прогон выполнен в новой копии базы/журнала. Это исправление измерения, production-код по этому результату не менялся.

Python — **57 тестов**: 25 файлового транспорта, 3 HTTP/file интеграции с имитацией 1С, 19 общего lifecycle и 10 публичного адаптера. Добавлены случаи непринятого запроса, обхода только restart при обычных заданиях перед ним, чужого канала, обоих порядков ответов, отказа restart, неопределённой ошибки публикации, отменённого запроса, вложенного restart и сохранения durable unknown/ключа без повторной выдачи.

Тестовая EPF собрана на 8.5.1.1529 с ThinClient/Server/HandlersExistence. Production BSL не менялся, BSL LS повторно не запускался. Генератор --check, AST изменённого Python, OpenSpec strict и git diff --check проверены отдельно. Прежние изменения сохранены, рабочая установка не обновлялась. Запуски использовали доверенную настройку профиля в тестовой EPF, поэтому штатное восстановление профиля вне оснастки этим не подтверждается.

## Остаток

Блокер «file restart ждёт конца асинхронного expect» устранён на указанном стенде. Это не закрывает 2.3, 6.1 или 6.2: остаются профиль без startup-оснастки, полноценная матрица аварийной потери исполнителя/владельца и ответа после записи документа, row/snapshot ID, клиент-серверный/RDP и реальный server_host. Анонимизация остаётся отложенной частью 6.3. Требования не упрощены.

Доказательства: [архив](evidence/file-restart-runtime.zip), [манифест SHA256](evidence/file-restart-manifest.json). Включены оба успешных runtime-прогона, тестовая форма, итоговые проверки, журналы unit/build и точные Python-исходники. Базы и EPF-бинарники не включены. Собственных процессов по итоговой проверке осталось 0.
