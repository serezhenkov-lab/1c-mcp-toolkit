# Обратная связь тест-клиента и наблюдатель форм

18.11.2026. Идеи для возвращения к TASK-019. Действующее решение и границы подключения описаны в [9.1](row-observer-decision.md).

## Как подтвердить результат действия

Успешный вызов платформенного метода подтверждает этап вызова. Для результата выбираем проверку по цели команды:

- Подбор товара — прочитать исходную ячейку после завершения редактирования. На УНФ при возврате из подбора менялась оболочка окна. Повторная привязка по навигационной ссылке и имени формы позволила подтвердить исходную строку.
- Открытие отчёта — дождаться нужной формы или формы выбора варианта. При появлении диалога вернуть его и последнее состояние. Повторять можно чтение в пределах бюджета.
- Запись и проведение — запросом проверить точную ссылку, результат проведения и при необходимости движения.
- Остановка клиента — наблюдать возможный вопрос о выходе и проверять завершение конкретного процесса. На УНФ появление диалога именно во время проблемного stop пока не доказано.

При неизвестном исходе нужно уточнять состояние окна, операции или данных перед следующей мутацией. Testpilot тоже читает состояние после действия. Его бинарный декодер разбирает ответы протокола, а диагностика отдельно читает окно и сообщения. Специализированный подбор проверяет принятое значение. Для Toolkit полезен этот принцип ограниченного наблюдения внутри той же команды.

Источники: [пилот УНФ](tasks/TASK-014.md#результат-и-доказательства), [пробелы УНФ](unf-mvp-verification.md), [Testpilot: нажатие и чтение результата](https://github.com/ROCTUP/1c-testpilot/blob/46eaa7454292e3e8a8159f631190221b5ffdce72/app/_runtime.py#L2043).

## Что даёт наблюдатель

Менеджер и тест-клиент — два процесса 1С. В локальном варианте TASK-019 оба работают в одной тестовой базе. Наблюдатель запускается в том процессе, где открыта нужная форма. Соседний сеанс в той же базе не получает её живое состояние.

По проекту это отдельный режим той же EPF Toolkit. Первая задача — в одном клиентском обработчике прочитать нативный ID строки `ДанныеФормыКоллекция` и относящиеся к ней значения. Две строки с одинаковым товаром, количеством и ценой могут иметь разные ID. Прототип подтвердил это на фикстуре и показал стабильность ID при перестановке. Динамические списки, деревья и замена источника требуют отдельных проверок.

Менеджер выполняет ввод и нажатия штатно. Наблюдатель читает разрешённые свойства. ID связывается с сеансом, формой, таблицей и поколением источника. Между снимком и последующим внешним нажатием строка может измениться. Даже точный снимок не делает проверку и действие одной операцией.

### Варианты канала

| Вариант | Плюсы | Что потребуется и где ограничение |
|---|---|---|
| Выделенный файловый канал | Описан в TASK-019. Удобен для первой пробы с двумя локальными процессами. Можно переиспользовать правила публикации запросов, ответов и сроков жизни. | Отдельный потребитель и каталог или пространство сеанса. Проверить доступ обоих процессов, изоляцию, поздние ответы и переподключение. |
| Встроенный HTTP Toolkit | Переиспользуется работающий слушатель. Клиент может обращаться по localhost или доступному сетевому адресу менеджера. Публикация УНФ не нужна. | Нужен отдельный внутренний маршрут. EPF в тест-клиенте получает адрес и временную привязку при запуске, короткими исходящими запросами забирает задание, читает форму на клиенте и возвращает снимок с ID запроса и поколением сеанса. Проверить тайм-ауты и поведение при модальном окне. Маршрут должен обслуживаться, пока UI-операция менеджера ждёт ответ. |
| Автономный сервер платформы `ibsrv` | Публикует тестовую базу без отдельного Apache или IIS. Пригодится для отдельного стенда веб-клиента. | Опубликованный HTTP-сервис выполняется на сервере. Для живой формы тонкого клиента понадобятся посредник и наблюдатель в самом клиенте. |

При оценке HTTP перенести ограничения действующего контракта: привязка к нужному процессу и сеансу, узкий перечень операций чтения, отзыв привязки при переподключении и изоляция от публичной очереди MCP. Производительность каналов не измерялась. Локальная проба через файлы и HTTP для разнесённых процессов остаются вариантами для обсуждения.

## Что изучить при возвращении

1. На тестовой УНФ взять две одинаковые строки накладной. Сравнить, что видит менеджер тестирования и что можно прочитать из соседней EPF в том же клиентском процессе. [Менеджер открытых форм](https://infostart.ru/1c/tools/610324/) · [Обход открытых окон](https://infostart.ru/1c/articles/920170/) · [Идентичность строки коллекции](https://infostart.ru/1c/articles/2156279/) · [Идентичность узла дерева](https://infostart.ru/1c/articles/2165071/)
2. В типовом отчёте применить отбор по складу. Проверить, можно ли прочитать фактически применённые настройки СКД, и сравнить результат отчёта на данных двух складов. [Глобальное меню разработчика](https://infostart.ru/1c/articles/1273456/)
3. Для разведки состава формы сравнить статический XML с экземпляром, подготовленным под тестовой ролью. Отдельно изучить структуру снимка с путями к данным и типами. Снимок после создания формы и состояние после пользовательских действий отвечают на разные вопросы. [Снимок экземпляра формы](https://infostart.ru/1c/articles/2834354/) · [Сбор данных с управляемой формы](https://infostart.ru/1c/tools/2826823/)

Материалы Инфостарта изучались по опубликованным описаниям и фрагментам кода. Обработки на УНФ не запускались. Наблюдатель и HTTP-канал не подключены. Возвращение к реализации 9.2 требует отдельного решения.
