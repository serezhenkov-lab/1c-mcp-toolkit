## Архитектурная граница

Будущие локальные модули: `scenario_contract.py` (проверка/разрешение параметров и preflight), `scenario_import.py` (uilog → черновик), `scenario_runner.py` (последовательное исполнение через имеющиеся публичные test_*). API preflight: `preflight_scenario(template, parameters, context) -> report`. Вход не содержит функцию, BSL, shell, Python, SQL, URL сервера, пароль или инструкцию изменить конфигурацию. Никаких eval, интерполяции выражений, циклов, ветвлений, вложенных сценариев, фонового планировщика и параллельных шагов.

Первый потребитель — harness, затем отдельно согласованная продуктовая интеграция. Повторно использовать `valid_request` из `onec_mcp_toolkit_proxy/test_client_contract.py`; регистрация маршрутов находится в `test_client_api.py`, исполнение принадлежит `test_client_operations.py` и общему lifecycle. Их текущие схемы не являются реестром runtime-capabilities. Поля контекста ниже — внутренний контракт будущего preflight, не новые поля ответа существующего API.

Сеанс запускается/подключается снаружи сценария обычным test_session. В v1 шаги не запускают/останавливают/переключают клиента; runner может вызывать test_session/status только для получения состояния своей операции. Это позволяет закрепить одну базу/сеанс до первого шага. Команды сравнения query, захвата, импорта и произвольного execute_code не превращаются в шаги без отдельной версии/расширения реестра. TASK-020 остаётся внешней проверкой бизнес-результата.

## Переносимый шаблон

Корневые обязательные поля, неизвестные поля запрещены:

- `version`: целое 1; bool не версия.
- `scenario_id`: стабильный ID шаблона, `revision`: положительное целое. Изменение любого содержимого меняет digest, даже если автор забыл повысить revision.
- `state`: `draft` или `reviewed`. Импорт всегда создаёт draft; неизвестное событие не пропускается молча. reviewed — декларация автора, а не разрешение на выполнение.
- `parameters`: объект объявлений `{name: {type, required, default?}}`. Типы: string/boolean/integer. Необязательный параметр обязан иметь default своего типа; required=true запрещает default. Явный null не поддержан. Неизвестные/лишние параметры вызова отклоняются.
- `data_scope`: `{policy_id, purpose, mutation}`; mutation — `read_only` или `ui_write`. Это запрос области, а не полномочие. policy_id должен совпасть с отдельно разрешённой политикой контекста.
- `steps`: 1–100 шагов строго в порядке массива.

Имена параметров, scenario_id, step_id и policy_id: 1–128 ASCII-символов, первый — буква/цифра/подчёркивание, далее также допустимы точка и дефис. Пользовательские значения и селекторы поддерживают Unicode. Формат имён задан schema, не переносится на существующие технические ID публичных команд.

Шаг: `{step_id, tool, arguments, on_error, timeout_ms}`. step_id уникален во всём шаблоне; tool — один из реестра ниже. arguments содержит только специфичные поля публичной команды (`action`, `params`, `window`, `element`); `params` обязателен, остальные зависят от команды. request_id/session_id/timeout_ms внутри arguments запрещены: их вставляет исполнитель. timeout_ms — 1..300000, сумма по сценарию не больше 1800000 мс; ожидание подтверждения не даёт автоматически увеличить бюджет.

Размер шаблона после UTF-8 JSON-кодирования не больше 256 KiB; параметров не больше 100, длина строкового значения не больше 65536, глубина JSON не больше 32. Дубли JSON-ключей, NaN/Infinity и числа вне целого диапазона ±(2^53−1) отклоняются до разрешения параметров. После подстановки итоговые команды также должны удовлетворять собственным лимитам test_*; суммарный материализованный план не больше 1 MiB.

### Параметры и селекторы

Единственная ссылка — объект `{"$param":"name"}` целиком вместо одного скалярного значения внутри arguments. Объект с дополнительными полями не ссылка и отклоняется. Нет `$step`, JSONPath, `${…}`, подстановки ключей объектов, сцепления строк, функций или доступа к окружению. Тип сохраняется: boolean false не строка "false", 0 не false. Подстановка выполняется один раз; строка, содержащая `$param`, остаётся строкой. Значение параметра не может быть объектом и поэтому не добавляет поля команды.

tool/action и ключи объектов не параметризуются. action — литерал из публичной схемы. Параметры допустимы в конечных пользовательских значениях, включая точные части селектора, после полной проверки материализованной команды. Изменение значения параметра никогда не сохраняет прежнее разрешение на выполнение.

Шаблон не содержит request_id, operation_id, session_id, HWND, PID, window/element/row ID, snapshot_id или cursor. Для window используется только точный selector по текущей публичной схеме, не `active` и не `id`; element/targets — selector, row — where. Вложенные selection_window/table подчиняются тому же правилу. Это переносимые описания целей; совпадение подписи не доказывает единственность. Неоднозначность в runtime запрещает мутацию, похожий элемент не выбирается.

Секреты и параметры подключения не являются параметрами шаблона: credential handle принадлежит контексту, значения не записываются в сценарий/диагностику. Защищённые пользовательские данные и артефакты следуют действующей изоляции/политике; новый механизм анонимизации отложен, его отсутствие не разрешает обход существующей обработки.

## Реестр шагов и capabilities

| tool | Допустимые варианты | Обязательства |
| --- | --- | --- |
| test_open | без action, params.link | Существующий e1cib link; только разрешённая область той же базы; эффект UI |
| test_inspect | windows/tree/values/messages | Read-only; явный охват; ограничения результата сохраняются |
| test_input | text/check/select | Эффект UI; select через таблицу требует её доказанной поддержки |
| test_action | click/activate_window/select_page/close | Эффект UI; click по группе-карточке не становится доступным по поддержке обычной кнопки |
| test_table | read/find/select/add/fill/delete | Поддержка конкретного действия, источника и целостности; allow_navigation=true считается эффектом UI |
| test_expect | без action; condition по публичной схеме | Проверка наблюдаемого свойства, row требует пригодной таблицы |

Реестр идентичен именам/вариантам публичных схем, но **не утверждает их готовность**. Неизвестный tool/action или лишнее поле — rejected до первого шага. Запретить action=open_cell_value, попытки восстановления посредством неизвестной команды и произвольные расширения JSON. Поддержку действий с таблицами и click_group не выводить из доступности базового tool.

Внутренний capability key — `(tool, action-or-property, variant, source_kind)`. Для обычного ввода variant=scalar; для select — list/selection_table; для click — button/group; таблицы различают collection/dynamic_list/tree. Если вид цели ещё неизвестен, требование остаётся целевым runtime-условием, но preflight обязан подтвердить хотя бы одну разрешённую ветвь и пометить остальные как запрещённые. Runtime не вправе использовать неподтверждённую ветвь. Запрос только табличной ветви при недоказанной идентичности/охвате блокируется целиком.

Каждая capability поступает из доверенного адаптера реестра реализации/доказательств: `supported/unsupported/unknown`, версия реализации, платформа/режим, ограничение источника, причина и ссылка на свидетельство. Отсутствие записи = unknown, никогда true. Нельзя вписать supported в шаблон. При отсутствии поставщика capabilities preflight не выдаёт ready. Новая проверка платформы в 11.1 не выполняется; прежние доказательства используются с их прежними границами.

## Контекст запуска и полномочия

Контекст создаётся доверенной стороной из выбранного текущего канала и сеанса: owner/consumer_id, channel_id, base_id, profile_id, session_id и поколение, manager_mode, подтверждённая готовность API, версия реализации/платформы/режим, capabilities с ревизией, разрешённый policy_id/мутации/цели данных, политика подтверждения, observed_at/expires_at. Он хранится отдельно от переносимого шаблона. Подставлять эти поля из parameters запрещено.

Все шаги относятся к одной базе и владельцу. Значения ссылок/навигации не дают права перейти в чужую базу; область ссылок проверяется после параметризации. Точные правила данных предоставляет действующая политика: preflight не пытается вывести права из имени объекта или текста кнопки. Неразрешимая принадлежность ссылки/цели — blocked/data_scope_unproven. Разрешение общего test_* вызова не равно разрешению всех побочных бизнес-эффектов конкретной кнопки.

Шаблон ui_write требует явного разрешения мутаций в контексте. read_only отвергает test_open/input/action, select/add/fill/delete и любое allow_navigation=true; неизвестная классификация эффекта — blocked. test_expect и inspect не считаются средством подготовки/изменения формы.

## Полный preflight до первого действия

Две фазы одного полного контроля: **весь план до старта** и обязательные **предусловия шага непосредственно перед вызовом**. Preflight не кликает, не открывает формы, не активирует окно и не завершает редактор для проверки следующего шага.

1. **Декодирование/бюджет:** JSON-объект, версия, отсутствие дублей/неизвестных полей, ограничения размера/глубины/числа шагов. Неверный последний шаг не допускает запуск первого.
2. **Весь шаблон:** уникальные step_id, разрешённые tool/action, переносимые селекторы, отсутствие исполняемого текста/временных идентификаторов, политики ошибок и конечные бюджеты. draft не исполняется.
3. **Все параметры:** полные объявления и значения/default, отсутствие лишних/необъявленных/несуществующих ссылок, точные типы, однократная подстановка. Проверяются ссылки даже в последнем шаге. Вся совокупность материализованных команд проверяется существующим valid_request с временными служебными ID; эти ID не отправляются и не создают lifecycle-операции.
4. **Весь контекст/область:** владелец, канал, та же база, профиль/сеанс/поколение, ready, срок контекста, политика данных и разрешённые эффекты каждого шага. Истёкший/неподтверждённый контекст блокирует старт. Разрешение подтверждения не подменяется флагом reviewed.
5. **Все capabilities:** каждый шаг/вариант сопоставляется с явной поддержкой нужной среды и источника; unknown/unsupported блокируют старт. Параллельно строится полный список целевых runtime-предусловий для каждого шага. Будущая форма, создаваемая предыдущим шагом, не обязана существовать сейчас; это не разрешение снять её проверку перед вызовом.
6. **Запечатанный план:** digest шаблона + типизированных параметров + контекста/политик/capability revision, список материализованных шагов и их проверок. ready только если нет ошибок/блокеров по всему плану. Сам report не запускает выполнение.

Ошибки собираются детерминированно по фазе, индексу шага и JSON Pointer, максимум 100; `errors_truncated=true` не означает, что непрочитанный остаток проверен. При превышении общего бюджета возврат rejected, dispatch_count=0. Можно прекратить сбор подробностей, но нельзя выдать ready по частично проверенному документу.

Перед **каждым** действием runner повторно проверяет: неизменность запечатанного плана и владельца/базы/сеанса/поколения/политики; достаточность capability для фактически найденного типа; актуальную уникальную цель, её видимость/доступность с предками, режим редактирования и табличную идентичность/coverage при необходимости; действующее подтверждение. Это проверки штатного исполнителя, не новый наблюдатель. Отказ после начала сценария не отменяет уже выполненные шаги и не запускает их снова.

### Отчёт preflight

Обязательные поля: `version:1`, `status` (`ready/rejected/blocked`), `scenario_id`, `revision`, `template_digest`, `parameters_digest`, `context_digest`, `plan_digest` (null если нет ready), `checked_steps`, `total_steps`, `issues`, `issues_truncated`, `runtime_checks`, `expires_at`, `dispatch_count:0`.

17.11.2026: необязательная секция draft `recording_review` сохраняет исходные события и обязательства композиции активизаций; точный формат — [дополнение 11.2](uilog-import-fix.md) и синхронные JSON Schema. При наличии секции допустим только state=draft; preflight добавляет blocked/recording_requires_review. Переключение state без разрешения композиции не допускается. Это ограничение импортированного черновика, не новое исполняемое действие.

Issue: `{code, phase, step_id|null, path, detail_code}`; без сырых значений/BSL/секретов. Коды rejected: invalid_json, unsupported_version, invalid_shape, unknown_step, invalid_arguments, duplicate_step_id, unknown_parameter, missing_parameter, parameter_type_mismatch, invalid_parameter_reference, forbidden_runtime_binding, unsupported_error_policy, input_budget_exceeded. Коды blocked: draft_requires_review, context_unavailable, context_expired, session_not_ready, owner_mismatch, base_mismatch, data_scope_denied, data_scope_unproven, capability_unknown, capability_unsupported, approval_unavailable. Rejected имеет приоритет над blocked; все обнаруженные причины сохраняются до лимита.

Digest = SHA-256 канонического UTF-8 JSON (`sort_keys=true`, `ensure_ascii=false`, без пробелов вне строк); не логировать digest секретов и параметры отдельно от защищённых артефактов. Срок ready не дольше срока самого раннего свидетельства контекста/capability. Изменение любого шага/параметра/контекста аннулирует ready, требует полного нового preflight. Старый report из другого владельца не переносится.

## Политики ошибок и идентичность исполнения (для 11.3)

`on_error` обязателен: `stop` либо `continue_observation`. По умолчанию импортёр ставит stop. continue_observation допустим только для read-only inspect/expect и table.read/find с allow_navigation=false; после ошибки пропускаются все последующие мутации, выполняются только независимо разрешённые наблюдения. Изначально весь последующий хвост всё равно проходит preflight; политика не позволяет спрятать неизвестный шаг. Общий результат остаётся failed/partial, не success.

Unknown, обрыв соединения, отказ/истечение подтверждения и потеря контекста всегда останавливают автоматическое продвижение, независимо от on_error. Сбой диагностики отделён от execution/verification исходной команды. Rollback/повтор UI-действия не подразумевается.

scenario_id/step_id — ID шаблона; run_id — новый ID явного запуска; step_execution_id — ID исполнения конкретного шага данного run. request_id детерминирован для пары run_id/step_execution_id, связан с operation_id существующего lifecycle. Повтор доставки той же пары/аргументов получает прежний результат, новая пара не использует старый результат. Те же ID с изменёнными аргументами отвергаются; истёкшая/потерянная запись не разрешает молча повторить действие.

Новый набор параметров = новый run_id и полный preflight. Unknown разрешается только сверкой текущего состояния и явным решением пользователя с проверенными предусловиями; факт unknown в истории не переписывается. Runner сохраняет связи в существующих артефактах/сводке общего lifecycle; отдельный исполнительный журнал, launcher и транспорт не добавляются. Само хранилище этих связей и тест восстановления относятся к 11.3.

## Примеры и границы проверки 11.1

JSON Schema проверяет переносимый контейнер и форму ссылок. Она **не заменяет** valid_request, проверку связности параметров, capabilities, политики данных и доверенного контекста. В examples для каждого случая отдельно указаны schema_valid и ожидаемый итог полного preflight; семантические итоги проверены разбором правил, не выдаются за выполненный runtime-preflight.

Покрыты: положительный нетабличный сценарий, неизвестная версия, неизвестный последний шаг, лишний BSL, несуществующая ссылка параметра, неверный тип значения, duplicate step_id, неизвестная/отрицательная capability, чужая база, запрещённая область записи, ошибочная политика продолжения, draft, смена поколения, неоднозначная цель точного селектора, отсутствие наблюдателя для табличной ветви и частичное выполнение/unknown. Положительный пример использует синтетически подтверждённый контекст, не объявляет готовой новую платформенную комбинацию.

Автоматическая проверка: `python -B tests/test_client/check_scenario_contract.py` — **20/20 случаев структурной схемы**, из них для **14 случаев** дополнительно проверена форма материализованных публичных запросов. Не складывать эти перекрывающиеся числа. [Отчёт](evidence/scenario-contract-review.json) отдельно фиксирует, что семантический/runtime-preflight не исполнялся. Ошибка последнего tool/action подтверждена валидаторами; запреты capabilities/области данных/продолжения зафиксированы как семантические ожидаемые результаты для 11.3. Проверка работает без транспорта и отправки команд.

Проверки исходников подтверждают только действующие имена/формы test_* и владение общим lifecycle. Новые запросы к 1С, сборка EPF, повтор старых проверок и рабочая установка в 11.1 не нужны. Следующий шаг — 11.2: импорт uilog в draft с диагностикой неподдержанных событий. Исполнение и проверка восстановления — 11.3. Все незавершённые пункты остаются открытыми.

Необязательное поле шага `finish_focus` содержит `selector` (точные name, type=field, необязательный title) и `same_form: true`. Только test_input/text; runtime ID, ссылки параметров и произвольные поля запрещены. При подготовке плана условие материализуется в необязательный params.finish_focus публичного test_input/text; конфликт условия шага и параметра отклоняется. Старые шаги и вызовы без условия совместимы.

Для композиции activate/inputText/activate импортёр переносит селектор последнего события в finish_focus; запись всех трёх событий/обязательства recording_review сохраняются. Preflight сверяет условие с последним событием композиции: удаление или изменение условия при сохранённом ревью даёт finish_focus_review_mismatch. Снятие recording_review требует авторского ревью; оно само по себе не разрешает удалить смысл события.

Требуемый runtime-контракт: до первой активизации/ввода однозначно разрешить исходное поле и цель в той же живой форме, проверить доступность, получить фактически выбранную драйвером цель завершения и сравнить **нативные ссылки**. Несовпадение/неоднозначность/недоступность останавливает шаг до мутации. Выбор и проверка должны выполняться внутри того же вызова исполнителя; внешняя проверка inspect не исключает смену состояния между вызовами. После завершения проверить, что текущий элемент равен сохранённой цели. Блокирующий диалог, потеря формы или несовпадение после ввода не означают успех и не разрешают повтор ввода; нужен результат с указанием возможной мутации. Заголовок со звёздочкой не является идентификатором формы.

**Реализовано 17.11.2026.** Менеджер проверяет условие до activate, после finish_edit сравнивает текущий элемент с сохранённой нативной ссылкой. До ввода несовпадение даёт failed/finish_focus_mismatch с execution=not_started и completed_steps=[]; после ввода — failed/finish_focus_mismatch, execution=invoked, сохранённые completed_steps и after_confirmed=false. Неудачное чтение обрабатывается общим отказом, без повтора. Блокирующее окно по прежнему правилу останавливает finish_edit. В data.finish_focus возвращаются before_confirmed/after_confirmed.

Для плана требуется отдельная capability `test_input:text:finish_focus:none` с доказательством, привязанным к implementation_revision/platform/mode. Обычная scalar capability не разрешает guarded input. Условие входит в материализованные arguments, command_scope и digest плана; runner отправляет его без отдельного окна между проверкой и исполнением. Draft/recording_review по-прежнему блокируют запуск; локальная reviewed-производная создаётся явно после ревью и со свежим контекстом. [Проверка реализации](finish-focus-runtime.md).
