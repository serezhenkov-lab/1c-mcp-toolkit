# TASK-013 — клиентский исполнитель, 13.11.2026

## Реализация и границы

В служебной форме добавлены последовательная очередь UI, строгая проверка аргументов,
селекторы окна/элемента, ID с проверкой живого объекта, ограниченный обход дерева,
test_open, test_inspect (windows/tree/values/messages) и test_expect.
Основная форма предоставляет внутренний клиентский адаптер с callback конечного результата.
Незавершённое ожидание отдаёт управление платформе; status читает локальное состояние.
Изменяющее действие open вызывается один раз; execution отделено от verification.
При ошибке наблюдения сохраняется последний полученный снимок, если он есть.

Публичная регистрация, разрешения, анонимизация и общий реестр операций относятся
к TASK-016. До их подключения транспортный диспетчер явно отклоняет эти команды
как client_context_unavailable. Серверные фоновые задания UI не исполняют.
Рабочая установленная EPF, рабочий proxy и конфигурация тестовой базы не обновлялись.

Адаптированы принципы поиска, дерева, чтения полей и сообщений Answer42:
точное сравнение вместо нормализации/подстрок, явная неполнота вместо пустого массива
после исключения, сохранение панели сообщений, ограниченные шаги ожидания.
Учтены типизированные значения ВидГруппыФормы.Страницы и видимость предков;
поддерево сохраняет эффективную видимость своего корня. Скрытые узлы остаются в поиске.
MIT-уведомление сохранено в `1c/MCPToolkit/licenses/Answer42-MIT.txt`.
WebSocket/Python/RAG инфраструктура донора не переносилась.

По ответу пользователя в TASK-013 включены message и row. Контракт дополнен в
[design.md](design.md), сценарии — в [UI-06](specs/test-client-ui/spec.md).
message проверяет текущий снимок; row читает текущую строку без смены курсора.
Положительное совпадение доказывает наличие; полного обхода таблицы здесь нет.
row/not_equals возвращает incomplete_search. Ответ явно содержит scope=current_row,
complete=false и прочитанные значения. Это ограничение API, а не пустая таблица.

## Выполнение и доказательства

Итоговые отчёты и контрольные суммы сохраняются в `evidence/task013-*`.
Финальный UI-прогон: [46/46 успешных утверждений](evidence/task013-runtime.json).
Регрессия TASK-012: [основной прогон](evidence/task013-session.json),
[восстановление](evidence/task013-recover.json), [обычный режим](evidence/task013-normal.json),
суммарно 32/32. Ручные действия в этих прогонах не потребовались.
Проверяются окна и открытие ссылки; дерево и значения; неоднозначный, отсутствующий,
неверный регистр/path и устаревший элемент; ограничения depth/max_nodes; сохранение
сообщений при повторном чтении; ожидания сообщения и строки; неизменность курсора;
видимость неактивной страницы; readonly/editing; очередь и доступность status;
нулевое ожидание, тайм-аут и достижение условия после изменения значения;
закрытие окна, пересоздание формы, неизвестный параметр и чужой session_id.

Платформенный CheckConfig: ThinClient, Server, HandlersExistence; затем сборка EPF.
Python: 24 теста unittest успешны; зависимости использованы из `.local/task012/python-deps`.
BSL LS проверяет оба изменённых модуля. В основной форме остаются 752 Error,
совпадающие с baseline TASK-012 по коду диагностики и строке исходника; новых нет.
Это findings, не «чистая статика». Окончательный драйвер проверен отдельным анализом.
Окончательный драйвер: [300 диагностик, Error=0](evidence/task013-static.json).
Основные замечания — несколько операторов на строке, длина строк, сложность и описание
параметров. QueryParseError относится к WQL, ExternalAppStarting — к проверенному
локальному запуску; два UnusedLocalVariable — намеренная проверка живого API-объекта
чтением его свойства. [SHA-256 исходников и тестовой EPF](evidence/task013-sha256.json).

В промежуточных прогонах исправлены: запись в системное свойство ИмяФормы,
сравнение имён типов через строковое представление, сброс значений по умолчанию
выходным аргументом Свойство, канонический URL формы, получение текста исключения
в контексте обработчика, тайм-аут неполного обхода и видимость неактивной страницы.
Неуспешные промежуточные прогоны не считаются приёмкой.

клиент-серверная база, 8.3 и пользовательская бизнес-приёмка остаются вне этого протокола.

проверены управляемые лимиты depth и max_nodes на реальном дереве.
Остановка менеджера не превращает неподтверждённое действие в успешное.

Строгая валидация OpenSpec, проверка ссылок протокола, git diff --check и сверка
исходников с тестовой копией (за исключением явной инструментализации) успешны.
