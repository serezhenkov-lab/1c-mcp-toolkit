# TASK-016/6.1 — готовность общего lifecycle и защита диспетчера

14.11.2026. **Общий lifecycle не готов, 6.1 остаётся открытым.** Реализована доступная защитная часть: все семь test_* отклоняются в публичном клиентском диспетчере до передачи в параллельный/серверный исполнитель. Новый реестр операций не создавался; локальные проверочные вызовы драйвера не превращены в публичную интеграцию.

## Проверка зависимости

**Дополнение 14.11.2026, после TASK-017/7.4:** [первая реализация общего lifecycle](../rezhimy-podtverzhdeniya-i-izolyatsiya-chatov/lifecycle-proxy-partial.md) уже существует в proxy и проверена native MCP → 8.5.1.1529. Ниже сохранён исходный срез до этой реализации: вывод об отсутствии журнала больше не описывает новый opt-in API, но остаётся верным для legacy-вызовов и неподключённых test_*. Полный 6.1 открыт: передача awaiting_approval/rejected и адаптер test_* не завершены.

Владелец общего lifecycle — [TASK-002 соседнего изменения](../rezhimy-podtverzhdeniya-i-izolyatsiya-chatov/tasks/TASK-002.md). Его шаги 3.1–3.3 открыты. Это подтверждено не только планом, но и текущими исходниками:

- `onec_mcp_toolkit_proxy/command_queue.py`: `_add_command` выдаёт новый UUID на каждый приём; `request_id` внутри params не является ключом дедупликации. `ChannelCommandQueue.wait_for_result` удаляет индекс/состояние после завершения ожидания, в том числе тайм-аута. `set_result` после удаления не принимает поздний результат.
- Диагностический запуск настоящего `ChannelCommandQueue` с фиктивными командами (без отправки в 1С) подтвердил разные ID при одинаковом request_id, принятие изменённых параметров, отклонение позднего ответа и KeyError при обращении после тайм-аута. [Наблюдения](evidence/task061-queue-observations.json). Это проверка отсутствующих гарантий, не успешная приёмка OL-01/OL-02.
- Поиск `request_conflict`/`result_expired` в текущем Python proxy и BSL не обнаружил реализации. BSL исследован через RLM, полный обход 7 модулей без ошибок чтения. Текущие UUID контекстов и operation_id запуска клиента сами по себе не являются устойчивым журналом с дедупликацией и сроком хранения.
- `ПринятьКомандуUI` хранит текущую очередь и callback; повторный приём в этот внутренний интерфейс не заменяет общий lifecycle. Восстановление unknown и сохранение просроченных ключей на уровне общего журнала отсутствуют. Результаты предыдущих тестов unknown относятся к локальному исполнителю.

## Что изменено

Следующее дополнение 14.11.2026: [события подтверждения из 1С](../rezhimy-podtverzhdeniya-i-izolyatsiya-chatov/lifecycle-approval.md) уже реализованы и проверены в общем native API. Утверждение выше об их незавершённости относится к предыдущему срезу. Адаптер test_* не подключён, поэтому 6.1 остаётся открытым.

`ВыполнитьКомандуСУчетомКонтекста` ранее явно отклоняла только test_open/test_inspect/test_expect. Добавлены test_session/test_input/test_action/test_table. Сохранены существующий формат `success=false/error` и `client_context_unavailable`; проверка разрешений перед этим отказом сохранена. Изменение закрывает путь этих четырёх групп в общий серверный dispatch, пока нет поддержанного адаптера lifecycle. Оно не добавляет status, дедупликацию, хранение результатов или новый публичный контракт.

## Стендовая проверка

8.5.1.1529, тонкий клиент Windows, ApiProbe, отдельная `.local/task043/db`. Новая копия `.local/task061/gate`, неизменённая InputFixture.epf. Подготовка: `prepare_runtime.py --lifecycle-gate`; сборка штатным epf-build, запуск run_runtime.ps1 с явной тестовой базой.

**23/23**: семь групп × первый запрос/повтор/изменённые параметры, отсутствие обращения к fallback и сохранение готового тестового сеанса. [Runtime](evidence/task061-gate-runtime.json). Тест вызывается через настоящий клиентский диспетчер основной формы, а не HTTP: три транспортных маршрута остаются 6.2. В одноразовой копии fallback снабжён счётчиком и исключением; итоговый счётчик равен нулю. Все запросы отказаны до исполнения — это не подтверждение повторного получения уже выполненной операции и не проверка request_conflict.

Платформенные ThinClient/Server/HandlersExistence и сборка успешны. Дополнительный `unittest discover -s tests -p test_file_transport.py` не выполнил тесты из-за отсутствующего модуля ahocorasick в текущем Python; не засчитан. Код Python транспорта в этом поручении не менялся.
