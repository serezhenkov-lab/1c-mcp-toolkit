# Очередь 2 — промежуточный прогресс общего lifecycle

16.11.2026. Реализована доступная часть 8.3: прогресс UI-операций до окончательного результата. Общий владелец и существующий журнал сохранены. Наблюдатель не подключён, анонимизация отложена, рабочая установка не обновлена. Формальные 13/42 и все открытые пункты сохранены.

## Контракт

Исполнитель менеджера сообщает `lifecycle_event=progress`, `lifecycle_seq=3..100000` и ограниченный `progress`. Прежние awaiting_approval/1 и running/2 сохраняются. Владелец объявляет поддержку в доставляемой команде `lifecycle_progress_version=1`; без неё новая EPF не публикует новые события. Это существенно для старого файлового моста, который не умеет разобрать новый event. Версия основного lifecycle остаётся 1.

Публичный `test_session(action=status, params.operation_id=...)` возвращает в `data.operation.data.progress`:

| Поле | Значение |
| --- | --- |
| operation_id | ID исходной операции, добавляет владелец |
| sequence | Последний принятый номер события |
| scope | intermediate_snapshot |
| phase | executing, waiting или observing |
| completed_count | Целое 0..1000000; число подтверждённых примитивных шагов, не процент готовности |
| elapsed_ms | Целое 0..86400000; время от начала UI-операции |
| last_confirmed_step | null при count=0; иначе activate, open_choice_list, select_choice, toggle_check, clear, input_text, finish_edit, action, add или open |

Произвольные строки UI и неизвестные поля не принимаются. Это ограничение новой схемы, а не реализация отложенной анонимизации остальных результатов. Прогресс публикуется после разрешения, подтверждённого шага и между проверками условия ожидания. При неизменных phase/count частота ограничена одним событием в секунду; смена фазы/счётчика публикуется сразу. Процент готовности не вычисляется. Короткая операция может завершиться раньше первого чтения status; получение каждого события не гарантируется.

Снимок относится к UI-командам драйвера. Для start/stop/restart остаются прежние состояния, отдельный числовой прогресс их фаз не заявляется. Чтение status не исполняет UI повторно. При count>0 нетерминальный публичный конверт сообщает execution=invoked; у unknown остаются execution=unknown и verification=not_confirmed.

## Хранение и отказы

- SQLite расширен полями progress/progress_bytes, миграции независимы; замена снимка учитывается в общей квоте. Только running/awaiting_approval принимают прогресс. Повтор идентичного номера не пишет снова; устаревшие события и уменьшение count/elapsed отвергаются. Итог исключает собственные байты прогресса из проверки квоты и удаляет снимок.
- Embedded сохраняет копию структуры в существующей записи. Проверка выявила и устранила ошибку: первоначально сохранённая ссылка позволяла вызывающему коду изменить уже принятый снимок. Запись прогресса прекращается при приближении журнала к 56 MiB с запасом 4096 байт, до прежнего предела финальной записи 60 MiB. TTL/компактация удаляют просроченный прогресс.
- Перезапуск без окончательного результата сохраняет unknown и последний снимок. Поздний прогресс не возвращает unknown/terminal в running. Чужой канал не получает запись. Промежуточные данные не заменяют terminal_snapshot итоговой диагностики.
- HTTP передаёт событие существующим callback; file bridge использует существующий lifecycle-файл и не освобождает активную команду до окончательного ответа. Второго журнала нет.
- Замеченная исполнителем ошибка отправки даёт diagnostics.progress_delivery_failed; она не повторяет UI и не меняет исход действия. Файловый отправитель не получает подтверждения принятия каждого снимка, embedded может пропустить необязательный снимок по квоте. Прогресс best effort. Синхронный HTTP callback сохраняет прежний timeout 3 с; отсутствие любой задержки при сетевом отказе не обещается.

## Проверки

Стенд: Windows, локальные файловые копии StubConfig, тонкий клиент и отдельный менеджер **8.5.1.1529**, ApiProbe. Рабочая установка не обновлялась. Обычная EPF собрана из исходников с modules,handlers; fault EPF — отдельная тестовая копия.

| Проверка | Результат |
| --- | --- |
| Python journal, transport, public operations | 62/62; схема, монотонность, дубли, квоты, TTL, изоляция, unknown, неизменность итога, capability |
| REST embedded | 8 проверок длительного ожидания + 3 проверки действия/повтора/счётчика |
| REST HTTP proxy | 11/11 |
| REST file bridge | 11/11 |
| Native MCP, окончательная обычная EPF | По 2/2 на embedded, HTTP и file: промежуточный снимок виден до итога, итог expectation_timeout без progress |
| Владелец без объявления capability | 2/2 на file: прогресс не поступает, окончательный результат доставлен; моделируется старый контракт новым proxy, исторический бинарник не запускается |
| Embedded journal/restart | 7/7: валидация, копия структуры, порядок, чужой канал, unknown с последним снимком, поздний event, защита terminal |
| Искусственный отказ доставки progress | 4/4: действие успешно, счётчик=1, повтор ключа без второй мутации, явная диагностика |

На длительном REST ожидании наибольшее время status в выборке: embedded 0.551 с, HTTP 0.156 с, file 0.024 с. Это замеры локального стенда, не SLA. Ожидание несколько секунд дало несколько возрастающих sequence/elapsed_ms до финального отказа по условию.

Первый embedded REST прогон содержал ошибку проверки: harness искал значение поля в tree, где его нет. Первые 8 проверок прогресса приняты; критерии действия отдельно перепроверены через test_expect(value=1). Ошибка сохранена в initial-results. Первичная owner-проверка воспроизвела дефект ссылки; после LifecycleКопия все 7 прошли. Эти неуспешные прогоны не объявлены успешными. Обычные REST/fault прогоны предшествовали завершающей проверке capability; native MCP на всех маршрутах выполнен на итоговой EPF после обоих исправлений.

BSL LS проверил оба изменённых модуля: 7344 диагностики, 752 Error в существующем основном модуле, 0 Error в драйвере, 0 Error на строках правок относительно сохранённых исходников начала этапа. Это сравнение изменённых строк, не объявление чистоты всего проекта. Сборка платформы с modules,handlers успешна.

Сценарии: tests/test_client/run_intermediate_progress.py, run_progress_owner.py, run_progress_mcp.py. Они используют общие helpers run_queue1_finish/run_lost_response, требуют подготовленных .local/progress/<route>/db и обычной Fixture.epf; существующие results.json защищены от перезаписи. --legacy-owner только у MCP file; --fault только у отдельной fault-копии. Доказательства: [сводка](evidence/intermediate-progress-runtime.json), [архив](evidence/intermediate-progress-runtime.zip).

## Оставлено открытым

8.3 не закрыт: анонимизация отложена, полная транспортная/клиент-серверная/RDP матрица и полные UI-снимки before/after не подтверждены. Остаток 8.2/6.4, идентичность строк и очередь 1 сохраняются в [единой сводке](queue2-current.md). Наблюдатель и Открыть() в этот этап не включены. Промежуточный прогресс больше не является техническим блокером очереди 2 на проверенном локальном стенде.
