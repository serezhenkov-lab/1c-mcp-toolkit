# TASK-019 / 9.1 — решение об идентичности строк

## Решение для встроенного HTTP от 19.11.2026

Для HTTP выбираем отдельный внутренний обмен «забрать пробу / вернуть снимок» через действующий loopback-слушатель Toolkit. Менеджер создаёт ограниченную пробу, сохраняет идентификатор родительской операции и возвращает управление платформе. Клиентская роль той же EPF забирает пробу коротким исходящим запросом, читает форму в своём процессе и возвращает результат. Менеджер продолжает наблюдение отдельным шагом. Синхронное ожидание ответа внутри UI-вызова заблокировало бы обработку обратного события в клиентском коде менеджера. Основания — [обработчик события формы](../../../1c/MCPToolkit/MCPToolkit/Forms/Форма/Ext/Form/Module.bsl#L20536), [регистрация маршрутов компоненты](../../../native_components/MCPHttpTransport/src/http_transport.cpp#L66) и [прежняя проба идентичности](row-identity-851.md).

- Внутренние запросы распознаются отдельно от публичных MCP/REST-инструментов и очереди UI. Роль выдаётся только явно запущенному собственному клиенту. Привязка включает сеанс Toolkit, подтверждённый PID с моментом запуска, поколение наблюдателя и одноразовый секрет bootstrap. Секрет передаётся локальному процессу по защищённому от чужого доступа bootstrap, исключается из URL, командной строки и диагностических данных.
- Проба ограничена чтением разрешённых форм, элементов и коллекций. Проверяются срок, привязка и размер результата. `probe_id` коррелирует единственный снимок с исходным `operation_id`; просроченный или чужой ответ отбрасывается. При обрыве чтения менеджер возвращает неполное наблюдение. Принятая мутация остаётся под управлением действующего журнала, повторное чтение не запускает её заново.
- Первый допуск проверяется для `ДанныеФормыКоллекция` с отдельным сигналом смены источника. Пара UUID формы и ID строки недостаточна: новая коллекция может повторить ID. До и после чтения должны совпасть привязка, форма, таблица и поколение источника. Токены строк отзываются при смене источника, пересоздании формы, потере связи и перезапуске роли. Сортировка требует отдельной проверки актуальности позиции. Для динамических списков и деревьев собираются отдельные доказательства.
- Операция позиционирования выполняется существующим TestManager API. Даже согласованный снимок не устраняет окно между чтением и действием. Для записи требуется подтверждение той же строки перед действием и проверка наблюдаемого результата. При невозможности связать наблюдение со строкой действует `incomplete_search` по [UI-08](specs/test-client-ui/spec.md#requirement-ui-08-идентичность-строки-независимо-от-её-текста).

Файловое решение ниже описывает отдельный маршрут. HTTP-вариант переиспользует границы этого контракта, общую EPF и владельца операции. Встроенный сервер сегодня обрабатывает публичные `/mcp`, `/api/*` и `/health`. Внутренний обмен и клиентская роль остаются работой 9.2.

## Решение для файлового транспорта от 16.11.2026

16.11.2026. Статус: архитектурное решение зафиксировано без внедрения по текущему поручению. Это не согласие на 9.2, не готовый API и не новая runtime-приёмка. Отсрочка подключения сохраняется; незавершённые отметки не закрыты.

## Решение и отвергнутые варианты

Выбран **ограниченный read-only наблюдатель ДанныеФормыКоллекция в отдельной роли той же EPF Toolkit**, запускаемый в тестируемом клиенте только по отдельному поручению. Основная конфигурация/расширение не изменяются; отдельная native DLL, сервис и произвольный клиентский BSL не вводятся. Менеджер остаётся единственным UI-исполнителем, общий lifecycle — единственным владельцем операции.

Наблюдатель не заменяет штатное UI-действие присваиванием реквизита или прямым вызовом обработчика. Он не принимает текст кода, имя вызываемого метода, произвольный путь реквизита, запрос к базе, сценарий, команду ОС. Новая роль не должна регистрировать execute_code/execute_query и прочие команды обычного Toolkit. Отказ прав не обходится повышением привилегий.

Не выбраны: текст строки/хеш ячеек, порядковый номер, число выделенных, повторный ПерейтиКСтроке, изменение скрытого реквизита-маркера. Прототип даёт прямые контрпримеры первым внешним эвристикам. Extension/правки основной конфигурации и полный клиентский executor выходят за выбранную границу.

## Что действительно доказано прототипом

Сверены исходники tests/test_client/native_row_observer.bsl, row_identity_probes.bsl, prepare_row_identity_probe.py и verify_row_identity_probe.py; все четыре SHA-256 совпадают с сохранённым манифестом. [Исторический протокол](row-identity-851.md) и 12/12 verified относятся к прежнему runtime, не повторялись.

| Свойство | Основание | Предел |
| --- | --- | --- |
| UUID реальной формы и текущий native row ID | ПолучитьОкна/Содержимое, УникальныйИдентификатор, ТекущаяСтрока | Подтверждено на форме fixture |
| Одинаковые тексты, разные строки | IDs 0 и 1, повторное чтение стабильно | Не ключ любой таблицы/базы |
| Перестановка | [0,1] → [1,0] | Не полная проверка визуальной сортировки |
| Удаление/добавление/очистка | [0,2], затем [3] | Не доказывает отсутствие повторного ID после замены источника |
| Внешние обход/выделение | ПерейтиКСтроке включает текущую; выделение имеет контрпример | Не основание row_id |

**Прототип не переносится как наблюдатель:** он обменивается результатом через поле/кнопку fixture и содержит исследовательские move/delete/clear/add. Эти способы и мутации исключены из выбранного read-only контракта. Чистый снимок чужой формы, изоляция, доставка, смена источника и атомарность ещё не проверены.

## Доставка и владение

- Пакет — та же EPF с отдельным внутренним режимом row_observer; версия/роль проверяются до readiness. Обычный режим сервера не включается как fallback. Загрузка только в явно выбранный собственный тест-клиент; при attach без отдельно подтверждённого наблюдателя capability остаётся unavailable/unverified.
- Повторно используется файловое оформление существующего транспорта: current.json/session.json, атомарная публикация, request → running → response, проверка channel/session/deadline и отсутствие повторного исполнения .running. В проекте это file_transport.py и файловый цикл основной формы. **Сегодня кода связи manager→observer нет**; 9.2 должен выделить/переиспользовать общий IO-код, а не копировать второй протокол.
- Нельзя посадить менеджер и наблюдателя двумя читателями одного каталога: команды будут украдены другим потребителем. Нельзя послать probe в ту же занятую очередь file bridge: текущая active-команда допускает только управляющий restart. Поэтому внутренний endpoint наблюдателя имеет отдельное пространство роли/сеанса; это существующий файловый транспорт с выделенным потребителем, не второй публичный канал выполнения.
- Менеджер — производитель внутренних read-only probe, наблюдатель — единственный потребитель. Внешние MCP/REST маршруты и родительский operation_id не меняются. Для correlation допускается probe_id, но самостоятельного долговечного operation journal/новой пользовательской операции не создаётся. Результат probe входит в результат родителя и следует его TTL/квотам/изоляции.
- Bootstrap связывает канал, session_id/поколение, базу, фактический PID+CreationDate клиента, роль/версию и одноразовый секрет. Секрет не передавать в URL, argv или обычный лог: только в ограниченно доступном bootstrap-файле. Проверка доступа/неподменяемости каталога обязательна; один UUID пути не считается авторизацией. Недоступный безопасный общий каталог — отказ готовности, не новый HTTP-сервер.
- Для клиент-серверной базы IO выполняется на клиентской машине рядом с обоими процессами, не в server_host. Для RDP перенаправление диска само по себе не подтверждает изоляцию/атомарность; нужна отдельная проверка. Частичный запуск не обещает полную матрицу.
- Detach/restart/потеря связи/смена consumer или формы отзывают binding и все токены. Поздний ответ старого probe не возрождает session и не переводит unknown в success. UI не повторяется; необязательный read-only probe может быть выполнен заново только как новое наблюдение, без продолжения старой мутации.

## Идентификаторы и охват

Внешний row_id — непрозрачный случайный токен реестра, а не индекс/native ID/текст. Внутренняя привязка: channel + session epoch + UUID формы + токен конкретной таблицы + source epoch + native row ID + snapshot ID. Реестр — отзывной кэш целей, не журнал операций. Объект source должен быть подтверждён отдельно от имени реквизита. Повторная выдача токена не обязана сохранять строковое значение row_id между снимками; недопустимо переиспользовать прежний токен для другой строки.

Source epoch меняется при доказанной замене/перезагрузке источника, форме, переподключении, observer restart. Его нельзя вычислять из количества строк/ID/значений: замена источника может вернуть тот же native ID. Если надёжное обнаружение замены источника для конкретной формы не доказано, capability этой привязки не включается. Успех очистки/добавления в прототипе не снимает этот допуск.

| Источник | Начальная граница |
| --- | --- |
| ДанныеФормыКоллекция | Возможен нативный снимок доступной коллекции формы после проверки binding/epoch/ID |
| ДинамическийСписок | Неподдержан первой реализацией; ключ/выборка/подгрузка и версии отдельно |
| ДанныеФормыДерево | Неподдержано; путь/родитель/идентичность узла отдельно |
| ТабличныйДокумент, неизвестный источник | Явное ограничение; номера строк не становятся ID |

Полная коллекция формы не равна полному набору базы или отображаемому отфильтрованному/сортированному UI. coverage разделяет source_collection и rendered_rows; пока соответствие не доказано, визуальная полнота и отсутствие строки не подтверждаются. Усечение/бюджет → complete=false. Сборка словаря по текстам или удаление дублей запрещены.

## Ограниченные операции и целостность

Проект внутреннего контракта v1: handshake, snapshot_collection, validate_binding, release. Только зарегистрированные токены формы/таблицы и разрешённые имена колонок, не входной dotted path к любому реквизиту. Ответ содержит snapshot_id, binding epoch, источник/охват, current native ID и список разных row token с типизированными доступными данными/причинами недоступности. Этот контракт внутренний, семь публичных test_* не расширяются этим документом.

Снимок идентичности и относящихся к нему значений собирается в **одном клиентском обработчике**, без ожидания/навигации/вызова пользовательских обработчиков/возврата в event loop. Лимиты наследуют родительский запрос и действующие пределы строк/колонок/байтов; превышение даёт явную неполноту. Разбивка на несколько обработчиков не считается одним атомарным снимком без отдельного доказательства revision.

Два внешних чтения ID «до/после» недостаточны: A→B→A между ними оставляет одинаковые конечные ID. Поэтому нативные токены нельзя приклеить к уже собранным менеджером ячейкам и объявить values_verified=true. Если согласованность отображаемых значений внешнего API и нативного снимка не доказана, возвращаются incomplete_search/identity unavailable; диагностические значения не являются подтверждением условия UI.

**Проверка перед мутацией не атомарна с последующим внешним UI-вызовом.** Снимок или validate_binding не блокирует пользовательские/фоновые изменения между процессами. Read-only наблюдатель сам по себе не решает этот разрыв. До runtime-доказательства безопасного условного позиционирования и однократного штатного действия capabilities изменения/выбора не включаются. Нельзя устранить разрыв прямым присваиванием значения, вызовом прикладного обработчика или повтором действия после несовпадения. Если это потребует расширения роли наблюдателя, сначала отдельное архитектурное решение, а не скрытое расширение 9.2.

Публичные отказы сохраняют текущие категории: непроверенная/неподдержанная возможность — unsupported_operation до действия; недостаточная идентичность/целостность — incomplete_search; отозванная известная цель — stale_target. Новые диагностические reason не заменяют существующие error codes. Совпадение строк не меняет verification.

## Допуск к 9.2 и зависимым задачам

| Проверка | Текущее знание / необходимый результат |
| --- | --- |
| Дубли и перестановка | Историческая fixture подтверждает основу; не повторять без изменения механизма |
| Реальная визуальная сортировка | Нужны разные значения и доказанный visual mapping; прежняя сортировка одинаковых текстов недостаточна |
| Полная замена источника с теми же значениями/ID | Новый epoch, старые row_id отозваны; сейчас не доказано |
| Пересоздание формы, detach/restart | Новый UUID/epoch и отказ прежним токенам; сейчас не доказано |
| A→B→A между внешними чтениями | Не выдавать подтверждённую целостность; нужен единый снимок/revision |
| Сбой/таймаут/чужой канал/неверная роль/поздний ответ | Без выдачи данных и без второго исполнения родительского UI |
| allow_navigation=false | Ни cursor, ни selection, ни фокус не меняются |
| Позиционирование + действие | Отдельное доказательство отсутствия TOCTOU, readback и запрета повтора; ID недостаточно |
| Частичная коллекция, список/дерево | Явный охват и ограничение, не full-table success |

Отдельное поручение на подключение необходимо даже после этого решения. Capability включается по операции/типу источника/версии/конкретному проверенному binding, не общей галкой «есть наблюдатель». До этого 4.1/5.1–5.3 остаются открытыми; 1.4/click_group/open_cell_value не получают подтверждения от ID строк.
