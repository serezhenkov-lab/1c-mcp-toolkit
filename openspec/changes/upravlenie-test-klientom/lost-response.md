# Очередь 1: потеря ответа после UI-записи — 16.11.2026

Сценарий TI-01 «Потерян ответ после записи» подтверждён на файловой **8.5.1.1529** для трёх маршрутов: HTTP proxy, локального файлового моста и embedded HTTP. После потери ответа три одинаковых запроса возвращают первоначальную успешную операцию, кнопка повторно не нажимается и исходный документ остаётся один. **Production-код не изменён**, незавершённые пункты и 13/42 отметки сохранены. Наблюдатель не подключён, анонимизация отложена, рабочая установка не обновлялась.

## Стенд и точка отказа

Три отдельные копии `.local/lost-response/{http,file,embedded}/db`, Windows, тонкие клиенты 8.5.1.1529, пользователь ApiProbe. Production EPF скопирована из проверенной сборки предыдущего этапа, SHA-256 сборки и соответствующих исходников проверены до запуска. Конфигурации баз не изменялись: используется уже существующий документ `T43_Required`. Профиль настраивается штатной командой формы через существующий `execute_code`, без startup-вставок в Toolkit.

| Маршрут | REST endpoint | TESTCLIENT | Проверки |
| --- | --- | --- | --- |
| HTTP proxy | 127.0.0.1:17669 | 16549 | 20/20 |
| Локальный file bridge | 127.0.0.1:17670 | 16549 | 20/20 |
| Embedded HTTP | 127.0.0.1:17671 | 16549 | 20/20 |

Прогоны последовательные. Клиент запускается отдельно с тестовой внешней обработкой `permission_fixture`, менеджер подключается публичным `test_session/attach`. Соответствие базы проверяет существующий драйвер по однозначному `/IBConnectionString`; чтение документов выполняется запросом через менеджер того же стенда. Точный режим подтверждения/анонимизация задаются только для этих тестовых сеансов.

Внешняя обработка содержит кнопку «Диалог», которая при каждом нажатии **создаёт новый объект документа**, заполняет обязательное поле и записывает его. Дедупликации, поиска уже созданного документа или фиксированного уникального номера в обработчике нет. В тестовую копию добавлены только две записи трассы: вход в серверный обработчик и успешный возврат из `Документ.Записать()` с UUID. Это измерение тестовой команды, не клиентский наблюдатель/адаптер Toolkit.

Проверяющий relay на 127.0.0.1:17672 принимает исходный REST `test_action/click` и передаёт его неизменным. Он удерживает первоначальный асинхронный ответ, штатно опрашивает status до `succeeded`, проверяет наличие `committed` в трассе, затем закрывает TCP-соединение вызывающего клиента **без заголовков и тела HTTP**. Клиент получает `RemoteProtocolError`; терминальный ответ не просто игнорируется после получения вызывающей стороной. В `dropped-response.json` сохранены исходный ответ/итог, трасса перед закрытием сокета и SHA-256 тела запроса.

## Доказательства отсутствия повтора

На каждом маршруте выполнены следующие проверки:

1. Поле-маркер заполнено через публичный `test_input`, документ и вызовы обработчика с этим маркером до нажатия отсутствуют.
2. После обрыва соединения независимый запрос к базе находит ровно один документ с ожидаемым маркером, UUID, номером и отсутствующей пометкой удаления.
3. Три повтора с тем же request_id и параметрами возвращают `succeeded` и **тот же operation_id**. В базе остаётся та же единственная ссылка; в трассе ровно `invoked`, `committed` с её UUID.
4. Другие параметры под прежним request_id получают `request_conflict`, не меняя документ и трассу.
5. Положительный контроль: через UI введён отдельный контрольный маркер, затем та же кнопка нажата с **новым request_id**. Создан другой документ с другим UUID и двумя новыми событиями трассы. Исходный маркер по-прежнему относится ровно к одному документу. Это исключает ложный успех из-за неработающей кнопки или подавления повторов самим fixture.

| --- | --- | --- |
| Embedded | `2f01c2f1-6061-408a-9b89-ddcaa543b3b9` | 1 / 1 |
| HTTP proxy | `535a8646-293f-439a-91c3-cfb72a2e8a57` | 1 / 1 |

После остановки стендов read-only проверка SQLite HTTP/file подтвердила по одной записи `(channel, request_key)` с исходным ID, инструментом `test_action` и состоянием `succeeded`. Итог всех проверок HTTP-сценария — **60/60**. Собственные менеджеры, клиенты и proxy завершены; тестовые документы сохранены только в копиях баз для повторной сверки.

## Ограничения и промежуточные попытки

Потерян ответ **вызывающему REST-клиенту после сохранения успешного результата владельцем lifecycle**. Не моделировались потеря ответа между исполнителем и владельцем до фиксации результата, состояние unknown после такого сбоя, потеря файлового response.json, RDP-обрыв и клиент-серверная база. Также это запись кнопкой тестовой внешней обработки, а не новая полная приёмка стандартной формы прикладного документа с исправлением обязательных полей. Полная матрица TI-05, общий lifecycle и пункты 6.1–6.3 остаются открытыми.

Неудачные подготовительные попытки сохранены отдельно; все остановились **до UI-записи**:

- `embedded/attempt1`: скрипт не учитывал `error: null`; исправлена обработка успешного ответа.
- `embedded/attempt2`: самостоятельный запуск клиента через `/F` отклонён существующим строгим сопоставлением базы; запуск приведён к поддержанному `/IBConnectionString` без изменения драйвера.
- `http/attempt1`: учтена существующая JSON-строка результата `execute_code` в proxy.
- `file/attempt1`: attach опередил готовность TESTCLIENT; добавлено ограниченное ожидание порта до запуска проверки, без повторения UI-команды.
