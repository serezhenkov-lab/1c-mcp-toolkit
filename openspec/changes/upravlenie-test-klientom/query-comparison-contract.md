# TASK-020 / 10.1 — контракт сверки результатов запросов, v1

Дата: 16.11.2026. Основание: TE-03, [карточка](tasks/TASK-020.md), [решение](design.md). Это контракт для реализации 10.2, не реализованный компаратор и не протокол выполнения в 1С. Формальные отметки незавершённого плана сохранены.

Последующее состояние: [10.2 реализован и локально проверен](query-comparison-implementation.md). Формулировки ниже о будущем модуле и ручной проверке описывают исходный этап 10.1; нормативные правила v1 сохранены.

## Граница и API

В 10.2 предусмотреть чистый модуль `onec_mcp_toolkit_proxy/query_comparison.py` с функцией `compare_query_results(request: Mapping) -> dict`. Она сравнивает уже полученные данные, не выполняет запросы, не вызывает UI, не повторяет операции и не меняет lifecycle. Нормализация ответа выполняется отдельной функцией адаптера `normalize_query_result(result, context, contract) -> dict` этого же модуля. Здесь функции только специфицированы.

Первый потребитель — существующий тестовый harness. Новый публичный MCP/REST/test_* метод не вводится. Продуктовая интеграция относится к 10.3. Публичные параметры и ответы `execute_query` сохраняются. Адаптер получает структурированный ответ до JSON/TOON-представления с соблюдением действующей обработки данных; обратный разбор человекочитаемого текста не является источником доказательства. Нельзя обходить существующую анонимизацию. Разработка новой анонимизации отложена; несопоставимые преобразования сторон дают `unavailable`.

UI-снимки в v1 не принимаются. Их подключение требует отдельного доказательства целостности/охвата в 10.3 и не следует из готовности query-компаратора. Наблюдатель не требуется и не подключается.

## Что подтверждено исходниками

В `1c/MCPToolkit/MCPToolkit/Forms/Форма/Ext/Form/Module.bsl`:

- `ВыполнитьЗапрос` (3907): возвращает `success`, `data`, при `include_schema` — `schema`; отказ возвращает `success=false,error`. Цикл ограничивает число строк `Лимит`, отдельный признак усечения/полноты не возвращается.
- `СформироватьСхемуРезультата` (3998): имена колонок и наборы платформенных типов; это не обязательно точный тип каждой ячейки.
- `БезопасноеЗначениеДляПередачи` (3559): UUID становится строкой; неопределённое и пустая ссылка теряют различие; глубина вложения ограничена. Сериализованное значение не всегда позволяет восстановить исходный тип.
- `ОписаниеОбъектаПоСсылке` (15957): `_objectRef`, `ТипОбъекта`, `УникальныйИдентификатор`, `Представление`. Представление не является идентичностью ссылки.

В `onec_mcp_toolkit_proxy/mcp_handler.py`: существующий `execute_query` поддерживает `include_schema`; общий обработчик применяет обработку данных до `format_tool_result`. Общие поля `truncated` модели `CommandResult` не доказывают, что именно query-исполнитель их заполнил. Это статические факты текущего checkout, не новая runtime-проверка 8.5.1.1529.

## Вход: обязательные поля

Объект запроса содержит только `version: 1`, `contract`, `expected`, `actual`. Неизвестные поля и версии отклоняются как `invalid_contract`.

`contract` содержит:

| Поле | Правило |
| --- | --- |
| `id` | Непустой ID закреплённого эталона/правил; не operation_id |
| `base_id`, `query_fingerprint` | Ожидаемая база и SHA-256 точного текста запроса вместе с типизированными параметрами; fingerprint формирует доверенный сборщик, не компаратор |
| `schema` | Непустой массив `{name, type, null_policy}`; имена уникальны, регистр значим |
| `mode` | `bag`, `keyed` или `ordered`, без неявного выбора |
| `keys` | Массив имён; непустой только для `keyed` |
| `order_basis` | Для `ordered` непустое описание полного порядка запроса, включая разрешение равных значений сортировки; иначе `null` |
| `ignore_columns` | Массив `{name, reason}`; только существующие неключевые колонки, причина обязательна |
| `data_policy_id` | Версия/контекст одинаковой обработки данных обеих сторон |

`expected` и `actual` содержат `source`, `schema`, `rows`. `schema` имеет тот же формат, что контракт; `rows` — массив массивов типизированных ячеек, в порядке колонок своей схемы. При недоступности источника schema/rows могут быть null: адаптер сохраняет отказ, не создаёт пустой успешный набор. Длина доступной строки точно равна числу колонок. Колонки сопоставляются по имени, а не позиции в схеме. Пропавшая ячейка не равна null.

`source` содержит все поля: `kind` (`baseline` для expected, `execute_query` для actual), `base_id`, `query_fingerprint`, `data_policy_id`, `read_id`, `operation_id` (реальный ID либо null), `started_at`, `finished_at` (UTC ISO 8601), `status` (`success`, `failed`, `unknown`), `coverage` (`complete`, `partial`, `unknown`), `effective_limit` (положительное целое для query; null для baseline), `fidelity` (`exact`, `wire_projection`, `unknown`), `order_proven` (boolean). Для baseline read_id идентифицирует закреплённый артефакт; даты отражают его создание. Для actual — конкретное чтение. Интервал чтения не объявляется транзакционным снимком.

Также обязательно `normalization_error`: null либо один из кодов `ambiguous_null`, `ambiguous_type`, `numeric_precision_unproven`, `unsupported_value`, `schema_unavailable`, `malformed_source`. При таком отказе rows/schema допускают null; на стадии точности он передаётся как причина unavailable, не маскируется общим fidelity_unproven. Поле kind структурно является непустой строкой: неподдержанный источник (включая UI) получает unsupported_source на стадии проверки источника. Некорректные обязательные поля самого контракта/эталона дают invalid_contract; испорченный ответ query преобразуется адаптером в отказ источника.

Контекст базы/чтения и полноту подтверждает доверенный сборщик существующего транспорта. Самостоятельно переданные флаги `complete`/`order_proven` не являются доказательством; будущий публичный вход не вправе принимать их как доверенные. `base_id` — непрозрачная привязка к базе/контексту маршрутизации, не заголовок окна и не строка соединения. Эталон нельзя автоматически переносить в другую базу или перезаписывать фактическим результатом.

Fingerprint: SHA-256 UTF-8 JSON объекта `{query, params}` с сортировкой ключей, без пробелов вне строк, `ensure_ascii=false`. Текст запроса сохраняется точно, параметры заранее приводятся к типизированным значениям этого контракта; имена параметров сортируются, массивы сохраняют порядок. Неоднозначная нормализация параметров даёт `unavailable`. Хеш — проверка соответствия, не средство сокрытия секретов; не публиковать его отдельно от защищённых артефактов.

## Полнота и пригодность

Порядок проверки: структура/правила → источник и привязки → полнота/точность → схема → ключи/порядок → сравнение. При нескольких причинах возвращать первую по этому порядку; внутри стадии — expected перед actual, затем порядок колонок/строк. Не выводить частичный diff, если хотя бы один обязательный вход непригоден.

- `failed` или `unknown` не превращаются в пустой массив. Отсутствие данных — `unavailable/source_failed` или `source_unknown`.
- При текущем исполнителе query доверенный адаптер может подтвердить полноту успешного структурированного ответа только при известном эффективном лимите и `len(data) < limit`, отсутствии иных усечений и целостном получении ответа. `len(data) == limit` даёт `coverage=unknown`, даже если в базе ровно столько строк. `len(data) > limit` — недопустимый ответ источника.
- Дополнительный COUNT в другое время не доказывает целостность исходного чтения. Компаратор не выполняет его автоматически.
- Полнота относится к результату данного запроса с его фильтрами/FIRST, а не ко всем строкам таблицы базы. Оба успешных полных пустых результата равны; ошибка против пустого эталона — недоступность.
- Отличия базы, fingerprint или data_policy_id дают `unavailable/source_mismatch`. Частичный/неизвестный охват — `unavailable/incomplete_source`; UI — `unavailable/unsupported_source`.
- `fidelity=unknown` даёт `unavailable/fidelity_unproven`; `wire_projection` допускается только с явными правилами контракта и отражается в scope. Неизвестное преобразование не считается разрешённой проекцией. Некорректный ответ источника — `unavailable/malformed_source`; даты должны быть валидны, finished_at не раньше started_at. Структуру отказа проверять без требования успешной схемы/строк.
- Несовпадение схемы фактического результата с контрактом даёт `different/schema_mismatch` без построчного diff. Отсутствующая схема/неизвестный тип даёт `unavailable/schema_unavailable`. Самопротиворечивый эталон или неверный запрос компаратора — `invalid_contract`.

## Типы и равенство ячеек

Ячейка — `{type, value}`. Никаких автоматических преобразований строки в число/дату или bool в число.

| type | value и сравнение |
| --- | --- |
| `string` | Строка, точное сравнение Unicode; без trim, смены регистра и нормализации |
| `number` | Конечное десятичное число строкой по грамматике `-?(0|[1-9][0-9]*)(\.[0-9]+)?`; сравнение десятичное: `1` = `1.0`, `-0` = `0`; не binary float |
| `boolean` | JSON boolean, не 0/1 |
| `datetime` | Валидная календарная дата/время `YYYY-MM-DDTHH:MM:SS`, локальная семантика 1С; без угадывания часового пояса |
| `uuid` | Валидный UUID в каноническом формате; регистр hex незначим |
| `reference` | `{object_type, id, presentation}`: заполненная ссылка справочника/документа с проверенным UUID; равенство по базе, точному типу и UUID; presentation — строка либо null, на равенство не влияет |
| `wire_null` | Только JSON null, только если у колонки `null_policy=wire_null` |

В схеме `type` — один из первых шести типов; `null_policy` — `reject` или `wire_null`. `wire_null` в ячейке при разрешённой политике не доказывает, что исходные NULL, Неопределено и пустая ссылка одинаковы. Результат сравнения получает область `wire_projection`, даже если null фактически не встретился. По умолчанию выбрать `reject`; непрояснённый null даёт `unavailable/ambiguous_null`. Значение другого известного типа в корректном фактическом ответе — отличие типа, не неявное приведение.

Адаптер обязан доказать тип по схеме/значению. Объединение типов без однозначного способа различения даёт `unavailable/ambiguous_type`. Для чисел необходимы исходная десятичная лексема/Decimal либо доказанно точное целое; уже потерянная точность float не восстанавливается `str(float)` (`numeric_precision_unproven`). Значения вложенных таблиц/коллекций, произвольных объектов и ссылок перечислений в v1 — `unsupported_value`. Строковый литерал `<max_depth>` остаётся строкой, если доказан исходный строковый тип; строковая подмена неподдержанного объекта не становится корректным значением.

## Режимы, ключи и разрешённые исключения

- `bag`: multiset точных типизированных строк после проекции. Порядок незначим, кратность обязательна. `[x,x]` против `[x]` — один missing. Разные строки не подбираются по сходству: missing + unexpected, без changed.
- `keyed`: ключ составной, сравнивается точно, его колонки не допускают null/исключения. Ключ должен быть уникален на каждой стороне. Дубликат даже полностью одинаковых строк — `unavailable/duplicate_key`; для такой задачи явно выбрать bag. Один ключ и разные неключевые значения — changed. Изменение ключа — missing + unexpected. Порядок строк незначим.
- `ordered`: сравнение по нулевым индексам. Различия в общей части — changed, лишний хвост — missing/unexpected. Вставка в середине может дать несколько changed; поиск похожей строки/LCS не применяется. Требуются `order_basis` и подтверждённый полный порядок обеих сторон, иначе `unavailable/order_unproven`.
- Единственное исключение v1 — явные `ignore_columns` с причинами. Эти колонки обязаны существовать в обеих схемах с согласованным типом, но значения не участвуют в равенстве. Нельзя исключить все сравниваемые колонки или ключ. Применённая проекция всегда возвращается в результате. Изменённый порядок при ordered исключением не скрывается.
- Допуски чисел/времени, regex, пропуск строк, произвольные функции/BSL и «наиболее похожие пары» в v1 не поддерживаются; неизвестное правило — `invalid_contract/unsupported_rule`, не молчаливое игнорирование.

## Выход и ограничение diff

Обязательные поля: `version:1`, `contract_id`, `status`, `equal`, `reason`, `scope`, `sources`, `applied_rules`, `counts`, `diff`, `diff_truncated`, `business_confirmed:false`.

- `status`: `equal`, `different`, `unavailable`, `invalid_contract`; `equal` соответственно true, false, null, null. `reason` — null при equal, `value_mismatch` при различии строк, либо описанный код причины. Неверная структура — `invalid_contract/invalid_shape`; лимит входа — `unavailable/input_budget_exceeded`.
- `scope`: `query_result` либо `wire_projection` (разрешённый wire_null, исключённые колонки или преобразованное представление). Для непригодного входа — null. Равенство проекции не подтверждает равенство исключённых данных. `sources` сохраняет метаданные обеих сторон без SQL, параметров и секретов подключения.
- `applied_rules`: mode, keys, order_basis, ignore_columns с причинами, null_policy каждой колонки и data_policy_id. Нельзя скрыть исключения за одним boolean.
- `counts`: expected, actual — число строк, если известно; missing, unexpected, changed, equal — глобальные числа строк либо null, если сравнение строк не выполнялось. Для bag changed=0; для keyed/ordered одна изменённая пара считается одним changed. При выполненном сравнении: expected=equal+changed+missing, actual=equal+changed+unexpected.
- `diff`: массивы `missing`, `unexpected`, `changed`, `schema`. Missing/unexpected: `{row, count, indices}`; bag агрегирует одинаковые строки, остальные режимы count=1. Changed: `{expected_index, actual_index, key, cells}`, где key=null для ordered, cells — `{column, expected, actual}`. Schema: `{column, expected, actual}`, отсутствующая колонка обозначается null.
- Индексы нулевые, относятся к исходным входам. Для bag стабильный порядок — первое появление ожидаемой строки для missing, фактической для unexpected; keyed — порядок expected для changed/missing и actual для unexpected; ordered — индекс. Ячейки/schema diff — порядок контрактной схемы, лишние колонки в порядке actual.
- Бюджет v1: до 1000 строк на сторону, 100 колонок, 1 MiB UTF-8 JSON нормализованного запроса. Это лимиты компаратора, не утверждение о платформе. Сначала полностью вычислить счётчики, затем ограничить суммарно 100 записей diff и 256 KiB UTF-8 JSON самого diff; порядок отбора schema → missing → unexpected → changed. Запись, не помещающаяся целиком, и последующие опускаются; `diff_truncated=true`. Не обрезать значение внутри записи. Все индексы агрегата входят в ту же запись.
- Усечённый diff при полностью сравнённых входах сохраняет достоверный different и глобальные counts. Усечённый вход не даёт достоверного equal/different. Сбой компаратора — `unavailable/comparison_failed`, не новый запуск команды.

Diff содержит пользовательские данные: действуют текущая изоляция/доступ/сроки хранения артефактов; нельзя писать его и SQL в безусловный технический лог. Этот контракт не создаёт второго журнала lifecycle.

## Проверенные вручную примеры контракта

Обозначения: `S(x)` — string, `N(x)` — number с десятичной строкой, `B(x)` — boolean; строки в скобках. Если не оговорено иное, обе стороны успешны/полны, схема и контекст совпадают, лимит выше числа строк. Это ожидаемые результаты для тестов 10.2, не выполненные тесты компаратора.

| № | Режим / expected → actual | Ожидаемый результат и причина |
| --- | --- | --- |
| 1 | bag: `(S(a)),(S(b))` → `(S(b)),(S(a))` | equal; equal=2 |
| 2 | bag: `(S(a)),(S(a))` → `(S(a))` | different; missing=1, equal=1; кратность не потеряна |
| 3 | bag: `(S(a))` → `(S(b))` | different; missing=1, unexpected=1, changed=0 |
| 4 | keyed по id: `(N(1),S(a))` → `(N(1),S(b))` | different; changed=1, одна изменённая ячейка |
| 5 | keyed по id: `(N(1),S(a))` → `(N(2),S(a))` | different; missing=1, unexpected=1 |
| 6 | keyed: expected содержит два одинаковых id=1 | unavailable/duplicate_key; counts отличий=null |
| 7 | ordered: `(S(a)),(S(b))` → `(S(b)),(S(a))` | different; changed=2 |
| 8 | ordered: те же строки, order_proven=false | unavailable/order_unproven |
| 9 | bag: `(N(1.00))` → `(N(1))` | equal; десятичное сравнение |
| 10 | схема number → схема boolean; `(N(1))` → `(B(true))` | different/schema_mismatch; не equal из-за Python 1==True |
| 11 | bag: `(S(a))` → `(S(a ))` | different; missing=1, unexpected=1 |
| 12 | reference: одинаковые база/тип/UUID, разные presentation | equal; подпись не ключ |
| 13 | reference: одинаковый UUID, разные object_type | different; missing=1, unexpected=1 |
| 14 | expected пуст; actual failed, rows=null | unavailable/source_failed, не equal; адаптер сохраняет отказ, не синтезирует успешный набор |
| 15 | два успешных пустых набора | equal; все счётчики=0 |
| 16 | actual содержит ровно effective_limit строк | unavailable/incomplete_source, даже если значения совпали |
| 17 | actual из другой базы | unavailable/source_mismatch |
| 18 | UI/частичный набор против полного эталона | unavailable/unsupported_source; полный query с partial — incomplete_source |
| 19 | keyed: id тот же, изменена только исключённая колонка с reason | equal в wire_projection; исключение возвращено |
| 20 | неразличимый null при null_policy=reject | unavailable/ambiguous_null |
| 21 | два wire_null при явной null_policy=wire_null | equal в wire_projection; исходные виды null не подтверждены |
| 22 | значение пришло с недоказанной точностью float | unavailable/numeric_precision_unproven |
| 23 | tolerance/неизвестное правило | invalid_contract/unsupported_rule |
| 24 | 101 различная строка с теми же ключами | different; changed=101, максимум 100 записей diff, diff_truncated=true |

Проверка примеров: разбор по определённым выше правилам, включая баланс счётчиков и запрет ложного равенства при недоступности. Машинная проверка семантики появится в 10.2; сборка и повторные проверки 8.5.1.1529 для документа не выполнялись. Следующий шаг — 10.2: реализация нормализатора/компаратора и автоматизация этих примеров. 10.3 и незавершённая приёмка остаются открытыми.
