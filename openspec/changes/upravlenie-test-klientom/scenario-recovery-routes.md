# TASK-021 — восстановление runner: file и HTTP

17.11.2026. Проверен оставшийся маршрутный охват [восстановления runner](scenario-recovery.md) на отдельных файловых базах **8.5.1.1529**. Продуктовый код, EPF и сценарий проверки не изменялись. Подтверждённые embedded и локальные тесты не повторялись.

| Проверка | Файловый мост | HTTP-прокси |
|---|---|---|

| Завершение собственных процессов | Подтверждено | Подтверждено |

В каждом прогоне **10/10 утверждений**, включая привязку живого сеанса. Всего четыре реальных принудительных завершения дочернего Python-процесса runner. Восстановление выполнялось новыми процессами продуктового CLI; менеджер/клиент при этом сохраняли сеанс.

После завершения стендов журналы SQLite общего lifecycle прочитаны в режиме read-only. В каждом журнале ровно **две succeeded-операции test_input**, по одной на каждый исходный request_id двух сценариев. Для сохранённого receipt operation_id совпадает с checkpoint; для потерянного receipt runner не знает этот ID и не использует его для обхода unknown. Сведения из журнала сохранены отдельно как доказательство. Это подтверждает отсутствие новых операций ввода; отдельный счётчик вызова бизнес-обработчика в конфигурацию не добавлялся.

Сбой до сохранения receipt моделируется завершением процесса после HTTP-ответа транспортному адаптеру, а не физическим разрывом сети. File обозначает файловый транспорт Toolkit; обе информационные базы также файловые. Проверки не доказывают клиент-серверный режим базы, перезапуск менеджера, смену поколения сеанса или продолжение после утраты retention.
