# TASK-021 — восстановление continue_observation

17.11.2026. Следующая доступная часть выбрана из [единого остатка](task021-remainder.md): восстановление после подтверждённой ошибки read-only шага с политикой continue_observation. Предыдущие положительные префиксы/recovery по трём маршрутам повторно не проверялись.

## Изменение

Общее правило допустимого продолжения используется обычным исполнением и recover. После проверки сохранённой операции в общем lifecycle runner восстанавливает режим «только наблюдения», сохраняет failed и отдельно reconciliation. Последующие мутации отмечаются skipped без отправки; отметка сохраняется до перехода к следующему шагу. После ещё одной потери процесса пропущенный шаг распознаётся только при доказанном предшествующем режиме continue_observation. Оставшиеся чтения проходят полный preflight и свежий guard; нужны явный resume и прежняя привязка.

Итог остаётся partial, а не succeeded. Повторный recover/resume не повторяет ни failed-чтение, ни пропущенную мутацию, ни уже завершённое чтение. Известные failed/cancelled с политикой stop не превращаются в unknown. Unknown, отсутствие ID, недоступный/просроченный результат, отказ в правах/подтверждении, потеря соединения/сеанса не дают разрешения продолжить по continue_observation.

## Проверки

- Пять новых локальных тестов: восстановление failed/skipped/succeeded и повторный resume; stop; permission_denied; unknown; вторая потеря процесса сразу после сохранения skipped. Мутаций в этих сценариях нет.
- Отдельная файловая 8.5.1.1529, HTTP-прокси: намеренно неуспешное ожидание значения, реальное завершение дочернего runner после получения ID и до записи терминального результата, recover, resume, повторный resume. Продуктовый CLI восстановил failed, пропустил ввод и прочитал исходное пустое значение. Общий итог partial, число отправок 2 (ошибочная проверка и завершающее чтение).
- Первый подготовительный прогон завершился runner_wait_expired: секундный бюджет закончился до наблюдения терминального результата, до точки kill дело не дошло. Он не засчитан как приёмка failed. Обвязка точки сбоя теперь наблюдает ту же операцию до 15 секунд, чтобы дождаться терминального failed и завершить процесс именно в нужной точке. Это настройка инъекции сбоя, не изменение таймаутов продукта и не повтор команды. Исходный unknown сохранён в доказательствах.
- Ещё две подготовки не дошли до сценария: ошибка формата потока при старте клиента и ErrorWindow вместо Action Fixture. Их корневая причина не доказана; повторных команд сценария не было. Для итоговой копии использована ранее завершённая тестовая база HTTP, а не прежний исходный файл. В harness добавлено сохранение дерева неожиданного окна при таком сбое.
- После всех четырёх прогонов журналы общего lifecycle проверены read-only: test_input отсутствуют. В принятом прогоне документы до/после неизменны. В трёх непринятых прогонах итоговая query-сверка документов не выполнялась. Собственные процессы всех четырёх стендов завершены.
- Старая EPF использована без изменения/сборки; наблюдателя и новой записи uilog нет. Локальные прежние наборы и embedded/file runtime не повторялись. Этот новый вариант runtime отдельно подтверждён только на HTTP. AST, OpenSpec strict и diff-check выполнены.
