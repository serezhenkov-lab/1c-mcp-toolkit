# Номер документа и модальный вопрос — 16.11.2026

Продолжение [нативной проверки](native-document-partial.md), 4.1/7.5/8.3. Файловая 8.5.1.1529, тонкий Windows-клиент, HTTP proxy, отдельные копии подготовленного стенда. Наблюдателя нет, анонимизация отложена, рабочая установка не обновлялась. Незавершённые пункты остаются открытыми.

## Подтверждённая причина unknown

Диагностическая EPF из копии исходников добавляла только запись этапов и исходных исключений. Цепочка воспроизведена дважды:

1. Активизация поля «Номер» завершена.
2. `ВвестиТекст()` завершён, completed_steps содержит activate/input_text.
3. Платформа открыла MessageBox о ручном изменении автоматически заполняемого номера.
4. Toolkit вызвал `ЦельЗавершения.Активизировать()` для поля «Дата», чтобы завершить редактирование.
5. Платформа отказала: «Недоступный пользователю элемент управления не может выполнять интерактивные действия. (Дата)».

Перед пунктом 4 `ПередИзменениемUI` устанавливает execution=unknown; исключение не даёт подтвердить завершение. Общий `КодИсключенияUI` на нативном исключении без TKUI возвращает connection_lost. Это не доказанный обрыв соединения: окна и явный ответ на вопрос после него успешно читаются/исполняются. [Исходные стеки](evidence/modal-input/trace-parsed.json).

## Исправление

В производственном модуле формы менеджера после ввода/выбора/флажка и до следующего изменяющего вызова проверяется активное окно. Если оно отличается от целевого и не является основным, завершение ввода останавливается:

- status=failed, execution=invoked, verification=not_confirmed;
- error.code=action_not_confirmed;
- data.input_completion=blocked_by_other_window;
- data.blocking_window_id — зарегистрированный ID обнаруженного окна;
- completed_steps сохраняет подтверждённые вызовы; finish_edit отсутствует, actual/editing не выдумываются.

Текст уже передан платформе; failed не означает отмену ввода. Сборщик не должен автоматически повторять его. Вопрос не закрывается и не получает автоответа. Продолжение требует отдельного явного действия и наблюдения состояния. Проверка относится также к другому перехватившему активность окну, а не объявляет любое такое окно модальным. Если состояние изменится после проверки или чтение API само откажет, общий unknown остаётся возможен; универсальное устранение всех гонок не заявляется.

Классификатор всех платформенных исключений этим узким исправлением не переписан. Трассировка и подробные нативные исключения в обычную EPF не включены. Новых транспортов, автоматических повторов и клиентских модулей нет.

## Что установлено о stale_target

В двух новых прогонах исходной логики ответ «Нет» по полученным ID прошёл успешно: сразу после снимка и после задержки 55 секунд. После ответа диалог исчезал, чтение основного поля оставалось доступным. Это опровергает необходимость заменять ID подбором по похожему тексту и не подтверждает гипотезу об обязательном истечении ID за такую задержку.

На исправленной обычной EPF явный ответ также успешен. Дополнительная команда к тому же уже закрытому MessageBox получила stale_target/execution=not_started. Это правильная защита от обращения к отсутствующей цели, её не ослабляли.

В старом прогоне после stale_target последующий поиск уже не находил окно; точный момент исчезновения и полный нативный стек тогда не сохранялись. Причина исчезновения не установлена: нельзя утверждать, что первый ответ его закрыл, что это был сбой реестра или действие пользователя. Новые положительные ответы не доказывают причину старого отказа. При новом воспроизведении нужен снимок непосредственно перед ответом и трасса разрешения цели, а не слепой повтор нажатия.

## Проверки

Диагностические прогоны: [немедленный ответ](evidence/modal-input/20261116T123706/proof.json), [ответ через 55 секунд](evidence/modal-input/20261116T123839/proof.json). Одна попытка запуска controller до появления state.json отказала локально до UI-действий; повтор после готовности не был повтором мутации.

Обычная исправленная EPF: [7/7 целевых проверок](evidence/modal-input/20261116T124131/fixed-checks.json):

1. Явное прерывание завершения ввода без unknown в воспроизведённом случае.
2. Только activate/input_text в подтверждённых шагах, без finish_edit.
3. blocking_window_id совпадает с обнаруженным MessageBox.
4. Явный ответ «Нет» успешен.
5. Диалог после ответа отсутствует.
6. Закрытый ID отклоняется до вызова.
7. Обычный ввод в обязательное поле после ответа завершается и подтверждает значение.

Проверен именно изменённый путь; прежняя запись документа/потеря ответа/полные старые наборы не повторялись, новых документов не записывали. Статика и сборка: CheckConfig ThinClient/Server/HandlersExistence и сборки диагностической/обычной EPF успешны. Все собственные процессы трёх запусков завершены.

Открыты первоначальная причина исчезновения диалога, другие среды/маршруты, позднее появление блокирующего окна, табличные ветви и общая приёмка. Формальные 13/42 сохранены.
