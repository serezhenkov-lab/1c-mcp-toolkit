# Квоты, отказы и задержки embedded lifecycle — 15.11.2026

Продолжение очереди 1: проверена текущая реализация физической компактации на 8.5.1.1529. Изменена только тестовая оснастка и документация; runtime Toolkit сохранён. Анонимизация отложена, наблюдатель не подключён, рабочая установка не обновлена. Незавершённые пункты и все 13/42 отметки плана сохранены.

## Стенд и методика

Windows, 64-разрядный тонкий клиент 8.5.1.1529, отдельная файловая база `.local/lifecycle-limits/db`, пользователь ApiProbe. EPF содержит текущий runtime и добавленные тестовые процедуры. Две сборки оснастки прошли ThinClient/Server/HandlersExistence. HTTP — localhost:17661, анонимизация в оснастке отключена. SHA256 основной формы до/после: `fca93fb3638ec39a353ec344a7f7a12d85e4575d62536dcb7cc83e67c088dc83`.

Наборы на 1 000/9 999/10 000 ключей и около 60/64 MiB — синтетические сохранённые записи совместимого формата с SHA256, созданные по записи реального владельца. Это нагрузка загрузки и компактации, а не выполнение 10 000 пользовательских действий. Для ключевых наборов сохранены tombstone result_expired; для объёмных — неистёкшие результаты. Первый ключ keep имеет прежние реальные ID/key/fingerprint, поэтому повтор проверяется штатным admission. Входные файлы имеют LF, checkpoint платформы — CRLF: первоначальный рост на один байт на запись ожидаем.

Время startup_ms измеряет настройку владельца, включая чтение и стартовую компактацию, без запуска процесса/формы. Время compaction_ms — принудительная компактация в уже запущенном владельце. Фоновое обслуживание отключено только в оснастке для воспроизводимого замера. Для 1 000 записей выполнены три раунда, для 10 000 и больших файлов — по одному. Это наблюдаемые измерения, не статистический SLA.

HTTP-клиент имеет таймаут 2 с. Таймаут означает, что ответ не получен в этот срок, а не что сервер завершил обработку за 2 с. На первом наборе 1 000 опрашивались health и status; на последующих status вызывается только до/после раунда, внутри — health. Состав выборок различается, сравнивать их как одинаковые нагрузочные процентили нельзя. Исходная оснастка ожидала объект error: строковый error ответа HTTP 503 вызвал AttributeError при разборе. HTTP-код и время ответа сохранены; сводка отдельно считает ReadTimeout, HTTP 503 и ошибку парсера, не выдаёт последнюю за таймаут платформы.

## Квоты и отказы

- **100 активных:** 100 queued созданы штатным admission, 101-я отвергнута operation_quota_exceeded. Прямое чтение первой записи работает. Но публичный диспетчер test_session/status для неё также получает operation_quota_exceeded: чтение само резервирует новую операцию. Этот случай проверен прямым вызовом публичного диспетчера из оснастки, без HTTP.
- **10 000 ключей:** при 9 999 загрузка заняла 213,587 с; новый ключ занял последнее место, следующий получил operation_quota_exceeded. На готовом наборе 10 000 повтор keep вернул прежний ID, оба новых ключа отвергнуты. HTTP status до компактации также вернул operation_quota_exceeded, несмотря на доступность исходной записи владельцу.
- **Результат:** штатная проверка оценивает размер как число символов сериализованного JSON, умноженное на 4. Ровно 1 048 576 символов приняты (succeeded); 1 048 577 дали unknown/result_storage_quota. Это не проверка фактического размера UTF-8 в 4 MiB. После компактации повтор обоих ключей сохранил ID.
- **64 MiB + 1 байт:** входной журнал отвергнут operation_store_unavailable до разбора; его размер сохранён, исполнение не открыто.
- **Отказ append:** действующий журнал удержан ФайловымПотоком. Завершение не публикует успех, владелец получает operation_store_unavailable и healthy=false. После нового запуска прежний ключ имеет тот же ID и unknown.
- **Отказ замены:** блокировка действующего файла мешает замене после записи commit. Владелец закрывается с operation_store_unavailable; следующий запуск восстанавливает checkpoint, тот же ID остаётся unknown. Это реальный отказ файлового доступа, не заполнение системного диска и не отключение питания.

Для 10 000 и near64 финальная проба выполнена сразу после фиксации окончания раунда. Восстановление HTTP после полного дренирования накопившихся запросов отдельно не измерено; постоянная недоступность не утверждается. Для over60 публичный status не дал ответа за 2 с, поэтому конкретный JSON-код его отказа по HTTP не подтверждён. Прямая admission-квота и её длительность подтверждены отдельно.

Автоматические проверки сохранённых отчётов прошли (`check_limits_results.py`): граница результата, сохранение ID, безопасное восстановление, число ключей и активных записей, успешность checkpoint. Это не успешная приёмка доступности: найденные задержки и отказ чтения status остаются дефектами/ограничениями. Генератор, OpenSpec strict обоих изменений и git diff --check прошли, собственных процессов стенда осталось 0. Изменённый парсер HTTP оснастки учитывает строковый error; исходная измерявшая версия и сырые результаты сохранены, повторный runtime-прогон после этой правки парсера не заявляется.

## Выводы для следующей реализации

Сохранение ключей и безопасный отказ подтверждены, но квота исполняемых операций одновременно блокирует публичное чтение состояния. Нужен отдельный путь/политика для чтения существующего результата без расходования той же admission-квоты. Требования наблюдаемости не упрощаются.

Синхронная компактация задерживает обработку embedded HTTP. При 10 000 небольших записях она занимает минуты: важен не только размер файла. По исходникам LifecycleХеш выполняется на сервере без контекста и вызывается для каждой записи на нескольких проходах. Для N одноревизионных записей обычный checkpoint выполняет 3N+2 вызова хеша, штатная загрузка с ним — 4N+3. Это подтверждённая структура вызовов и вероятный существенный источник задержек; распределение затрат профилировщиком не измерено. Нужны пакетная обработка/сокращение переходов клиент–сервер и повторный замер доступности, с сохранением проверок целостности и commit-протокола.

Не проверены совмещённый максимум 10 000 ключей и 64 MiB, заполнение физического диска, отключение питания, клиент-серверный/RDP режим и пользовательская приёмка. SQLite proxy не изменялся. Автоматическое удаление ключей ради освобождения квоты не допускается. Очередь 1 и прежние открытые пункты не закрыты.
