## Практический вывод

Наиболее полезны схема диагностического снимка, сведения об активном вводе, список кандидатов при неоднозначности и разделение штатного API с дополнительным наблюдением внутри клиента. Копировать менеджер целиком нецелесообразно: Toolkit уже строже проверяет владение процессом, однозначность целей и полноту наблюдения. Тестер часто предпочитает продолжить сценарий после ошибки или автоматически изменить UI.

## 1. Подключение и завершение

[Test.Module, 42–127](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Test/Module.bsl#L42):

- `ConnectClient` повторяет `tryConnect` после исключения и попытки Disconnect. Конструктор `TestedApplication` вызывается через Eval, чтобы тип не требовался вне режима менеджера.
- `ConnectedHost/ConnectedPort` присваиваются **до** `App.Connect()`: это выбранные параметры попытки, а не независимо подтверждённая идентичность соединения. Прежнюю формулировку обзорной подборки о фактическом адресе нужно читать с этим уточнением.
- После подключения сохраняются App/Connected/MainWindow. `initMainWindow` ищет IsMain; если окна существуют, но такого признака не найдено, переменная цикла может остаться последним окном. Для единственного окна вызывается Activate.
- Обычное подключение с очисткой ошибок может закрывать окна. В режиме `MCPRequestProcessing` очистка отключена.
- `DisconnectClient(Close=true)` вызывает `MainWindow.Close()` и отключает API, но сам не проверяет PID, время создания и принадлежность процесса, не ждёт доказанного завершения. Исключение Close может прервать последующую очистку состояния.

В нашем `ОстановитьКлиент` уже есть проверка PID/created/базы/token, однозначности основного окна и наблюдение исхода. Подменять её донорским Close нельзя. Полезно взять тестовые случаи: нет основного окна; разрыв API после Close; отказ Connect; attach к клиенту с открытой ошибкой без закрытия окон. Готового решения TASK-012/2.3 здесь не подтверждено.

## 2. Селекторы и неоднозначность

[Fields.findField, 106–169](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Fields/Module.bsl#L106) поддерживает поиск по представлению и явному имени (`!`), путь разбирает `Focus`. При нуле совпадений поиск по представлению повторяется как поиск по имени. При нескольких совпадениях `showObjects` формирует имена/типы кандидатов, но после предупреждения выбирается `objects[0]`.

[Runtime.ShowWarning, 405–416](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Runtime/Module.bsl#L405) пишет предупреждение и снимок; явного raise нет. Это не строгий отказ при неоднозначности.

**Использовать:** состав кандидата `имя + тип + вид элемента`, добавив наш путь и ID. Это может улучшить сообщение `ambiguous_target`. **Сохранить:** ровно одно совпадение, полноту поиска и проверку устаревшей цели из `РазрешитьЭлементUI`. Имя элемента Тестера не является сеансовым ID Toolkit.

## 3. Снимок интерфейса и изменения

[Fields.GetWindowControls, 949–1015](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Fields/Module.bsl#L949) и `tableElement` (1454–1526) показывают полезную структуру:

- форма, текущий элемент, редактируемый текст, открытый выпадающий список;
- текущая колонка и признак редактирования строки;
- отдельно свойства элемента и данные строки, полученные клиентским адаптером;
- дополнительные сведения: режим выбора, текущий родитель, системные поля строки.

[Forms.GetChanges/ResetBaseline, 378–415](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Forms/Module.bsl#L378) возвращают полный снимок при смене формы или сравнение JSON с предыдущим. Сравнение реализовано внешней C++ библиотекой (`addon/root.cpp:323–339`).

**Кандидат для Toolkit:** дополнительное представление изменений между двумя снимками с `session_id`, поколением формы, ID исходного снимка и coverage. При неполном наблюдении нельзя объявлять исчезнувший элемент удалённым. Это новая возможность, не обязательная зависимость текущей приёмки.

**Не переносить буквально:** `prepareElements` пропускает узел при ошибке GetChildObjects; `isInvisible` исключает также недоступные элементы. Пользователь тогда не отличит отсутствующую кнопку от заблокированной. У Toolkit уже есть `available` и coverage; их следует сохранить. `getDisplayedText` при ряде ошибок возвращает пустую строку — для нас нужна явная недоступность значения.

## 4. Таблицы и клиентский наблюдатель

[Fields.clientContext/callClient, 1049–1101](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Fields/Module.bsl#L1049) отправляет `getControls` по HTTP, адрес берётся из `TesterAgentConnectionString`. `tableElement` использует `Context.ClientControls`, чтобы получить Rows, CurrentRowData и системные поля. Без этого адаптера процедура возвращается после базовых свойств текущей колонки/режима редактирования.

Это подтверждает практическую ценность отдельного наблюдателя, описанного в [нашем предложении](client-row-adapter-proposal.md). Но принимающий код не доказывает устойчивость row_id, поведение при перестановке/пересоздании данных или полноту динамического списка. Для нашего наблюдателя остаются требования связи с UUID формы, поколением источника и нативным ключом. HTTP донора не нужен для переноса самой идеи.

[FetchTableContent/getTable/tableData, 843–910](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Fields/Module.bsl#L843) завершает редактирование, переходит к первой строке, выделяет все строки; при обходе без множественного выделения перемещает курсор. Это изменяющее наблюдение, не реализация read-only inspect. Прежний курсор и выделение в этом маршруте не восстанавливаются.

[NavigateToRow, 1661–1705](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Fields/Module.bsl#L1661) после неуспеха GotoRow допускает успех по совпадению текущего значения. Это не доказательство уникальности строки; в MCP-ветке при окончательном неуспехе ещё и возвращает курсор к первой строке. Для TASK-015 такой алгоритм непригоден без переработки.

## 5. Ввод, выбор и карточки

[Fields.putValue, 562–604](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Fields/Module.bsl#L562): после отказа InputText пробует список выбора; при ChooseValue выбирает элемент с индексом 0. Дополнительная проверка сравнивает представления без учёта регистра и при несовпадении очищает поле. Это полезный перечень сценариев отказа, но не наш контракт однозначного выбора. В ветке ошибки InputText для read-only поля явного повторного raise нет.

[ClickField, 697–755](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Fields/Module.bsl#L697): для группы пробует Expand, затем Collapse, подавляя вторую ошибку. Это не нажатие карточки. Для кнопки исключение Click подавляется, если `controlEnabled` подтверждает доступность/видимость по цепочке родителей. Успешный возврат функции поэтому не доказывает выполнение прикладного действия.

**Использовать как идею:** проверка доступности родителей перед действием (`controlEnabled`, 757–768), с явным unknown при недоступном свойстве. **Не переносить:** подавление ошибок и автоматические альтернативные изменяющие действия. Проверок ShowAsCard/Hyperlink для группы в изученном Fields нет; TASK-014/4.4 не закрывается.

[ShowValueInInputField, 784–796](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Fields/Module.bsl#L784) вызывает Focus → editRow → field.Open → finishEditing. `editRow` начинает изменение, только если его ещё нет; завершает затем только начатое здесь редактирование. Это статический маршрут с побочными действиями, не доказательство причины нашего отказа. Восстановление после исключения Open отдельным finally не обеспечено. Опыт с Открыть() не возобновлялся.

## 6. Ожидания и диагностика

[Forms.Wait, 307–321](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Forms/Module.bsl#L307) делегирует ожидание `WaitForObjectDisplayed`. `Test.PauseExecution` вызывает внешнюю Pause; в `addon/root.cpp:341–349` это Sleep/sleep. `Debugger.delay` использует цикл по времени с UserInterruptProcessing. Эти механизмы не подтверждают доступность status во время ожидания и не заменяют наш пошаговый исполнитель.

[Debugger.ErrorCheck, 233–272](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Debugger/Module.bsl#L233) читает GetCurrentErrorInfo, хранит DetailErrorDescription и подавляет повтор той же ошибки по тексту. При исключении чтения error становится undefined. В `Runtime.GetErrors` (463–496) исключение чтения сообщений превращается в пустой массив, затем проверяются системные диалоги по известным именам.

**Использовать:** отдельные каналы диагностики — исключение действия, ошибка приложения, сообщения формы, последний снимок. **Изменить:** отказ чтения должен давать unavailable; одинаковый текст не доказывает, что это прежнее событие. Не очищать ошибки/окна во время диагностики.

## 7. Меню и снимок экрана

[Fields.FetchMainMenu, 1591–1659](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/tester/src/CommonModules/Fields/Module.bsl#L1591) сначала обращается к клиентскому кэшу, иначе нажимает разделы, открывает меню, а для некоторых разделов вызывает CloseAll. Такой способ наполнения кэша нельзя выдавать за пассивное чтение командного интерфейса.

[addon/shooter.cpp, 291–348](https://github.com/grumagargler/tester/blob/7803c0fd8d6a69dcdb0e7b68d5be1a4d6ce6fc04/addon/shooter.cpp#L291): Windows-снимок ищет окно через EnumWindows по заголовку, активирует его и снимает изображение. Полезен как пример реализации захвата, но не готовое решение TASK-016/6.4: нам нужна проверенная привязка к процессу нужного тест-клиента, а не только заголовок. Компонента не собиралась и не запускалась.

## Приоритет использования

| Приоритет | Что взять | Зависимости и необходимая проверка |
| --- | --- | --- |
| 1 | Кандидаты неоднозначного селектора с именем, типом, видом и путём | Собственная реализация поверх текущего дерева; две одинаковые кнопки, без действия |
| 1 | Диагностика активного ввода: editing text, текущая колонка, список выбора | Проверка доступности свойств на стенде; никакого Focus/EndEditRow в inspect |
| 1 | Проверка доступности родителей, сохранение исключения нажатия | Недоступный родитель, неподдержанное свойство, отказ обработчика |
| 2 | Раздельные снимки ошибок приложения и сообщений формы | Ошибка получения данных не равна отсутствию ошибок; анонимизация |
| 2 | Разница двух снимков | Сеанс/поколение/coverage, лимиты, смена формы и неполный обход; отдельное расширение контракта |
| Отложено | Клиентское обогащение строк | Предложение наблюдателя остаётся без внедрения; нужны исходники клиентского обработчика и тесты идентичности |
| Не переносить | Автовыбор первой цели/строки, подавление Click, автоматическая очистка окон, обход таблицы под видом чтения | Нарушают действующие требования Toolkit |

Ни один открытый пункт OpenSpec не закрывается этим анализом. Конкретные следующие изменения можно делать небольшими патчами в существующем драйвере, без переноса конфигурации, компилятора сценариев и внешней библиотеки Тестера.
