# Очередь 1: публичный адаптер общего lifecycle — 15.11.2026

Последующее поручение разрешило разработку после обновления плана. Сохранены прежние изменения и 13 отметок выполнения. Очередь не закрыта: здесь подтверждена часть 2.3, 6.1–6.3, 8.1–8.2, а не полная приёмка трёх маршрутов.

## Реализация

- Семь `test_*` опубликованы в native MCP и REST proxy. Используются существующие очередь HTTP/file bridge и общий OperationJournal, без отдельного UI-журнала. Нужны OPERATION_JOURNAL_DIR и доверенный локальный профиль через существующий внутренний API. Внешний контракт принимает только profile_id, не подключение, пароль, shell или BSL.
- Канонизация раскрывает defaults и нормализует целочисленные JSON-числа. Канал/request_id сохраняет operation_id; иной запрос даёт request_conflict. Дополнительный context общего журнала хранит публичный session_id, не исходную команду. Unknown не переисполняется.
- Status(operation_id) читает журнал без очереди 1С и запросов загрузки словаря. У чтения собственный ID; целевой снимок находится в data.operation и не меняет исходную операцию. Повтор ключа чтения возвращает сохранённый снимок; для нового наблюдения нужен новый request_id. Чужой/неизвестный ID не раскрывается.
- События подтверждения UI идут по существующему lifecycle-маршруту; полный конверт сохраняется при failed/unknown. Rejected владельца отображается как failed/permission_denied. Подтверждение сеанса имеет дедлайн; поздний callback не разрешает действие. При штатном закрытии менеджера публикуются доступные итоги незавершённых шагов.
- Выдача результата применяет действующую анонимизацию, включая политику исходного инструмента для вложенного сохранённого снимка статуса. Проверка изменения политики автоматическая; это не runtime-приёмка анонимизации всех маршрутов.
- Diagnostics содержит process_state, connection_stage, last_api_error, requested/observed endpoint. Ошибка API сохраняется как безопасный код/стадия, без сырого текста с возможными секретами. Недоступность времени создания не считается завершением процесса.
- Resolver возвращает resolution с exact_matches и кандидатами: до 20 и 64 КиБ, без живых ссылок. Подсказки не меняют точный выбор; действие не повторяется.

## Проверки и границы

Windows, тонкий клиент **8.5.1.1529**, файловые копии `.local/queue1/db` и `.local/queue1-file/db`, ApiProbe. Это не клиент-серверная база и не RDP-прогон. Наблюдатель не подключён, рабочая установка не обновлялась.

- Python: **50 + 14** тестов. Последние изменения адаптера дополнительно проверены его 7 тестами. Покрыты defaults/конфликт/одна выдача, status при ожидании, чужой канал, unknown, восстановление session_id, запрет server-host и политика вложенного результата.
- Платформа: ThinClient/Server/HandlersExistence и сборки EPF успешны. Startup и программные ответы реальным диалогам добавлены только в тестовые копии.
- BSL LS: два модуля, 6824 диагностик, 752 Error в существующем коде; **0 Error на изменённых строках**. Сохранены 344 GENERATED-блока. Весь проект чистым не объявляется.
- Native MCP перечисляет семь групп. HTTP и локальный file bridge: start, inspect/windows, activate_window, open навигационной ссылки, expect с тайм-аутом, повтор/конфликт. Input проверен отрицательным поиском, table/read — честным unsupported_operation; положительная приёмка всех действий не заявляется.
- Status доступен во время test_expect, повтор не создаёт новое исполнение.
- Публичный HTTP restart сохраняет /TESTMANAGER, сбрасывает session_allow в deny, оставляет один прежний TESTCLIENT. Старые session/window ID отклонены; второй start запрещён. Attach даёт новый session_id и owned=false; stop без владения запрещён.
- Restart во время test_expect дал unknown; повтор сохранил тот же ID без исполнения.
- File bridge: реальная форма дала awaiting_approval → rejected для UI и сеанса, awaiting_approval → результат для согласия. Повтор согласованного действия не вызывает его снова. Ответы программные из обвязки, не ручная приёмка.
- Финальная EPF: отсутствие/неоднозначность цели возвращают кандидатов без действия; Alive/ready и endpoint доступны. Подтверждение detach с timeout_ms=500 истекает до ответа обвязки через 3 секунды; поздний ответ не меняет ask и готовность сеанса.

## Сохранённые неуспешные пробы

Первая HTTP-проба обнаружила неверный порядок параметров доставки, исправленный до успешного прогона. Activate_window основного окна при открытом списке вернул invoked/not_confirmed, не успех; независимая проба согласия использовала активное окно и новый ключ.

Первый тест истечения остановил менеджер ошибкой обвязки: повторный Закрыть() уже закрытой формы. Причина подтверждена журналом регистрации. В обвязке добавлена Открыта(); production для обхода ошибки не менялся. Незавершённый read-only status, прежний exchange и общий журнал сохранены. Новый тестовый exchange использовал тот же журнал после перезапуска владельца; старый ключ не переисполнялся. Повторная проба успешна.

## Остаток очереди 1

1. Подключить durable lifecycle к **embedded HTTP** у общего владельца. Прежний отказ остаётся; он не считается выполнением требования. Подтвердить единый контракт трёх маршрутов.
2. Завершить штатную настройку/восстановление доверенного профиля вне startup-обвязки. Проверить restart на file bridge/embedded, аварийную потерю менеджера без штатного callback и element/row ID. HTTP-проба не закрывает весь 2.3.
3. Выполнить runtime-матрицу анонимизации/разрешений, late result и потери ответа/владельца. Unit-результаты не заменяют её.
4. Для 8.1 проверить Unknown/AccessDenied/Exited/StartTimeMismatch, смену endpoint и ошибки стадий. Здесь runtime подтверждён Alive/ready и отсутствие второго запуска после restart; остальные ветки не приняты.
5. Для 8.2 остаются дополнительные проверки лимита/недоступных свойств, активного ввода и предков. Кандидаты не закрывают весь пункт.

Все незавершённые пункты остаются открытыми. К Открыть() не возвращались, требования не упрощены.
