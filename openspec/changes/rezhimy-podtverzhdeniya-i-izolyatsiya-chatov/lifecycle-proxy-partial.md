# TASK-002 — общий lifecycle, первая реализация в proxy

14.11.2026. Реализована и проверена на 8.5.1.1529 основа OL-01/OL-02 для нового native MCP вызова `execute_code_operation`. Это частичный результат: 3.1–3.3, интеграция TASK-016/6.1–6.3 и сквозная приёмка остаются открытыми. Требования не сокращены.

## Контракт и размещение

- Журнал SQLite принадлежит существующему proxy; доставка остаётся в существующей ChannelCommandQueue. Второго исполнителя или очереди нет. Обработка 1С продолжает решать разрешения непосредственно перед выполнением.
- Включение только явно: `OPERATION_JOURNAL_DIR` — абсолютный путь к постоянному выделенному каталогу. Без него новые операции отклоняются с `operation_store_not_configured`; старый `execute_code` работает по прежнему контракту. Рабочая установка не настроена и не обновлена.
- Native `execute_code_operation(request_id, code, execution_context="server", wait_timeout_ms=0)` возвращает operation_id/status/result. wait_timeout_ms — целое 0…30000, ограничивает только ожидание уже принятой операции. Повтор не продлевает ожидание. `get_operation(operation_id)` читает тот же журнал в текущем канале без постановки кода в очередь. Поле success означает успешное чтение статуса; подтверждённый исход находится в status и вложенном result.success.
- Ключ — `(channel, request_id)`, длина request_id 1…128 символов. SHA-256 считается по каноническому JSON имени команды и фактических параметров после детокенизации. Порядок ключей словаря не важен, типы и содержимое важны. Код и входные параметры в журнале не сохраняются. Одинаковый ключ/содержимое возвращает прежнюю операцию; иное содержимое — request_conflict.
- Запись принятия фиксируется ДО публикации в очередь, running — ДО выдачи транспорту, итог — ДО уведомления ожидающих. SQLite synchronous=FULL и эксклюзивная блокировка владельца. Недоступный журнал/второй владелец не допускает новую команду к исполнению.
- После перезапуска все queued/running/awaiting_approval становятся unknown/executor_restarted; автоматического воспроизведения нет. Смена владельца канала также даёт unknown. Сбой записи журнала перед выдачей не передаёт команду 1С: запись может оставаться queued до восстановления процесса, после чего станет unknown. Это консервативная неопределённость, а не обещание выполнения.
- TTL результата — 24 часа; затем result_expired, тело результата удаляется логически. Старый ключ остаётся навсегда в ограниченном журнале. Максимум 10000 записей, 64 МиБ тел результатов, 4 МиБ на результат, SQLite ограничен 32768 страницами (обычно 128 МиБ). При заполнении новые команды отклоняются, running/unknown и ключи не вытесняются. Слишком большой результат даёт unknown/result_storage_quota. Удаление журнала ради квоты уничтожает защиту от дублей и не является поддержанным способом продолжения; обслуживание/ротация требуют отдельного решения.
- На диске сохраняется исходный результат до обработки анонимизатором: каталог должен наследовать ограничения доступа оператора proxy, не попадать в общий обменник/публикацию. TTL не означает физическое затирание страниц SQLite или резервных копий.
- При выдаче результат проходит существующую политику анонимизации. При включённом словаре его подготовка выполняется до принятия новой команды. Чтение статуса не загружает словарь запросами к базе: если после перезапуска словарь не готов, результат закрыт ошибкой operation_result_policy_not_ready. Ограничения server_host по инструментам, клиентскому контексту, токенам и требованию подтверждения сохранены; runtime server_host не проверен.

## Что подтверждено

1. Python: 38/38 тестов корневого набора, включая 14 новых lifecycle; отдельно 14/14 тестов test_client. Проверены тайм-аут/отмена ожидающего, поздний результат, один приём при повторе, конфликт, изоляция каналов, восстановление, TTL, квоты, исключение второго владельца, отказ хранилища, файловая доставка, анонимизация без запросов из status, запрет смены владельца при долгой команде и ограничения server_host. Файловый транспорт здесь проверен с имитатором ответа 1С.
2. Сборка тестовой EPF на 8.5.1.1529 успешна. Первоначальная ошибка синтаксиса тестового stop-hook исправлена только в генераторе стенда. Production BSL в этой работе не менялся.
3. Настоящий native MCP HTTP → proxy 127.0.0.1:17653 → клиент 8.5.1.1529 → файловая тестовая база. Отдельная копия `.local/lifecycle/db` создана при эксклюзивном чтении исходной `.local/task043/db`; начальный SHA-256 обеих: FF1BD54E9D9A304D1D1FE85EEE0BED8297E1694DA8ED60FC3E9023D025ED0C6C. Только служебный документ T43_Required; в копии остались два новых тестовых документа.
4. LATE: ожидание 1 мс, повтор того же ключа с тем же operation_id, конфликт изменённого кода, чтение running во время искусственной задержки ответа после фактической записи; через 3 секунды получен succeeded/LIFECYCLE_LATE.
5. DROP: запись выполнена в 1С, тестовая HTTP-обёртка поглотила ответ, затем завершён только собственный процесс proxy. После запуска с прежним журналом — unknown/executor_restarted, повтор ключа возвращает тот же ID и unknown. Предыдущий succeeded сохранён. Независимые запросы к тестовой базе подтвердили ровно по одному документу с каждым уникальным номером. Проверка данных не меняет unknown автоматически и не доказывает откат.
6. Первый проход after остановился на request_conflict: сам проверочный скрипт прочитал UTF-8 код из JSON системной кодировкой Windows. Исправлено явным encoding="utf-8"; исходный неуспешный лог сохранён. Защита от изменённого содержимого сработала корректно.
7. На окончательном коде proxy повторно проверены сохранённые succeeded/unknown, повтор DROP без запуска и количество обоих документов = 1. Оба OpenSpec change проходят strict validate; git diff --check успешен. 44 файла production-исходников 1С совпадают с манифестом TASK-017/7.2. Собственные тестовые процессы завершены, порт 17653 освобождён.

Исходники воспроизведения: `tests/lifecycle/prepare_stand.py`, `serve_stand.py`, `run_probe.py before|after`. Сырые результаты и успешные/неуспешные проходы — [архив](evidence/lifecycle-runtime.zip), итог native и запросов данных — [probe.json](evidence/lifecycle-probe.json). Запуск тестового сервера предполагает одноразовый каталог `.local/lifecycle`; маркеры fault injection не следует переиспользовать для нового эксперимента.

## Оставшаяся работа и сверка unknown

**Дополнение 14.11.2026:** передача awaiting_approval/running и структурированного rejected из 1С реализована и проверена на HTTP и локальном файловом мосте — [новый протокол](lifecycle-approval.md). Нижеследующий список сохраняет исходный срез первой реализации; пункт об отсутствии этих событий теперь выполнен в описанном новом охвате. Интеграция test_* и непроверенные режимы остаются открытыми.

- В текущем 1С-протоколе нет события перехода в awaiting_approval и структурированного rejected. Пока running означает «передано исполнителю», включая возможное ожидание его диалога; отказ 1С хранится как failed с исходным ответом. Нужна явная передача состояний без классификации по тексту ошибки. Проверка разрешений не перенесена в proxy.
- `test_*` ещё не подключены к этому журналу: прежние защитные отказы сохранены. Нужны общая нормализация/отпечаток действий, адаптер envelope и IDs, проверка полномочий и анонимизации в общей очереди. Клиентский адаптер нативных ID строк не внедрён.
- Встроенный HTTP и реальный файловый мост 1С, клиент-серверная база, долговременная нагрузка/квоты и полная пользовательская приёмка не проверены. Нельзя объявлять их готовыми по этому HTTP-прогону.
- При unknown: сохранить operation_id/request_id, канал и внешний признак изменения; прочитать итог по ID, затем отдельно проверить фактическое состояние данных по устойчивому бизнес-ключу. Не повторять автоматически и не генерировать новый request_id для того же изменения. При неоднозначности оставить unknown. API ручного изменения unknown в подтверждённый итог пока нет.
- Для отключения новых вызовов остановить тестовый proxy, сохранив журнал; старые операции не повторять. Откат программы не отменяет уже записанные данные. Рабочую установку, Открыть() и незавершённые пункты прежних задач эта работа не меняет.
