## Purpose

Простой выбор разрешений опасных операций в текущем сеансе обработки Toolkit.

## ADDED Requirements

### Requirement: Три режима разрешений

<a id="am-01"></a>

Toolkit SHALL предоставлять ровно три режима: deny («Запрещать»), ask («Спрашивать каждый раз»), session_allow («Разрешить всё в текущем сеансе»). Режим SHALL выбираться одним полем формы, кнопкой «Разрешить всё в текущем сеансе» в окне подтверждения либо командой MCP set_approval_mode и управлять подтверждением опасных операций Toolkit, не отменяя права 1С и ограничения платформы. Обращения, не требующие подтверждения, SHALL сохранять обычное поведение.

#### Scenario: Управление режимом через MCP
- **WHEN** клиент вызывает set_approval_mode с единственным обязательным параметром mode из deny/ask/session_allow
- **THEN** обработка меняет существующее поле тем же обработчиком, что форма, без отдельного подтверждения; возвращает mode, previous_mode и scope=toolkit_session. Команда доступна через встроенный MCP/REST и существующий proxy с маршрутизацией в выбранный канал. Иные значения и лишние параметры отклоняются до изменения режима. Повтор того же значения не отзывает текущие разрешения. Новый режим и параметр запуска не вводятся.

#### Scenario: Изменение режима при ожидающем подтверждении
- **WHEN** set_approval_mode изменяет режим при наличии ожидающей опасной команды
- **THEN** прежнее поколение разрешений становится неактуальным, как при изменении поля формы; команда управления сама не исполняет и не повторяет ожидающую операцию. Выполняющаяся операция не объявляется остановленной.

#### Scenario: Размещение поля
- **WHEN** пользователь открывает основную форму
- **THEN** поле «Опасные операции» расположено в общей части вкладки «Подключение» перед «Параллельное выполнение команд» и видно в режимах proxy и встроенного сервера; переключение режима подключения не скрывает поле. Отдельные группа, пояснение, имя базы и кнопка отзыва отсутствуют.

#### Scenario: Запрет
- **WHEN** в deny поступает команда, распознанная Toolkit как опасная
- **THEN** команда отклоняется без диалога и исполнения.

#### Scenario: Каждая команда отдельно
- **WHEN** в ask поступают две опасные команды
- **THEN** кнопка «Разрешить» даёт разрешение только на показанную команду и оставляет ask; для второй требуется отдельное решение.

#### Scenario: Переключение режима из подтверждения
- **WHEN** в ask пользователь нажимает третью кнопку «Разрешить всё в текущем сеансе» в актуальном окне подтверждения опасной команды
- **THEN** окно закрывается, поле «Опасные операции» основной формы принимает session_allow, текущая команда разрешается и последующие опасные команды выполняются без повторного вопроса. Это поведение одинаково для встроенного HTTP и proxy; proxy передаёт решение обработке.

#### Scenario: Отказ или закрытие окна
- **WHEN** пользователь нажимает «Отклонить» либо закрывает окно без выбора разрешения
- **THEN** текущая команда не разрешается и режим не меняется.

#### Scenario: Устаревшее подтверждение сеансового разрешения
- **WHEN** третья кнопка нажата в окне другого поколения разрешений, изменённой команды либо отменённой или просроченной операции
- **THEN** окно не включает session_allow и не разрешает команду. Для актуальной ожидающей операции переключение режима не должно отменять её собственное подтверждение.

#### Scenario: Разрешить всё
- **WHEN** пользователь выбирает session_allow
- **THEN** последующие опасные команды в этом сеансе выполняются без дополнительных подтверждений Toolkit, включая операции удаления; выполнение остаётся в пределах прав платформы.

### Requirement: Сеанс обработки и отзыв разрешения

<a id="am-02"></a>

Session_allow SHALL включаться действием пользователя либо командой set_approval_mode и действовать для текущего сеанса обработки Toolkit в данной базе, общего для подключённых клиентов. Разрешение SHALL не сохраняться для следующего сеанса. Отключение, закрытие, перезапуск Toolkit либо смена базы/пользователя 1С SHALL сбрасывать его в ask. Возврат подтверждений SHALL выполняться выбором ask в том же поле либо через MCP.

#### Scenario: Возврат подтверждений
- **WHEN** пользователь переключает session_allow на «Спрашивать каждый раз»
- **THEN** ещё не запущенные команды проверяются по ask, уже выполняющиеся не объявляются отменёнными или выполненными с откатом.

#### Scenario: Новый сеанс
- **WHEN** обработка отключилась и подключилась заново либо перезапущена
- **THEN** действует ask; сохранённые параметры запуска не восстанавливают session_allow, старое подтверждение не запускает новую команду.

#### Scenario: Несколько клиентов одной обработки
- **WHEN** к той же обработке подключён другой чат
- **THEN** он использует общий выбранный режим; Toolkit не обещает разделения разрешений или защиты от вмешательства между чатами. Область действия описана в документации.

#### Scenario: Обычный HTTP-обмен
- **WHEN** завершён один HTTP-запрос либо переподключился MCP-клиент без отключения самой обработки Toolkit
- **THEN** режим сеанса обработки сохраняется; граница отдельного чата не используется.

### Requirement: Совместимость существующих настроек

<a id="am-04"></a>

Старый флаг подтверждения SHALL мигрировать в deny при false и ask при true, но никогда в session_allow. В новых режимах старые автофлаги записи/привилегированности SHALL не обходить deny или ask; изменение их прежнего поведения SHALL быть объяснено пользователю.

#### Scenario: Переход со старого флага
- **WHEN** загружены старые настройки с авторазрешением записи
- **THEN** выбран deny/ask по основному флагу; старое исключение не выполняет опасную команду без решения в ask. Документация объясняет переход, бессрочного разрешения не появляется.

### Requirement: Разрешения определяются обработкой

Proxy SHALL передавать валидный execute_code обработке без фильтра опасных слов и без добавления признаков разрешения. Решение SHALL принимать обработка; устаревшие переменные ALLOW_DANGEROUS_WITH_APPROVAL и DANGEROUS_KEYWORDS SHALL игнорироваться прокси.

#### Scenario: Прозрачная передача через proxy
- **WHEN** через MCP или REST proxy приходит валидный код подключения внешней компоненты, в том числе при старом ALLOW_DANGEROUS_WITH_APPROVAL=false
- **THEN** proxy передаёт код и контекст в выбранный канал; обработка применяет deny/ask/session_allow, а её результат или отказ возвращается клиенту.
