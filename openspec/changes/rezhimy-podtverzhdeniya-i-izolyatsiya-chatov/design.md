# Минимальное решение в две очереди

## Основание

Поручение пользователя от 12.11.2026 сокращает прежний объём до трёх режимов, поздних результатов и диагностики. Реализована первая очередь в отдельной ветке; пользовательская приёмка не завершена. [Проверка](verification.md). Реализация второй очереди поручена 12.11.2026, без обновления работающего Toolkit. [Требования режимов](specs/approval-modes/spec.md), [операций](specs/operation-lifecycle/spec.md), [диагностики](specs/runtime-diagnostics/spec.md).

## Первая очередь — существующая настройка обработки

Булев флажок заменяется выбором «Запрещать / Спрашивать каждый раз / Разрешить всё в текущем сеансе». Поле «Опасные операции» размещено в общей части вкладки «Подключение» перед «Параллельное выполнение команд» и видно в режимах proxy и встроенного сервера. Отдельных группы, пояснения, имени базы и кнопки отзыва нет. Для возврата подтверждений выбирают «Спрашивать каждый раз». Подтверждение одной команды в ask разрешает только показанный код; изменённая команда требует нового решения. Сеансовое разрешение включает пользователь в форме, не агент своим вызовом.

Под сеансом понимается текущий запуск/подключение экземпляра обработки Toolkit. При отключении, закрытии, restart или смене базы/пользователя 1С временный режим сбрасывается в ask. Завершение отдельного HTTP-запроса или уход из чата не сбрасывает режим, пока обработка остаётся подключённой. Разрешение общее для всех клиентов обработки. Нет owner_id, lease, heartbeat, ограниченных планов или обязательного таймера grant.

Постоянно сохраняются только deny/ask. Session_allow не переносится через startup/autostart/restart и не включается автоматически. При отзыве либо смене режима перед стартом повторно проверяется действующий режим; уже выполняющийся код не считается остановленным. Старые окна не дают разрешения другому сеансу или изменённой команде.

| Условие | Поведение |
| --- | --- |
| Команда не требует проверки опасных операций | Обычное выполнение |
| deny | Отказ без диалога |
| ask | Отдельное решение на команду |
| session_allow | Нет повторных диалогов опасных операций в текущем сеансе |
| Proxy запрещает передачу опасного кода | Отказ proxy независимо от режима формы; понятное ограничение |

Старый danger_confirm=false переводится в deny, true — в ask. Старые автофлаги записи/привилегированности не обходят новые режимы; документация объясняет это намеренное ужесточение при переходе. Это не скрытый четвёртый режим legacy. Разбор старых параметров сохраняется, значение session_allow не принимается как разрешение из сохранённой настройки. Отдельный запрет proxy не снимается автоматически.

Дорабатывается существующая EPF, без изменения основной конфигурации. Основной путь первичной приёмки — имеющийся встроенный HTTP и локальная форма подтверждения. Для уже поддержанного proxy-пути проверяется применение режима в EPF с сохранением верхнего запрета proxy; новая транспортная инфраструктура не создаётся. Подключать отдельный proxy для работы флажка не требуется. Журнал второй очереди и исследование идентичности чатов первую очередь не блокируют.

В окне подтверждения доступны «Разрешить», «Отклонить» и третья кнопка «Разрешить всё в текущем сеансе». Третья кнопка закрывает окно с отдельным результатом session_allow; общий обработчик HTTP/proxy сначала проверяет актуальность показанной команды и ожидающей операции, затем штатным обработчиком смены режима обновляет поле «Опасные операции» и разрешает текущую команду. У текущей ожидающей операции обновляются только режим и поколение разрешений в снимке настроек; прочие ограничения остаются в силе. Разовое разрешение, отказ и закрытие окна режим не меняют. Постоянно сохраняется ask, а не session_allow.

## Вторая очередь — операции после таймаута и диагностика

Отделить срок ожидания клиентского ответа от жизни операции. Использовать operation_id и ключ повтора, связанный с фактическим кодом/параметрами. Native статус/получение результата не должны повторять execute_code. Журнал фиксирует приём, возможный запуск и подтверждённый итог; после неоднозначного сбоя остаётся unknown.

До реализации TASK-002 определить минимальное размещение журнала для выбранного существующего пути: в компоненте, принимающем команды (EPF либо используемый proxy). Не создавать обязательный отдельный сервис. Записи о запуске должны переживать сбой этого компонента; при недоступном хранилище новые команды отклоняются до исполнения. Сроки/квоты объявляются явно. Просроченный ключ отклоняется, running/unknown не вытесняются ради места; конкретный формат хранения и ограничение повторов обосновываются в TASK-002 без обязательной системы эпох из прежнего проекта.

Состояния различают awaiting_approval, queued, running, succeeded, failed, rejected, expired/cancelled при наличии такого исхода, unknown. Новый API отмены, список с пагинацией и независимые чтения данных не входят в эту поставку. Служебный статус не требует выполнения кода базы. Предусмотреть безопасную сверку unknown по фактическим данным/ответу, без автоматического повторения и без обещания отката.

Диагностика объясняет источник отказа, показывает operation_id/correlation_id (один ID), этап, базу и контекст. При успехе error=null; детали/стек очищаются от секретов. Сообщения выдаются только при проверенной возможности отделить вызов, иначе unavailable. Готовность показывает последнее подтверждённое состояние и его свежесть, не запускает второй клиент после потерянного ответа restart.

## Границы и особенности 1С

Права 1С и ограничения платформы сохраняются; session_allow не выдаёт новые права. UI выполняется на клиенте, код — в его фактическом client/server контексте. Ожидание пользователя не удерживает транзакцию; ошибка после записи не доказывает откат внешних эффектов. Работа без пользовательского интерфейса не предполагает автоматического предоставления session_allow.

Из объёма удалены защита от второго чата, резервирование базы, координатор, ограниченные планы/манифесты, модельная проверка, хранилище артефактов, отдельная платформа испытаний прав, расширение транспортов и анонимизация. Режимные проверки на тестовой базе остаются обычной приёмкой, не отдельным проектом.

## Проверка, поставка и откат

Первая очередь принимается отдельно: три режима, несколько последовательных опасных команд, возврат ask, отключение/restart, старые настройки и запрет proxy. Выполнить применимые автоматические проверки, BSL/формы и сборку; runtime-проверку фиксировать отдельно на свежих тестовых данных.

Вторая очередь принимается отдельно: поздний успех, retry без дубля, конфликт кода, сбой/unknown, истечение хранения, сообщения и ошибочные/устаревшие сведения. До отката разрешить фактический исход активных операций, сохранить нужные результаты; откат EPF не откатывает данные.

Для первой очереди сверена отдельная тестовая среда 8.3.27.2342. Правки выполнены в обработчиках основной формы без изменения GENERATED-блоков; поиск генератора перестал блокировать именно эти правки. Генератор для будущих зависимых изменений по-прежнему не найден. Отдельный server-host со своим профилем не является сеансом основной формы и не изменён. Чатовая идентичность, модельный провайдер и координатор больше не являются вопросами этого change.
