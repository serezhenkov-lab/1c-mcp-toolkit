# Минимальное решение в две очереди

17.11.2026: [протокол восстановления файлового канала](file-recovery.md). Менеджер удерживает executor.lock от чтения current/session до конечного ответа, фиксирует маркер каждой принятой команды. Proxy проверяет маркер и общий журнал, отзывает старый сеанс и публикует новый только под эксклюзивным handle. HTTP доступен во время ожидания исполнителя; unknown не переисполняется. Legacy/unclaimed и неподтверждённые платформы остаются заблокированы, не объявлены реализованными.

16.11.2026: [ограниченный промежуточный прогресс](../upravlenie-test-klientom/intermediate-progress.md) добавлен в существующие владельцы SQLite/embedded, без второго журнала. Сохранены capability negotiation, квоты, изоляция и unknown; незавершённые задачи не закрыты.

Продолжение 15.11.2026: [обслуживание журнала без длительного захвата HTTP](../upravlenie-test-klientom/lifecycle-http.md). Подготовка и обе проверки checkpoint разделены на шаги, запись отменяет неподтверждённую подготовку; commit/замена выполняются без уступки управления. Формат и правила восстановления сохранены.

Продолжение 15.11.2026: [оптимизация embedded-владельца и чтение status](../upravlenie-test-klientom/lifecycle-fast.md). Хеши вычисляются пакетами, неизменившийся полный checkpoint не переписывается перед каждым отказом. Чтение существующей операции не создаёт новую запись; старые ключи/ID и изоляция сохранены.

Замеры 15.11.2026: [embedded-квоты и задержки](../upravlenie-test-klientom/lifecycle-limits.md): подтверждены ограничения доступности при синхронной очистке и отказ чтения status по общей квоте. Runtime не изменён; требования не ослаблены.

Продолжение 15.11.2026: [протокол компактации embedded-владельца](../upravlenie-test-klientom/lifecycle-compaction.md): проверенный checkpoint + commit, периодическое удаление истёкших payload, сохранение занятых ключей и активных/unknown записей. Зависимые результаты ограничены сроком источника; UI-адаптер мигрирует старые cached status. SQLite-путь не изменён, полная матрица остаётся открытой.

Продолжение 15.11.2026: общий embedded-owner находится в runtime EPF (`1c/runtime/embedded_lifecycle.bsl`), UI-адаптер использует его API без второго журнала. [Формат хранения, TTL/квоты, восстановление и ограничения](../upravlenie-test-klientom/embedded-lifecycle-partial.md). SQLite остаётся владельцем существующего proxy-пути; обязательного нового сервиса нет. Физическая очистка JSONL и полная матрица отказов не завершены.

## Первая очередь — существующая настройка обработки

Булев флажок заменяется выбором «Запрещать / Спрашивать каждый раз / Разрешить всё в текущем сеансе». Поле «Опасные операции» размещено в общей части вкладки «Подключение» перед «Параллельное выполнение команд» и видно в режимах proxy и встроенного сервера. Отдельных группы, пояснения, имени базы и кнопки отзыва нет. Для возврата подтверждений выбирают «Спрашивать каждый раз». Подтверждение одной команды в ask разрешает только показанный код; изменённая команда требует нового решения. По уточнению пользователя от 17.11.2026 тот же режим можно установить командой MCP set_approval_mode: обязательный mode=deny/ask/session_allow. Команда доступна через встроенный MCP/REST и существующий proxy, использует обработчик поля формы, не требует собственного подтверждения и не исполняет ожидающие команды. Ответ содержит mode, previous_mode, scope=toolkit_session; повтор текущего значения не меняет поколение разрешений. Четвёртый режим и новый параметр запуска не вводятся.

Под сеансом понимается текущий запуск/подключение экземпляра обработки Toolkit. При отключении, закрытии, restart или смене базы/пользователя 1С временный режим сбрасывается в ask. Завершение отдельного HTTP-запроса или уход из чата не сбрасывает режим, пока обработка остаётся подключённой. Разрешение общее для всех клиентов обработки. Нет owner_id, lease, heartbeat, ограниченных планов или обязательного таймера grant.

Постоянно сохраняются только deny/ask. Session_allow не переносится через startup/autostart/restart и не включается автоматически. При отзыве либо смене режима перед стартом повторно проверяется действующий режим; уже выполняющийся код не считается остановленным. Старые окна не дают разрешения другому сеансу или изменённой команде.

| Условие | Поведение |
| --- | --- |
| Команда не требует проверки опасных операций | Обычное выполнение |
| deny | Отказ без диалога |
| ask | Отдельное решение на команду |
| session_allow | Нет повторных диалогов опасных операций в текущем сеансе |
| Команда пришла через proxy | Proxy передаёт код обработке; решение определяется её режимом |

Старый danger_confirm=false переводится в deny, true — в ask. Старые автофлаги записи/привилегированности не обходят новые режимы; документация объясняет это намеренное ужесточение при переходе. Это не скрытый четвёртый режим legacy. Разбор старых параметров сохраняется, значение session_allow не принимается как разрешение из сохранённой настройки. Отдельный фильтр разрешений proxy удалён по уточнению пользователя от 12.11.2026; старые переменные ALLOW_DANGEROUS_WITH_APPROVAL и DANGEROUS_KEYWORDS игнорируются.

Дорабатывается существующая EPF, без изменения основной конфигурации. Основной путь первичной приёмки — имеющийся встроенный HTTP и локальная форма подтверждения. Для уже поддержанного proxy-пути проверяется применение режима в EPF без отдельного фильтра разрешений proxy; новая транспортная инфраструктура не создаётся. Подключать отдельный proxy для работы флажка не требуется. Журнал второй очереди и исследование идентичности чатов первую очередь не блокируют.

В окне подтверждения доступны «Разрешить», «Отклонить» и третья кнопка «Разрешить всё в текущем сеансе». Третья кнопка закрывает окно с отдельным результатом session_allow; общий обработчик HTTP/proxy сначала проверяет актуальность показанной команды и ожидающей операции, затем штатным обработчиком смены режима обновляет поле «Опасные операции» и разрешает текущую команду. У текущей ожидающей операции обновляются только режим и поколение разрешений в снимке настроек; прочие ограничения остаются в силе. Разовое разрешение, отказ и закрытие окна режим не меняют. Постоянно сохраняется ask, а не session_allow.

## Вторая очередь — операции после таймаута и диагностика

Отделить срок ожидания клиентского ответа от жизни операции. Использовать operation_id и ключ повтора, связанный с фактическим кодом/параметрами. Native статус/получение результата не должны повторять execute_code. Журнал фиксирует приём, возможный запуск и подтверждённый итог; после неоднозначного сбоя остаётся unknown.

До реализации TASK-002 определить минимальное размещение журнала для выбранного существующего пути: в компоненте, принимающем команды (EPF либо используемый proxy). Не создавать обязательный отдельный сервис. Записи о запуске должны переживать сбой этого компонента; при недоступном хранилище новые команды отклоняются до исполнения. Сроки/квоты объявляются явно. Просроченный ключ отклоняется, running/unknown не вытесняются ради места; конкретный формат хранения и ограничение повторов обосновываются в TASK-002 без обязательной системы эпох из прежнего проекта.

Состояния различают awaiting_approval, queued, running, succeeded, failed, rejected, expired/cancelled при наличии такого исхода, unknown. Новый API отмены, список с пагинацией и независимые чтения данных не входят в эту поставку. Служебный статус не требует выполнения кода базы. Предусмотреть безопасную сверку unknown по фактическим данным/ответу, без автоматического повторения и без обещания отката.

Диагностика объясняет источник отказа, показывает operation_id/correlation_id (один ID), этап, базу и контекст. При успехе error=null; детали/стек очищаются от секретов. Сообщения выдаются только при проверенной возможности отделить вызов, иначе unavailable. Готовность показывает последнее подтверждённое состояние и его свежесть, не запускает второй клиент после потерянного ответа restart.

## Границы и особенности 1С

Права 1С и ограничения платформы сохраняются; session_allow не выдаёт новые права. UI выполняется на клиенте, код — в его фактическом client/server контексте. Ожидание пользователя не удерживает транзакцию; ошибка после записи не доказывает откат внешних эффектов. Работа без пользовательского интерфейса не предполагает автоматического предоставления session_allow.

Из объёма удалены защита от второго чата, резервирование базы, координатор, ограниченные планы/манифесты, модельная проверка, хранилище артефактов, отдельная платформа испытаний прав, расширение транспортов и анонимизация. Режимные проверки на тестовой базе остаются обычной приёмкой, не отдельным проектом.

## Проверка, поставка и откат

Продолжение 14.11.2026: [события подтверждения](lifecycle-approval.md) передаются только для команд lifecycle_version=1. Неоконечные awaiting_approval/running имеют порядковые номера 1/2; rejected поступает как структурированный конечный ответ с причиной. Старые события не меняют итог и не возобновляют unknown. HTTP и файловый путь используют существующую очередь; решения остаются в 1С. Встроенный HTTP и test_* ещё не интегрированы.

Решение 14.11.2026: первый существующий путь — proxy, устойчивый SQLite-журнал над ChannelCommandQueue; opt-in native execute_code_operation/get_operation, без изменения legacy execute_code. [Контракт ключа, TTL, квот, восстановления и ограничения](lifecycle-proxy-partial.md). Это частичная реализация; awaiting_approval/rejected из EPF и встроенный HTTP ещё не подключены, требования OL-01/OL-02 сохраняются полностью.

Первая очередь принимается отдельно: три режима, несколько последовательных опасных команд, возврат ask, отключение/restart, старые настройки и передачу решений обработки через proxy. Выполнить применимые автоматические проверки, BSL/формы и сборку; runtime-проверку фиксировать отдельно на свежих тестовых данных.

Вторая очередь принимается отдельно: поздний успех, retry без дубля, конфликт кода, сбой/unknown, истечение хранения, сообщения и ошибочные/устаревшие сведения. До отката разрешить фактический исход активных операций, сохранить нужные результаты; откат EPF не откатывает данные.

Для первой очереди сверена отдельная тестовая среда 8.3.27.2342. Правки выполнены в обработчиках основной формы без изменения GENERATED-блоков; поиск генератора перестал блокировать именно эти правки. Генератор для будущих зависимых изменений по-прежнему не найден. Отдельный server-host со своим профилем не является сеансом основной формы и не изменён. Чатовая идентичность, модельный провайдер и координатор больше не являются вопросами этого change.
