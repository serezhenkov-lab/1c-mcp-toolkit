# TASK-002 — состояния подтверждения из 1С

14.11.2026. Добавлена передача состояний из основной формы Toolkit в существующий общий журнал proxy. Это продолжение [первой реализации](lifecycle-proxy-partial.md). Незавершённые пункты плана не закрыты, рабочая установка не обновлена, клиентский адаптер не внедрён; Открыть() не затрагивался.

## Реализация

- Только durable-команда получает верхнеуровневый `lifecycle_version=1`. При её приёме 1С сохраняет адрес и канал доставки, чтобы событие относилось к принятой команде. Legacy-команды не получают новых событий/признаков отказа.
- Перед открытием формы подтверждения 1С отправляет `lifecycle_event=awaiting_approval, lifecycle_seq=1`. Принятое актуальное разрешение отправляет `running, 2`. Это сообщения состояния, а не результат: они не завершают ожидание и не извлекают следующую команду.
- Отказ приходит в конечном ответе с `success=false`, `lifecycle_outcome=rejected` и причиной `mode_deny`, `user_declined` либо `approval_stale`. Исходный текст ошибки сохраняется, но не используется для классификации. Закрытие формы без решения трактуется как user_declined. Ошибка исполнения с похожим текстом остаётся failed.
- HTTP использует существующий `/1c/result`; файловый мост — отдельный атомарно публикуемый `<id>.lifecycle.json` рядом с ответом. Файл события не удаляет привязку принятого задания и не завершает его. Мост читает последнее событие перед итогом и удаляет его при уборке результата.
- Журнал хранит номер события. Повтор того же события идемпотентен, старый номер/противоречивый переход отвергается. Событие чужого канала, ещё не выданной/legacy-команды или уже завершённой операции не принимается. После перезапуска awaiting_approval становится unknown; позднее running не возобновляет исполнение. SQLite прежнего формата получает event_seq без удаления операций и ключей.
- При недоставленном событии 1С пишет диагностическое сообщение, но не повторяет опасный код и не изменяет решение пользователя. Наблюдаемый статус может отставать до конечного ответа. Отказ передаётся конечным структурированным результатом независимо от доставки промежуточных событий. Права и решение остаются в 1С, транзакция базы для ожидания окна не открывается.
- Рукописные точки: приём proxy-команды, открытие и callback подтверждения, проверка разрешения перед исполнением, отказ параллельного подтверждения и сериализация результата. **344 GENERATED-блока не изменены**; модуль объекта и форма клиентского адаптера не менялись.

## Проверка на 8.5.1.1529

Отдельная файловая база `.local/lifecycle-approval/db` — копия предыдущего изолированного стенда. Native MCP на `127.0.0.1:17654`, канал `lifecycle-approval`; реальные EPF и клиент платформы. Выполнены **12/12 сценариев**: по шесть через HTTP polling и локальный файловый мост. Это не проверка RDP-сети или клиент-серверной базы.

| Сценарий | Итог на обоих маршрутах | Документов с уникальным номером |
|---|---|---:|
| deny | rejected / mode_deny; без ожидания окна | 0 |
| отклонение | awaiting_approval → rejected / user_declined | 0 |
| закрытие без решения | awaiting_approval → rejected / user_declined | 0 |
| смена поколения разрешений | awaiting_approval → rejected / approval_stale | 0 |
| разовое разрешение | awaiting_approval → running → succeeded | 1 |
| разрешение сеанса | awaiting_approval → running → succeeded | 1 |

Открывалась настоящая форма подтверждения. Через три секунды тестовая копия программно закрывала её с соответствующим результатом: это имитация решения пользователя, не ручная приёмка кнопок. Пока окно открыто, независимый native get_operation видит awaiting_approval, а повтор запроса возвращает тот же ID без нового исполнения. Повтор после итога также не запускает действие. Количество документов проверено отдельными запросами 1С. В файловом маршруте короткий running после разрешения не всегда попадал в опрос; его фактическое принятие подтверждено event_seq=2 в SQLite, а не предположено по succeeded.

В файловой базе параллельный исполнитель штатно выключен. Ветка его отказа обновлена, но сквозное выполнение параллельного режима здесь не подтверждено. Встроенный HTTP, server_host, реальные удалённые диски и test_* не объявляются проверенными этим прогоном.

## Диагностика файлового стенда

Первые четыре файловых запроса deny остались без ответа. Точная ошибка 1С: `ТекстовыйДокумент.Записать: Вывод запрещен`. Выгрузка текущей конфигурации подтвердила отсутствие Output в роли ApiProbeAdmin. В **этой тестовой копии** добавлено только `Configuration.StubConfig: Output` через role-edit и частичную загрузку роли. Код записи файлов Toolkit не заменялся способом обхода права.

Перед новым файловым сеансом исход каждого зависшего запроса независимо сверялся через уже проверенный HTTP-путь: документов с его номером 0. Старые `.running` и журнал сохранены; указатель current.json архивировался только после сверки и остановки старого клиента. Защита файлового моста от неразрешённого перезапуска действительно сработала. После изменения тестовой роли все шесть файловых сценариев прошли. Эти исходные неуспешные попытки не включены в число успешных сценариев.

Дополнительная попытка чтения через V85.COMConnector не удалась (`TYPE_E_LIBNOTREGISTERED`), регистрация COM/системная настройка не менялась; сверка выполнена через Toolkit HTTP. Первые быстрые вызовы сверки попадали до подключения клиента; проверочный скрипт теперь ожидает только явно возвращённый consumer_unavailable, не повторяя принятые операции.
