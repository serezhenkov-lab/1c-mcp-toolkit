# TASK-012: локальный менеджер тест-клиента

Проверки исполняют настоящую служебную форму Toolkit в одноразовой копии EPF.
Основная конфигурация и рабочая установленная обработка не изменяются.
Функции инъекции модального вопроса и потери процесса добавляются **только** в копию.

Предпосылки: Windows, тонкий клиент 8.5.1.1529; стенд
`.local/test-client-preflight/20261112/controlled85`, пользователь `ApiProbe`,
метаданные диагностической обработки `ApiFixture` из preflight; свободный порт 16538.
Пользователь стенда уже настроен для открытия внешних обработок без предупреждения.
Сами тесты эту настройку не меняют.

1. `python tests/test_client/prepare_runtime.py .local/task012/<новый-каталог>`
2. Собрать `<новый-каталог>/MCPToolkit.xml` в `<новый-каталог>/Toolkit-test.epf`
   штатным `epf-build`, с проверкой ThinClient/Server/HandlersExistence на 8.5.
3. `powershell.exe -NoProfile -File tests/test_client/run_runtime.ps1 -RunDir .local/task012/<новый-каталог>`
4. Тем же вызовом с `-WithoutManager` проверить отказ обычного сеанса.

Для повторного полного прогона нужен новый каталог. Скрипт проверяет свежесть отчётов.
`result.json` содержит основной прогон, `result-recover.json` — новый процесс менеджера,
`result-normal.json` — отказ без TESTMANAGER. Детали — сериализованные снимки состояния.
Очистка сверяет PID, время создания и уникальный токен из receipt этого прогона.
Принудительная остановка есть только в тестовом fault injection/cleanup, не в драйвере.

Проверяются старт и API-ready, запрет второго запуска, профиль другой базы,
detach/attach, новый session_id, чужой stop, занятый порт без владения, stop собственного
процесса, модальное препятствие без автоматического ответа, нулевой тайм-аут,
потеря процесса, прерывание с unknown, восстановление receipt новым менеджером,
отказ stop без восстановленного доказательства владения и сброс session_allow.

Это локальные проверки TASK-012. Они не проверяют сетевой restart через MCP,
публикацию operation_id/дедупликацию общего lifecycle, UI-ID следующих TASK,
HTTP/file-маршруты или клиент-серверную базу.

## Внутренний интерфейс драйвера

Основная форма: `ПолучитьМенеджерТестирования(Профиль)` возвращает единственный драйвер.
Он не открывает дополнительное окно. Профиль — доверенная локальная структура:
`id`, `exe`, `connection`, `user`, `port`, `receipt_path`, необязательный `password`.
Она не принимается как параметры внешнего инструмента. Внешний контракт принимает
только `profile_id`; его разрешение и проверка разрешений относятся к TASK-016.

В этой версии exe должен совпадать с `1cv8c.exe` текущей платформы менеджера,
connection — со строкой текущей базы. Порт 1024–65535, endpoint — только localhost.
Для attach подтверждается владелец TCP listener и однозначная командная строка
формата профиля: `/IBConnectionString ... /TESTCLIENT -TPort...`.
Иные варианты запуска (включая ручной `/F`, псевдонимы и удалённый endpoint)
не считаются доказательством базы и отклоняются. Это отказ при недостатке доказательств,
не вывод о несовместимости самой платформы.

Вызовы: `Настроить(Профиль)`, `ВыполнитьСеанс(action, session_id, operation_id, timeout_ms)`,
`СостояниеСеанса()`, `ЗавершитьМенеджер()`. operation_id передаёт будущий общий адаптер;
здесь нет второго реестра операций, TTL, разрешений или транспортного envelope.
Живые объекты API и WMI остаются на клиенте. Снимок содержит текущую операцию,
состояние, диагностические окна и ошибки без командной строки/секретов.

Receipt хранит только PID, время создания и токен. Он записывается до запуска
с неизвестным PID, затем уточняется. После перезапуска receipt запрещает повторный
запуск, но **не даёт владения**: подключиться можно явно, stop запрещён.
Повреждённый receipt или незавершённый запуск с неизвестным PID требуют ручной сверки
процессов перед удалением receipt; автоматического сброса этой защиты нет.
После доказанного завершения известного процесса новый start допустим.

## TASK-013: чтение UI и ожидания

Для UI-прогона используйте `python tests/test_client/prepare_runtime.py .local/task013/<новый-каталог> --ui`;
сборка и запуск — теми же командами выше. Добавляются только тестовые callbacks и
методы подготовки фикстуры в одноразовую копию; исходная конфигурация базы не меняется.

Основная форма предоставляет внутренний клиентский вход
`ПринятьКомандуТестирования(tool, args, operation_id, callback)`.
Принятие возвращает queued; последовательный обработчик передаёт конечный envelope в callback.
UI-объекты не передаются на сервер. status сеанса читает локальное состояние очереди.
Общий transport/lifecycle/permissions/anonymization подключается в TASK-016;
публичный диспетчер пока возвращает client_context_unavailable, чтобы не обходить эти проверки.

Проверки: open, окна, дерево/лимиты, значения, точные селекторы и path, неоднозначность,
устаревшие ID, сохранение сообщений, видимость страниц, readonly/editing, очередь,
нулевой тайм-аут и достижение условия после отдельного изменения фикстуры.
message сравнивает точный текст в текущем снимке. row проверяет значения текущей строки
без навигации; отсутствие во всей таблице не подтверждается, not_equals → incomplete_search.
Без независимого идентификатора строки equals также возвращает incomplete_search,
verification=not_confirmed, actual.identity.status=unavailable и values_verified=false.
Прочитанные values — диагностика; matched/found=false не доказывают отсутствия строки.
UI-прогон создаёт две физические строки с одинаковыми текстами и в отдельном сценарии
переключает строку между чтениями ячеек. Перехват внедряется prepare_runtime.py только
в одноразовую копию. Последующая запись маркера во вторую строку подтверждает, что
первая и вторая — разные строки; производственный expect навигацию не выполняет.


Пункт 3.4: UI-прогон также проверяет coverage для windows/tree/values/messages, partial при depth/max_nodes и явные unsupported command_interface/command_bars/table_additions. Полнота относится только к заявленной области.

Для test_input: `python tests/test_client/prepare_runtime.py .local/task041/<новый-каталог> --input`.
Соберите `tests/test_client/input_fixture/ApiFixture.xml` в `<новый-каталог>/InputFixture.epf`,
а созданный `MCPToolkit.xml` — в `<новый-каталог>/Toolkit-test.epf`. Запуск — через тот же
`run_runtime.ps1`. В тестовую команду запуска клиента добавляется `/Execute InputFixture.epf`;
основная конфигурация базы не меняется. Новая форма содержит строку, флажок, список с
разными значениями/одинаковыми подписями, обработчик исправления текста и список из 501 пункта.

Проверяются text/clear/check/select, отсутствие повторного переключения, отказ значения,
неоднозначный/неполный список, readback-сбой и неизвестный исход после фактического ввода.
Инъекции остаются только в одноразовой копии. При unknown отдельно проверяется текст
редактора: данные ещё не изменены, редактор не отменён и ввод вызван ровно один раз.
Табличная часть читает только уже выделенные строки; одинаковые описания не объединяются.
Успешный выбор через табличную форму этим прогоном **не подтверждается**: независимая
идентичность строки отсутствует, 4.1 остаётся частично выполненным.

## Локальная часть приёмки TASK-017/7.3

`python tests/test_client/prepare_acceptance_ui.py .local/task073/<новый-каталог>` создаёт одноразовую копию harness разрешений и fixture с уникальными номером/маркером документа. Соберите `<каталог>/fixture/ApiFixture.xml` в `<каталог>/InputFixture.epf`, затем `<каталог>/MCPToolkit.xml` в `<каталог>/Toolkit-test.epf`; используйте epf-build с платформенными проверками. Запуск — `run_runtime.ps1 -RunDir <каталог> -DatabasePath <отдельная-копия-базы>`.

Обязательно отдельная одноразовая файловая база с T43_Required: сценарий фиксирует запись через кнопку служебной формы. Создание копии допускается только при исключительном доступе к исходному 1Cv8.1CD; рабочие базы не копировать этим сценарием. Пакет `acceptance-plan.json`, точный запрос из acceptance-result.sdbl и результат `acceptance-data.json` сохраняются рядом с result.json. Проверяется отсутствие номера до UI и после отказа, затем ровно одна запись и её значения. Ссылки документа относятся к этой одноразовой базе.

Это локальный вход через ПринятьКомандуТестирования и тестовая форма, не публичные HTTP/file-маршруты и не нативная форма документа. Ответы на диалоги разрешений вводит harness; автономность пользовательского сценария этим не принята. Данные оставляются в изолированной копии для проверки; повторный прогон — с новым каталогом/идентификатором, без массового удаления документов.
