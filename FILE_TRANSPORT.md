# Файловый транспорт через RDP

Экспериментальный режим для Windows: локальный Python-прокси сохраняет задания,
открытая обработка 1С читает их с перенаправленного диска RDP и записывает ответы.
MCP остаётся HTTP на loopback; публикация базы, внешний IP и изменение VPN не нужны.
Исполнение команд и ограничения исходного toolkit сохраняются.

## Подготовка

Используйте зависимости из `requirements.txt` и Python, совместимый с ними.
Соберите EPF из `1c/MCPToolkit/MCPToolkit.xml`: поставленная `build/MCP_Toolkit.epf`
ещё не содержит файлового режима. Новые Python-зависимости для транспорта не нужны.

## Запуск

### Установленный комплект harness

Рабочий каталог: `C:\1C\tools\ai\mcp\1c-mcp-toolkit`.
Запуск: `& C:\1C\tools\ai\mcp\1c-mcp-toolkit\run.ps1`.
Каналы и порт задаются в `config.json` рядом со скриптом. EPF — `MCP_Toolkit.epf`
в этом же каталоге, обмен — `exchange\<канал>` (внутри — сеансы с UUID).
Для локальной базы используйте адрес
`file://C:\1C\tools\ai\mcp\1c-mcp-toolkit\exchange\<канал>`,
для RDP — `file://\\tsclient\C\1C\tools\ai\mcp\1c-mcp-toolkit\exchange\<канал>` (внутри — сеансы с UUID).
Постоянный путь канала берите из строки `RDP file channel` в логе. Не переносите активные задания из старой папки обмена.

### Запуск исходников для разработки

В harness корень форка — `C:\1C\dev\1c-harness\external\mcp\1c-mcp-toolkit`.
Запуск из PowerShell с подготовленным виртуальным окружением:

```powershell
cd C:\1C\dev\1c-harness\external\mcp\1c-mcp-toolkit
$env:FILE_BRIDGE_ROOT = 'C:\1C-Bridge'
$env:FILE_BRIDGE_CHANNELS = '1703784,1690771'
$env:PORT = '6004'
$env:RESPONSE_FORMAT = 'json'
$env:DEBUG = 'false'
.\.venv\Scripts\python.exe -m onec_mcp_toolkit_proxy
```

Единый параметр `FILE_BRIDGE_CHANNELS` — список через запятую. Для одной базы
укажите одно значение, например `client-test`. Прежний `FILE_BRIDGE_CHANNEL`
больше не используется. Имена: латинские буквы, цифры, дефис, подчёркивание,
до 64 символов; пустые имена, повторы без учёта регистра и имена устройств
Windows отклоняются при запуске. Номер тикета подходит; тестовую и рабочую
базы различайте суффиксами, например `1703784-test` и `1703784-prod`.

Прокси слушает только `127.0.0.1` и создаёт отдельные каталоги:

```text
C:\1C-Bridge\1703784\<UUID первого сеанса>
C:\1C-Bridge\1690771\<UUID второго сеанса>
```

Полный путь каждого выводится в строке `RDP file session` вместе с каналом.
Подключения MCP проектов используют один порт:

```text
http://127.0.0.1:6004/mcp?channel=1703784
http://127.0.0.1:6004/mcp?channel=1690771
```

В RDP включите разрешённое перенаправление диска. Откройте собранную EPF в
тестовой базе тонким/толстым клиентом, выберите режим **Прокси**.
Для первого проекта адрес — `file://\\tsclient\C\1C-Bridge\1703784`,
поле **Channel ID** — `1703784`. Для второго используйте его канал и постоянный каталог.
Для локальной проверки: `file://C:\1C-Bridge\1703784`.
Префикс `file://` — маркер транспорта; после него идёт буквальный Windows-путь,
без URL-кодирования. На один канал допускается одна открытая обработка.
Соответствие канала конкретной базе задаёт оператор.

При обновлении на постоянные пути один раз переоткройте новую EPF и уберите
GUID из адреса. После этого перезапуск прокси не требует менять адрес в 1С:
обработка читает `current.json` в папке канала при каждом опросе. Если за время
остановки исчерпаны попытки переподключения, нажмите «Подключиться» с тем же адресом.
Внутренние папки с GUID по-прежнему меняются. Добавление каналов требует перезапуска.

Файлы читает и пишет клиентская часть; сервер 1С выполняет команды и проверяет
UTC-срок задания. Часы локального ПК и сервера 1С должны быть синхронизированы.
Веб-клиент не поддерживается. Права на внешние обработки и файловые операции необходимы.

## Доставка и сбои

- `current.json` атомарно публикуется после создания `session.json`; содержит
  версию, канал и UUID. В 1С UUID проверяется до построения пути.
- Принятое задание запоминает папку сеанса. Его ответ сохраняется туда же,
  даже если `current.json` уже указывает на новый сеанс. Старые ответы не
  переносятся и старые задания не сканируются.
- При штатной остановке отзывается `session.json`, а указатель остаётся:
  чтение остановленного сеанса завершится ошибкой. Новый запуск заменит указатель.

- В каждом канале один запрос в работе, остальные ожидают в его очереди.
  Разные каналы обслуживаются независимо: отсутствие ответа или ошибка
  файлового транспорта одного канала не останавливает остальные.
- `.tmp` не читаются; готовый JSON публикуется переименованием.
- Клиент переименовывает `.request.json` в `.running` до исполнения.
  Файлы `.running` не подхватываются повторно.
- Ответ `.response.json` принимается только для текущего UUID и проходит
  ту же модель валидации, что HTTP-ответ. После приёма файлы команды удаляются.
- Срок задания учитывает время ожидания в очереди. Истёкшее задание возвращает ошибку.
- При тайм-ауте MCP исполнение в 1С не прерывается. Пока не придёт ответ,
  следующее задание в этом канале не выдаётся: исход предыдущего может быть неизвестен.
- При обрыве после исполнения, но до записи ответа, автоматического восстановления
  результата нет. Проверьте исход операции в базе, отключите старую обработку,
  перезапустите прокси и подключитесь по **тому же адресу канала**. Изменение данных не повторяйте вслепую.
- При штатной остановке удаляется `session.json`. При аварийном завершении файл
  может остаться: старую обработку нужно отключить; ещё не истёкшее задание иначе
  может выполниться. Это не гарантия exactly-once и не транзакция между диском и базой.
- Содержимое папки — команды и данные базы. Доступ на запись равносилен возможности
  отправлять задания. Ограничьте доступ к каталогу; старые сеансы удаляйте после
  отключения обработки и выяснения исхода операций.

Загрузка таблицы соответствий анонимизации из формы по HTTP в файловом режиме
не поддерживается. Файловый канал не добавляет собственной анонимизации.
Перезапуск/закрытие сеанса и вспомогательные нативные функции требуют отдельных проверок.

## Проверка

### Ошибка повторного подключения и статус серверной части

Исправление от 2026-10-27 касается подготовки подключения к прокси (как
файлового, так и HTTP) и отображения состояния серверной части EPF.

При диагностике различайте два независимых уровня:

- Ошибка чтения `current.json` по `\\tsclient\...` относится к доступу клиента
  1С к перенаправленному диску. Код Windows 995 означает прерванную операцию
  ввода-вывода; он сам по себе не доказывает причину обрыва. После пяти ошибок
  подряд обработка прекращает опрос.
- `Неизвестная функция: СохранитьНастройкиНаСервере` при нажатии
  «Подключиться» означает, что клиент не смог вызвать серверный метод EPF.
  Раньше этот вызов выполнялся без перехвата, ещё до запуска файлового обмена.
  Потеря серверной части открытой EPF — гипотеза; для установления причины
  нужны события сеанса/сервера 1С. Обрыв RDP сам по себе её не доказывает.

Теперь перед сохранением адреса вызывается серверная проверка, даже если
периодический контроль выключен. Оба вызова защищены одним обработчиком
исключения: это покрывает и потерю серверной части между проверкой и
сохранением. При отказе опрос останавливается, исходная ошибка с именем
метода попадает в журнал обработки, пользователь получает предупреждение.
При неизвестном методе предлагается переоткрыть EPF; при иной ошибке —
проверить связь с сервером 1С. Вызов сохранения автоматически не повторяется.
Единичный отказ делает состояние неопределённым; прежнее правило двух
последовательных признаков потери серверной точки входа сохранено.

После отключения последний успешный результат больше не отображается как
актуальная доступность: форма показывает, что проверка приостановлена.
При активном подключении результат старше `Макс(30, ИнтервалКонтроляСервера * 2)`
секунд помечается устаревшим; используется тот же критерий, что в readiness.
Индикация пересчитывается обработчиком контроля и сразу при подключении/
отключении. Это не запускает фоновые серверные вызовы в отключённом состоянии
и не меняет настройку автоматического перезапуска сеанса.

Для обновления соберите новую EPF из ветки форка и переоткройте её.
Переустановка Python-прокси для этой правки не требуется: файловый протокол
не изменился. До переоткрытия можно проверить чтение `current.json` изнутри
RDP. Чтение этого файла на локальном компьютере не проверяет перенаправление.
Если EPF по-прежнему не вызывает серверные методы, дальнейшее восстановление
сеанса выполняйте вручную, предварительно сохранив работу в других формах.

Регрессионные сценарии для отдельного тестового сеанса (это план проверки,
а не утверждение, что сбой реального сервера уже воспроизведён):

| Сценарий | Ожидаемый результат |
| --- | --- |
| Исправная EPF, подключение по `file://` и по HTTP | Проверка и сохранение проходят, опрос запускается, запрос `ВЫБРАТЬ 1 КАК Проверка` выполняется |
| Отключение кнопкой после успешной проверки | «Отключено», прежнее «Серверная часть доступна» заменено сообщением о приостановке проверки |
| Потеря доступа к тестовому каталогу обмена на пять опросов | Опрос прекращён, нет ложного подтверждения доступности; после восстановления пути можно подключиться снова |
| Серверный метод проверки недоступен у открытой EPF | Нет необработанного исключения; опрос не запускается, исходная ошибка есть в журнале, показана рекомендация переоткрыть EPF |
| Метод сохранения недоступен после успешной проверки | Тот же управляемый отказ, в журнале указан именно метод сохранения; повторного сохранения нет |
| Обычная ошибка связи с сервером 1С | Предупреждение о связи, без утверждения о доказанной потере контекста |
| Периодический контроль выключен | Проверка перед подключением всё равно выполняется; при истечении срока показан устаревший результат |
| Повторное нажатие «Подключиться» при ранее активном опросе и отказе сервера | Прежний обработчик опроса отключён, новые задания не принимаются |

Потерю серверных методов и сбой между вызовами проверяйте в отладчике или
на изолированной тестовой копии. Не останавливайте рабочий сервер ради теста.
Переоткрытие EPF не восстанавливает неизвестный результат ранее принятого
задания: правила `.running` и запрет слепого повторения остаются в силе.

### Автоматические и эксплуатационные проверки

`python -m unittest discover -s tests -v` проверяет Python-транспорт.
Перед работой на реальной базе проверьте получение метаданных и запрос
`ВЫБРАТЬ 1 КАК Проверка`, затем обрыв RDP до получения задания и после его захвата.
Проверьте отказ при несовпадающем канале и невозможность исполнения `.running` повторно.
Автоматические тесты с имитацией клиента не заменяют эту проверку.

Проверки исправления повторного подключения, 2026-10-27:

- Все 16 существующих Python-тестов транспорта и MCP HTTP прошли. Они
  проверяют доставку, но не исполняют клиентский BSL-код формы.
- EPF собрана на платформе 8.3.27.2342 в отдельной временной базе;
  синтаксический контроль ThinClient/Server и проверка наличия обработчиков
  прошли. Рабочая база для сборки не использовалась.
- BSL Language Server проверил изменённый модуль формы с сопоставлением
  исходного отчёта. Новые замечания `DeprecatedCurrentDate` относятся к трём
  клиентским вызовам `ТекущаяДата()`: оставлен единый источник времени с
  существующим контролем связи; замена на серверное время сеанса здесь
  изменила бы расчёт возраста проверки. Остальные замечания были до правки;
  это не «чистый» отчёт по всему модулю.
- Потеря серверного контекста, разрыв RDP и пользовательские сценарии из
  таблицы выше на реальном клиенте после правки пока не проверены.
  Новая EPF автоматически в рабочий сеанс не устанавливалась.

После этой проверки пользователь подтвердил работу новой обработки и
разрешил включить её в рабочий комплект. Поведение после сбоя пользователь
не проверял; сценарии восстановления остаются открытыми. Это подтверждение
не считается проверкой потери серверного контекста или переподключения RDP.
