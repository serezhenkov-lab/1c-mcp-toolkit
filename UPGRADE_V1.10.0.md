# Пробное обновление до v1.10.0

Дата: 2026-11-06. Ветка: `codex/upstream-v1.10.0`.
Исходное состояние форка: `8fb2bda`; авторский релиз: `v1.10.0` (`ca14a98`).
`main`, установленный прокси, его каналы и EPF не изменялись.

## Совмещение изменений

- Сохранены файловый транспорт RDP, несколько каналов, блокировки каталогов,
  смена сеансов и запрет повторной отправки команды при неизвестном исходе.
- Файловые каналы зарегистрированы в новом реестре исполнителей v1.10.0.
  Регистрация действует до остановки файлового runtime; HTTP-клиент и server-host
  не могут занять такой канал после истечения обычного срока аренды.
- Общая модель ответа сохраняет новое поле `base`, включая различие между
  отсутствующим полем и явным `null`.
- Сохранена проверка серверной части EPF перед подключением. При восстановлении
  регистрации соблюдается новый параметр автора `СохранятьПодключение`.
- Файловый транспорт остаётся последовательным. Новая возможность параллельного
  выполнения для него явно отклоняется: протокол файлового моста не реализует
  HTTP-проверку состояний параллельных команд.
- Зависимости форка уже соответствовали требованиям v1.10.0; они не обновлялись.

## Выполненные проверки

- `python -m unittest discover -s tests -v`: 18 тестов, успешно.
  Проверены доставка MCP через файлы с имитацией 1С, два независимых канала,
  поздние ответы, смена сеанса, тайм-аут без повторного выполнения, завершение
  runtime, защита канала от server-host, `base` и обычный HTTP/REST-обмен.
- Платформа 1С 8.3.27.2342: проверка `ThinClient,Server,HandlersExistence`
  в отдельной временной базе и сборка EPF завершились успешно.
- Сборка: `.local/upgrade-v1.10.0/MCP_Toolkit.epf` (локальный артефакт, вне Git).
  SHA256: `FAF68E6FFE2A2FD62E4BC8D380F28447CEF6DBC61B4FF2E4DBFAA0824EBD91C9`.
- Логи: `.local-upgrade-tests.log`, `.local-upgrade-build.log` (вне Git).

Это проверка исходников и транспорта с имитацией клиента, а не подтверждение
работы всех инструментов релиза в живой базе. Анонимизация, server-host,
новые нативные компоненты и параллельное выполнение HTTP-режима требуют
отдельной проверки, если планируется их использование. Готовые EPF в `build/`
взяты из авторского релиза и не содержат файлового моста форка.

## Изолированная проверка в 1С

Запустить из корня этой ветки в отдельном PowerShell. Сначала убедиться, что
порт 16004 свободен. Используется существующее Python-окружение без изменения
его зависимостей; рабочий прокси на другом порту продолжает работать.

```powershell
$env:PORT = '16004'
$env:FILE_BRIDGE_ROOT = Join-Path (Get-Location) '.local/upgrade-v1.10.0/exchange'
$env:FILE_BRIDGE_CHANNELS = 'upgrade-v110-test'
& C:/1C/tools/ai/mcp/1c-mcp-toolkit/.venv/Scripts/python.exe -m onec_mcp_toolkit_proxy
```

В отдельном тестовом сеансе 1С открыть собранную EPF и указать:

- режим «Прокси»;
- Channel ID: `upgrade-v110-test`;
- адрес через RDP:
  `file://\\tsclient\C\1C\dev\1c-mcp-toolkit\.local\upgrade-v1.10.0\exchange\upgrade-v110-test`;
- адрес MCP тестового прокси:
  `http://127.0.0.1:16004/mcp?channel=upgrade-v110-test`.

Проверить запрос `ВЫБРАТЬ 1 КАК Проверка`, чтение метаданных, отключение и
повторное подключение EPF, затем штатный перезапуск тестового прокси.
Убедиться, что EPF подхватывает новую папку сеанса, а рабочие каналы продолжают
отвечать. При наличии `.running` сначала выяснить исход команды; не удалять
его ради обхода блокировки запуска.

После проверки остановить тестовый прокси через Ctrl+C и закрыть тестовую EPF.
Это полностью прекращает пробный запуск; откат рабочей установки не требуется,
поскольку она не изменялась. Обновлять закреплённую ревизию harness и рабочую
установку следует после успешной проверки в живом тестовом сеансе.
